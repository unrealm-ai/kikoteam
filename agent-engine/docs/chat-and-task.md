# 对话与任务 Session、Pi 扩展

**输入与回报增量设计（2026-11-17，已接入，验收范围见专项设计）**：用户输入默认 steer，可选 queue；任务回报在来源主 chat 排队单独成轮，空闲时主动唤醒，见[引导输入与任务轮次回报](../../backend/docs/session-input-and-task-report.md)。本文静默 append_assistant 仍为独立的零模型调用能力，不承担主动回报。引导不强制取消当前请求或并发执行第二轮，原生 RPC 控制已接通，业务多输入消费证据仍已接入，验收范围见专项设计。

> **2026-11-16 关系与生命周期已确认**：一 Task 一 task Session，共享环境归 Conversation；创建、停止、归档、首版放置及三层回收按[业务会话与共享环境生命周期](../../docs/architecture/conversation-lifecycle.md)。本页已同步目标设计，执行编排及相关机器契约仍待实现。

## 1. 创建时明确模式

候选 `POST /sessions` 必填 mode: chat | task 和可信 Conversation 归属，模式不可切换。Backend 首次聊天创建唯一主 chat；每次新任务同事务建立 Task 与唯一 task Session，补充或故障后继续沿用原 Session。两类上下文独立，首版 task 固定在该业务会话环境的管理 Engine/宿主，chat 独立调度。这里的两类 Agent 仅指运行角色，不新增员工主体。

| 项目 | chat：对话 Agent | task：任务 Agent |
| --- | --- | --- |
| Harness | 固定 Pi，不读取员工选择的任务引擎来决定 Harness | 按员工任务配置和平台已支持的 Harness 解析；当前候选仍只有 Pi，不宣称其他引擎已接入 |
| 模型 | AI 员工配置的自备或官方模型，无工作区／官方默认回退 | 员工配置的 ModelProfile 与版本 |
| 思考 | 显式关闭可配置的 reasoning/thinking | 按任务 Harness 策略，不新增员工或创建会话的思考参数 |
| Sandbox / Runner | 不申请、不创建、不领取 Runner 配置、不等待 Sandbox 健康 | 取得所属业务会话共享的 Sandbox 与 Runner |
| 工具 | 平台预设的 task_delegation 业务 MCP 及其他明确允许、不依赖 Sandbox 的有限能力；禁止本地文件/命令工具、builtin Sandbox MCP、CLI/stdio | 来自当前获准能力包，保留来源与账号边界；首版不挂 task_delegation，避免递归委派 |
| 压缩 | 待评估的后台压缩，新增扩展须先明确确认 | 仍按原任务 Harness 设计；不自动套用 chat 扩展 |
| 静默追加 | 候选静默 assistant 追加，原生能力缺口及扩展方案须先明确确认 | 暂不因本设计扩大范围 |

chat 的 Engine 侧配置目录、持久原生历史和 Engine 身份映射仍然存在，但不是可执行业务脚本的 Sandbox。不建设平台逐轮检查点；故障后旧 Turn interrupted，后续新 Input 经 `--session` 加载并继续。不能因为没有 Runner 就在 Engine 宿主放开文件或命令工具。任务型能力交给独立 task Session，[会话委派 MCP task_delegation](../../backend/docs/task-delegation-mcp.md)已明确六个预设计工具及 Backend/Manager 边界，代码与联调仍未实现。工具集通过平台预设挂载，不作为员工普通插件或任务能力包；来源主会话从可信凭据取得，不由模型填写父 ID。

创建工具只返回受理身份，不等待子会话完成。Manager 的轮次 / 业务完成回报与 MCP 创建响应分开，结果如何入主会话上下文及唤醒仍须对接整体会话入口；下文 append_assistant 只静默追加，不自动总结回复。停止主 chat 不停止其已委派任务，子任务继续、停止及归档遵循生命周期正文。

当前公开创建接口不支持临时指定任意模型。chat 的模型由员工配置决定，平台预设只约束 Harness、工具和非思考策略；客户端不能按消息覆盖模型。创建 chat 时将员工所选模型写入 Session 配置快照；已有会话不回写模型，也不热切换。之后修改员工模型只影响新建会话，不改旧历史。员工修改任务引擎不改变 chat 的 Pi、非思考或工具策略；task 的规则不变。

## 2. 非思考策略与扩展加载

不能仅靠提示词要求“不思考”，也不能只隐藏思考展示。固定版本适配器将平台 `thinking=off` 语义映射到实际提供方支持的请求参数，检查模型及提供方是否支持关闭；只支持强制思考或无法核验该模式的模型不得静默作为 chat 预设使用，应报告配置不兼容。不推断模型内部完全没有推理，仅承诺关闭对外可配置的思考模式。

只加载平台白名单扩展，不继承用户 HOME、员工资源包或任意目录中的扩展。发布固定版本和摘要，登记能力协商结果。背景压缩及静默 assistant 的原生能力缺口须先评估；若确需扩展，先取得用户明确确认，再审查版本、许可和真实行为。“可以加载扩展”不表示已有非阻塞压缩或静默 assistant 能力。

Engine 直接通过原生 RPC 驱动正常轮次，遵守 [Pi 原生能力优先规则](../../AI_RULES.md#通用开发与静态检查)。下述背景压缩和静默 assistant 是历史候选设计，不构成新增插件、扩展桥或自定义 SDK 启动器的实施授权。必须先说明原生能力缺口并取得用户明确确认，再定义控制契约及验收；不能直接改 JSONL、假造用户 prompt 或隐藏输出来冒充静默追加。

## 3. 不阻塞对话的后台压缩

“不阻塞”指前台正常 Turn 不等待后台摘要模型请求完成，不承诺上下文已超过模型硬上限时仍可无限执行。提前设置软阈值和输出预算；禁止原生同步自动压缩与扩展同时修改历史。相关开关和 hook 必须在固定 Pi 版本实测后才能交付。

1. 会话上下文由单一写入者排序，具有单调 `context_revision`、消息序号及 Pi 已持久化的原生记录。后台任务截取稳定前缀并记录截断序号、基准修订和 generation；不持有会话写锁等待摘要调用，不为压缩建立平台检查点。
2. 前台继续用合法的现有上下文处理输入；新消息（含静默 assistant）追加为尾部。后台只生成候选摘要，不覆盖正在执行的 prompt 视图或原生历史。
3. 在无在途 prompt 的安全边界，用短临界区核验 generation、基准前缀摘要和结构；只替换被总结的前缀，完整保留之后的消息、角色、顺序和工具调用/结果配对。原生加载/追加/压缩互斥提交，但后台计算不占该锁。
4. 新增尾部不一定使结果作废；基准前缀变化、分支、重新加载或代次变化则作废候选，不能让旧摘要覆盖新会话。通过原生扩展能力写入压缩记录并持久化，更新修订；不额外上传平台检查点。
5. 失败有界重试，现有历史不丢失；同会话至多一个有效压缩任务，取消/归档会停止或丢弃未提交结果。压缩用量与耗时独立观测，不伪装成前台回复。
6. 到达硬上限且候选尚未可用时，明确报告上下文容量受限并采用有界等待/失败，不静默丢消息或切到会阻塞对话的原生同步压缩。精确阈值在模型容量与压力测试后配置。

后台压缩会产生独立模型调用；它与静默追加“零模型调用”的承诺分开计量。新增输入不等待压缩计算，并不等于同一 Session 同时执行两个正常对话 Turn。

## 4. 仅追加 assistant，不触发模型

扩展操作暂命名 `append_assistant`，是内部上下文写入能力，不复用 `POST inputs`，也不改变公开 Input 只接收用户文本的约定。其精确内部 HTTP/扩展传输契约后续由所属组件设计定义，不新增假实现 API。

- 输入仅允许 `role=assistant` 的文本及来源引用、消息标识；调用方经可信服务身份与会话权限核验，不能注入 system、伪造用户或工具执行结果。不要开放成普通用户可任意伪造 assistant 的入口。
- 保存来源、调用主体与生成方式，公开历史可标记该消息来自平台注入而非本次模型生成；保留原文，不生成空 user 消息。
- 使用每会话唯一注入 ID 去重；同 ID 同内容返回原结果，不同内容冲突。重复通知或响应丢失不能重复追加。
- 在单写者序列中仅追加并持久化原生 assistant 消息和对应历史事件，不调用 prompt、不新建正常 Input/Turn、不触发工具执行或压缩模型调用。只追加可以标记后续需要压缩，但不以此操作直接调模型。
- 若正常 Turn 正在执行，持久排队，在安全边界按明确顺序应用，不修改当前流式响应；“已受理”不等于“已进入上下文”。在接收确认前后崩溃都按注入 ID 与原生记录核对，不盲目再次插入。该扩展的核对只处理静默追加自身，不恢复旧 Turn 或重发 prompt。
- 持久化以可恢复的原生记录为准，并关联平台投影；原生成功、平台投影失败时重建投影而不是重复注入，恢复缺失则保持未确认。没有活动 Pi 进程时可只加载会话处理追加，不发模型请求；加载失败不能新建空会话替代。
- 注入与压缩提交、归档、停止和失联接管共享顺序及代次校验。已归档或无权限拒绝；旧 Engine 的迟到写入拒绝。下一次真正用户输入应看到已确认的 assistant 内容，重启恢复后也相同。

## 5. 验收与证据边界

已有 `chat/task` 分类、平台预设和默认 Sandbox 的文字设计，不等于下面扩展已实现。此前 Pi 自定义 SDK 原型即使能静默追加，也不能证明当前原生 RPC 方案已支持；历史原型本轮未重新运行。后台压缩扩展、非思考参数及所有并发行为当前均为待验目标。

必须覆盖：

- 创建 Session 缺少 mode/未知 mode 被拒；mode 不可修改；员工任务引擎选择不改变 chat 固定 Pi。
- chat 全生命周期 Runner 创建/配置/释放调用为零，Sandbox 故障不阻塞其启动；本地工具及任务资源没有意外暴露。
- 捕获实际模型请求证明非思考配置生效；不支持关闭的模型明确拒绝，不以无可见思考文本当作证据。
- 人为延迟摘要响应时仍可处理多次前台输入；摘要晚到、失效、失败和硬容量边界不丢尾部、不破坏工具配对。
- assistant 单条/批量（若支持）追加、重复、并发、进程重启恢复：模型及工具调用计数均不因注入增加；下一次请求的 role 和内容准确。
- 正常 Turn/静默追加/压缩/停止/归档/代次接管竞争不重复、不乱序、不让旧摘要覆盖新消息；未确认写入可查询和恢复。
- 明确区分扩展单测、Pi 原型、Pi RPC 集成及真实模型验收；未完成当前组合验收不得称该能力可用。
