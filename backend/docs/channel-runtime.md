# 飞书可信输入、历史与可靠投递

**三渠道迁移（实施中）**：本页保留飞书已实现行为；钉钉/企微文本适配、能力差异及统一回执边界见[三渠道文本适配](channel-adapters.md)。单 EventHub，不扩展多节点连接归属；图片和文件共用 Web 会话的项目上传与任务委派链路。任务回告的版本选择和投递规则见[会话文件](conversation-files.md)。

**2026-11-18 目标方案，实施中**：每员工先过滤群事件，Manager 区分 Inbox 准入和 Input 入库；群历史逐条作为不触发上下文缓存，Engine 到首个触发 Input 截批提交一条原生 Pi user prompt。不增加 Node 定制、多角色注入或 assistant 静默追加。完整消息前缀与例子见[主会话规范](../../docs/flows/conversation-and-task.md#主会话输入合批与消息前缀2026-11-18-已确认实施中)。本节目标取代旧版“历史只拼当前正文、native committed 推水位”，实现状态以本次交付与测试为准，不代表真实飞书线上验收。

本期渠道身份独立于 Web，不创建平台账号，不借 workspace owner 的执行权限。三渠道是各自身份域；飞书为既有实现，钉钉/企微文本链路本次迁移中，完成状态以专项验收为准。

## 配置与信任边界

Platform 保存每员工独立机器人配置；Hub 只能通过 `KIKO_HUB_TOKEN` 认证的内部接口取完整配置，不直接查业务配置数据库。接口拒绝 Cookie/Origin，不能与 Engine/Runner 凭据互换。`identity_epoch` 在 AppID 变化时递增，Conversation/principal/dedup 同时绑定该 epoch 和已验证 tenant；相同提供方消息/用户/chat ID 也不能跨应用复用上下文。Secret 轮换保留同身份 pin 和会话；不同 tenant 的 pin 请求拒绝。`connection_generation` 在身份、凭据和启停变化时递增；规则有独立版本。Hub 启动全量、周期同步与通知提示见[配置文档](channel-configuration.md)。

SDK 验证的提供方事件包含绑定、代次、租户、聊天、发送者、消息标识及结构化 mention。已验证 tenant 必须先钉住，不能用空 tenant 作为任意租户通配。Manager 按当前配置再次检查；Hub 命中记录不是权限证据。私聊及私聊话题不在 Hub 静默过滤，员工停用由 Manager 生成固定答复。群/群话题仅在命中该员工可信 @ 或关键词时转发该员工 Inbox；规则命中不代表使用权限。普通群消息、其他员工的定时消息不主动复制；从事件路由目标上，实际命中该员工规则应进入其流程；当前飞书实时入口仍忽略非 `user` sender，保留防机器人互相触发限制，因此机器人 app 发言即使命中也暂不触发。按需历史不受此实时 sender 过滤限制。

`manager_channel_principals` 按 binding/tenant/open_id 隔离。Conversation/Session 创建者、Input 发送者采用 Web 字段与渠道字段二选一，保留真实来源；`user.message`/`input.updated` 为统一历史，渠道 `submitted_by=null`、`principal_type=channel`、`channel_principal_id` 独立。所有 Web 会话读取、列表、SSE 和控制都排除 channel Conversation；workspace owner 不自动获得渠道聊天内容。

员工使用范围与群触发条件分开：私聊按 sender 名单；群开启 `group_members_enabled` 时不受空私聊白名单限制，黑名单仍优先，群 chat allow/deny 范围仍生效。该开关不授予跨群上下文共享。能力包只支持可验证的渠道继承授权；任何 Web 成员白/黑名单包保守排除，不能把渠道 principal 当 Web member。

## 通讯录与部门规则（2026-11-18，迁移 26 已实现）

用户已确认部门规则可选择「包含子部门」；未勾选只匹配所选部门的直接成员。旧规则或未保存该选项的规则保持直接成员语义，不因升级自动扩大允许或拒绝范围；必须由用户显式选择并保存后才应用后代范围。`allow_department_rules` / `deny_department_rules` 保存 `{department_id, include_descendants}`；显式规则数组为准，空数组也表示清空，旧部门 ID 数组仅作镜像。迁移 26 将旧 ID 规则转为 `include_descendants=false`。旧客户端漏传规则而已有包含子部门规则时返回 409，避免静默丢失递归配置。

飞书完整通讯录快照有效期为成功同步后 **24 小时**；自动同步周期仍为 **1 小时**，不改为每天同步。同步失败不延长旧快照的原到期时间：网络/解析失败可沿用尚有效的旧快照，认证/权限读取错误仍使快照立即失效。迁移只将仍有效、完整且同来源的快照延长至 `synced_at + 24h`，不复活已过期或已撤销快照。24 小时是快照有效窗口，不是实时撤权保证；组织变化通常在下一次成功同步后反映。

部门允许规则只在完整、有效快照能够证明成员关系时授予权限；部门黑名单在成员关系未知、快照失效或所需后代关系无法可靠判定时继续保守阻断，不能把“查不到”当作“不在黑名单”。包含子部门不能跨绑定、租户或身份命名空间推断关系，异常层级不能据此扩大授权。

递归父链每路径最多 100 个节点，每次 `department_match`（一次名单匹配）最多 10000 次祖先查表；一次 ACL 的 deny/allow 匹配可能分别使用该预算。循环、缺父或超限均为 unknown。先检测全部直接成员命中，再消耗递归预算，避免已知直接证据被其他病态分支遮蔽。

后端与 Hub 的完整 check/build、迁移 26 schema 校验、相关真实隔离 PG/race 回归和 lint 已通过，包括递归预算与旧规则兼容；不代表真实飞书租户端到端验收。本次仅调整目录和部门范围，投递 `unknown` 的语义、去重及不盲重发行为不变。

## Inbox 与处理

`POST /api/internal/v1/channel-inbox` 先持久化再返回 `{id,status:accepted|duplicate}`。accepted 只表示可靠接收，不表示已授权或模型已执行。绑定+event ID 及绑定+message ID 双重去重；规则版本不是去重键。临时错误不得成功 ACK。

Manager 工作者重新校验当前代次、租户、权限、员工状态和触发条件。群无权限 @ 生成受控固定拒绝；仅关键词命中且无权限时静默；同时命中按 @ 处理。私聊无权限仍可固定拒绝。无权限原文及这些固定拒绝均只保留 Inbox/Delivery 事实，不写 Input、不推进群历史边界。其他失败的固定答复按现有业务规则处理，不通过回复文案反推 Input 已被接受。

Conversation 映射独立按员工绑定、聊天类型和来源 chat 固定，不继承 Web 会话、不替换已归档历史；本次确认主会话及每个话题分别映射独立会话/主 chat Session，Input、Pi 原生会话和历史边界全部隔离。话题继承父会话权限配置，但每次准入、执行、投递仍重验父级当前权限。无话题 ID 兼容原主会话映射及历史，不猜测迁移既有消息到话题；可信 thread/topic ID 才能建立话题身份，禁止拿主群水位假装线程水位。首次事件、消息类型与话题能力按各渠道真实支持情况验证。Input 追加复用原事务及稳定幂等来源，Inbox 崩溃后回收处理租约不会再次执行。

## 三渠道消息延迟排查

飞书、钉钉、企微共用下列日志节点。优先用 `binding_id` + `provider_event_id`（或 `provider_message_id`）找到 Hub 和 Backend 同一次入站，再用后续的内部 ID 串联日志。企微先用 Hub 的 `callback_id` 对上解析前后的记录；企微消息没有可靠的供应商产生时间，不用 Hub 接收时间冒充。相同事件重投会有多条回调记录，Backend 回执标明 `duplicate`；不能把重投当成多次模型执行。日志不含消息正文、姓名、鉴权信息或原始供应商响应。

| 区段 | 关键日志 | 关联方式 |
| --- | --- | --- |
| 渠道 → Hub | `channel.callback.received`、`channel.callback.result` | 渠道标识对照本地收到时间。若事件未匹配、无法转发或未拿到可靠回执，看 result；没有回调日志不能判断 Hub 之前具体哪里延迟。 |
| Hub → Inbox | `channel.inbound.forward`、`channel.inbox_persisted`、`channel.inbound.durable_receipt` | Inbox 持久受理或去重结果；控制事件或准入失败不等于普通 Inbox 写入。 |
| Inbox → Input | `channel.inbox_claimed`、`channel.inbox_waiting_history` / `channel.inbox_history_persisted`、`channel.input_persisted` | `inbox_id` → `input_id` / `session_id`。未授权、处理失败或确认专用路径有独立日志，不应寻找普通 Agent Input。 |
| Input → Engine | `input.claimed`、`turn.finished` | `input_id` / `session_id` / `turn_id`；`queue_wait_ms` 表示 Input 创建到本次领取，领取不等于模型已应用。随当前触发 Input 合批的历史行不逐条触发引擎。 |
| 出站 → 渠道 | `channel.outbox_persisted`（普通对话回复和固定回复）、`channel.delivery.claimed`、`channel.delivery.authorize_result`、`channel.delivery.send` / `channel.delivery.send_result`、`channel.delivery.query_result`、`channel.delivery.receipt_persist` | `delivery_id` 关联发送、供应商查询和回执落库；通知在 Backend 回执上用同一值的 `notification_id`。Backend 的 `channel.outbox_receipt_persisted` / `channel.notification_receipt_persisted` 给出新账本状态。钉钉 `accepted` 只是请求受理，不能按 `sent` 计算；没有确认不能当作已送达。 |


## 按需群历史与 Input 边界

用户选择：**取上次成功写入该员工 Input 的群事件之后、本次事件之前的消息，直到边界或最大历史条数；首次取近期消息**。两端事件不重复补；当前事件自己的 Input 单独保存。是否触发模型与 native receipt 均不参与定义这个渠道历史边界。

企微当前历史截取仍按上一条同名机器人 @ 定位。Manager 保存成功入 Input 的边界用于一致性检查，历史接口返回的秒级时间和快照内记录键无法直接关联该 Input 的回调消息 ID。见[企微群历史的当前实现](channel-adapters.md#企微群历史的当前实现)。

每个员工绑定身份 epoch、tenant、群/话题范围维护独立水位，至少保留来源事件 ID、渠道发生时间、Input 顺序及入库关联。Manager 冻结上次边界与当前锚，Hub 在授权范围内分页读取；不维护所有群消息的实时正文滑窗。历史拉取不按每个发言人的员工使用权限过滤，可以读到无权限发言、已经发送的固定拒绝及其他员工消息，但仍只能读本次获准范围。历史是引用上下文，不授予历史作者执行或读取权限。

首次绑定飞书或企微时，默认在员工群配置中启用该渠道的近期上下文，沿用员工现有条数。旧绑定、重新绑定和主动关闭的现有渠道不会被重新启用；钉钉不支持群历史。企微默认设置适用于收到群 @ 时补充近期消息，不改变主动发送通知的上下文处理。

历史按原顺序逐条写为 `trigger_agent_loop=false` 的 Input；当前授权用户触发消息按触发语义写 true。该员工群定时提醒的目标流程是先补此前历史，再写自身提醒 false Input；定时和人工确认端到端生产入口尚未实现，底层存储能力不等于已交付这些业务入口。**补历史、写当前事件、关联 Inbox/来源及更新水位在同一事务提交**；只在全部成功时推进。无权限事件不进入该事务。另一员工的定时消息不主动生成本员工 Input，但可能由本员工下一次历史补读纳入。

事件接收、来源权限、历史读取、Input 落库、Pi 消费、渠道送达分别是不同事实。定时提醒没有可靠提供方锚点时不能制造消息 ID 或把平台计划时间当成已发送时间；明确等待/降级并保存原因。固定拒绝只有已经出现在渠道中且落在当前历史区间内才可能补入；迟到于当前事件的拒绝留给后续历史，pending/unknown 不伪装 sent。

### 话题兼容与渠道能力

主会话及每话题的历史任务、快照、边界和 Pi 状态必须使用同一独立会话范围。话题历史 unavailable 是发生读取错误或无法证明范围时的降级，不是允许复用主会话；缺失锚点时只处理隔离后的当前输入并暴露历史缺口。群话题继续按本员工 @/关键词规则过滤；私聊话题直接进对应 Inbox。原话题回复能力和订阅权限须单独验收，不能用主群发送成功替代。

当前实现采用迁移 21 的 `channel_thread_id`：binding、identity epoch、tenant、聊天类型、父 chat ID 与 thread ID 组成独立 Conversation 映射，Inbox 在同话题内串行。旧 Conversation 的 thread 为空，兼容原主会话；历史中已混入的旧话题内容不会自动推断拆迁。

飞书群话题历史使用 `GET /open-apis/im/v1/messages`，`container_id_type=thread`、`container_id=thread_id`，不带时间筛选；倒序分页先定位当前精确消息 ID 并核对其时间，再收集到上次本员工本话题的 Input 边界或配置上限。两个锚点不纳入历史，同毫秒消息按提供方顺序处理；所有话题条目（包括锚点）严格核对 chat_id/thread_id。主群补历史过滤话题消息。私聊话题不创建 history job，也不调用历史接口。

每页 50 条，最多 10 页；job.limit 为 1–100 条，正文预算 32768 字节，历史 worker 外层仍有 15 秒预算。页预算耗尽、锚点缺失、范围错误、乱序、游标循环、权限撤回或接口错误时丢弃该次快照，明确 unavailable；不保留部分未知范围内容，不回退主群。降级时仅当前事件进入自身 Input 并推进自身边界，主群和其他话题水位不变。条数上限正常截取仍显式记录 truncated。

飞书群聊和私聊均使用 SDK 入站事件的 `chat_id`、`thread_id` 和原消息 ID 确定话题回复目标。领取和授权的目标一致后，Hub 用同一机器人身份按原消息 ID 查询飞书。仅当查到唯一一条身份、会话和话题均匹配的原消息，且该消息未标为已撤回时，Hub 才复核绑定并调用原消息的回复接口，显式传入 `reply_in_thread=true`。读取失败、缺少目标或范围不符时，投递记为 `failed / not_dispatched`，主会话不会收到兜底消息。

飞书回复回执必须包含新消息 ID，并且其中的 `chat_id`、`thread_id` 必须与授权目标完全一致。Manager 对照原始 Inbox 独立复核。飞书返回成功但缺少落点证据、返回其他会话或话题时，投递记为 `unknown`，保留尝试回执，不自动重发。旧 Hub 仅上报消息 ID 的话题回执也按此处理。同次尝试后来提供完整证据时可确认 `sent`。创建时间用于历史定位，确认回复位置只需上述三个 ID。该规则适用于新处理的回执，历史已确认记录保留原状态。

### 顺序、幂等与重试

同员工同群范围串行冻结区间，不允许后一事件先占用错误水位。提供方原始时间用于区间范围，消息 ID 与渠道顺序用于同毫秒锚点；接收顺序不假装就是提供方发生顺序。晚到不回退水位，重复来源复用原 Input/快照。冻结快照不因重试加入新消息，历史条目按来源 ID 去重；事务回滚后 Input 与水位均不得半成功。

达到历史条数或预算上限明确记录 truncated/partial。接口失败、已知锚缺失、线程不支持或范围未知明确 unavailable，不制造完整空历史；若按契约降级只写当前事件，成功入 Input 仍是新边界，同时保留缺口事实，不能承诺日后自动补齐。只保存历史快照、Inbox accepted 或 Delivery pending 都不等于成功写入当前事件的 Input。

原生 `context_state=pending/committed/absent/unknown` 保留，用于判断该输入是否已经进入 Pi、是否能安全重试，**不再推进或阻挡群历史边界**。Input 已成功提交后即使仍在 false 缓存、后来撤回或模型失败，也不把渠道边界退回；重试只核对既有事实。已提交批次结果未知时先核对原生可恢复证据，不盲目重放；明确未消费才可归还同一批次。

### Engine 合批与文本

Manager 保存逐条 Input，不在写入前合成一个替代记录。Engine 主动按 Session seq 拉取，只有 false 时等待；遇第一条 true，则领取此前 false 加该 true，固定为一批且仅提交一条原生 user prompt，后续消息留下一批。领取和成员关联应原子化，忙时 steer 不越过队首 queue 或不同权限主体，不借当前 Turn 的权限执行他人输入。

私聊用户正文不加前缀；群用户按 `[说话人=显示名]` 和可选 `[被@人=名称1,名称2]`；平台内容统一 `[系统消息]`，无定时/权限子标签。@ 身份去重、前导移除、正文保留及未知 token 原样规则以主会话规范为准。自家平台固定文案须由可信来源关联识别，不能把所有机器人内容或用户自写标签冒充系统消息；第三方机器人消息保持真实说话人。原生已有 assistant 回复不再作为新平台 Input 重复灌入；群历史对已有上下文的去重按可信来源关联判断，不能仅因文本相同就丢弃别人的独立发言。


## Delivery

Manager 从主 chat 的可靠正式消息生成持久回复。异步任务逐 Turn 回报与有可信来源的渠道投递已接入，见[任务回报](session-input-and-task-report.md)；不把单轮结束等同业务任务完成。固定拒绝答复和模型答复分别去重。失败或中断必须明确告知未成功完成，取消必须明确告知已取消、未完成；此类终态不把此前的过程文字作为最终答复投递。

Hub claim 取得短租约，authorize 在外部发送前重新检查当前绑定、代次、租户和范围，并返回不可变目标；固定拒绝仅可回到同一可信入站来源，不暴露模型内容。正常答复需当前员工仍启用及权限仍有效。

状态 `pending → leased → sending → sent`；发送前租约丢失可重新领取，发送中租约过期转 unknown。只在明确未发送且可重试时 retry，最多 5 次；超时/结果不明不得盲重发。提供方稳定 UUID 去重不能被误称为永久 exactly-once。回执只证明提供方受理，不证明用户已读。权限撤销则取消投递，不能改收件人逃避失败。

### 企业微信联系人发现与管理员转交映射

企微联系人不是全量组织快照，不支持部门授权树。owner/admin 在当前启用且已由可信入站确认的绑定上调用 `/channels/wecom/contacts/search?q=`；后端经官方 HTTP CLI 的 `contact.users.search` 发现候选。搜索 ID 与 Web 账号、回调消息用户 ID 均不等同；提供方数据不能直接生成映射或授权。候选缓存 10 分钟、每绑定最多 1000 项，只作发码时的来源证明，不是员工使用权。

`POST /contacts/verifications` 使用 `{search_user_id,request_id(UUID)}` 创建管理员转交的六位码，24 小时有效；同请求标识重试复用结果、同来源已有有效码不能重复创建。管理员核对候选后私下交给本人，由本人向该机器人私聊发送。此流程是管理员转交证明，不是独立的提供方身份认证。GET `/{id}` 读取状态；POST `/{id}/cancel` 只取消尚未完成的码。码仅在管理员 pending 响应中明文返回，数据库保存带用途/请求 AAD 的密文和员工范围 HMAC；消费/取消即清密文，过期明文不返回，后续发码有界清理过期密文。历史摘要保留防止旧码复用。

可信入站先校验 provider、绑定、租户作用域、代际，再在同一事务、普通 Inbox 插入前处理控制码。只有适配器明确标记 `control_eligible` 的无引用、无混合媒体私聊纯文本，且仅含一个可识别六位候选，才消费为控制消息。新码有效 24 小时；已用、作废或自然过期的旧码，从首次失效时刻起拦截 72 小时。跨过该窗口的新消息按普通消息权限处理，已消费回调仍按 provider event/message 双去重。群聊、话题、引用/混合消息不建立映射。控制事件不把识别到的码写入 Inbox/Input 或模型。

绑定成功和当前来源识别到的旧码会分别返回固定私聊提示（成功、已使用、已过期或已作废），不回显验证码或联系人信息。Manager 持久化后才返回状态；Event Hub 仅用该入站回调的原连接发送，不创建普通出站队列，不在换连接或重复回调时重试。旧来源消息不跨代际回执或绑定。新码分配器只有在旧码窗口结束后才可重用同一数字；联系人的已验证映射不随验证码失效而删除。

映射按 binding + identity epoch + credential generation 双向唯一。迁移 76 在同一机器人重新确认新连接代次时，沿用已核验的搜索 ID、回调 ID、验证凭据和现存姓名，并更新已配置确认人的代次。旧验证码、已发起的人工确认和在途投递仍按原代次校验。升级时在同一绑定与身份 epoch 内回填双向无冲突的历史映射，已被清理的姓名可在下次搜索时补齐。配置变化或撤权后的迟到搜索/发码不能发布；绑定行锁和管理员当前角色在事务内复核。每绑定最近 1 小时最多新签发 200 个验证码，重试同一请求不计为新签发；活跃挑战期间每 sender 每小时最多 10 次、整个绑定 100 次六位码尝试。映射成功本身不授予员工使用权，前端明确将已映射 callback ID 加入允许/拒绝草稿，仍需保存原渠道配置。三个渠道的统一身份选择不属于本轮。

迁移 31 只新增候选、挑战、映射、控制去重与限流表，不回填推测身份。可回退删除这批新增表，但将丢失本轮映射和挑战，因此应先备份。验收只使用本地 PostgreSQL 和受控 HTTP/组件响应，未创建真实应用、未搜索真实联系人、未发送外部消息。
