# 后台任务找人确认

员工管理员在「员工详情 → 设定与模型 → 人工确认规则」选择 Web 工作区成员、飞书、钉钉或企业微信联系人，配置负责范围，也可指定一名默认确认人。飞书和钉钉使用员工当前绑定的通讯录，企微使用绑定验证后的回调身份。遇到没有匹配规则或无法确定匹配人选的新问题时，AI 员工使用仍有员工私聊使用权的默认确认人。默认确认人可以同时填写负责范围。每次保存使用当前配置版本。工作台顶部「待人工确认」统计当前工作区全部未结束的确认单，点击后打开同口径的只读清单；清单正文按下文权限展示。

## 执行与回执

- 执行 Agent 调用 `list_human_confirmation_scopes`，按负责范围选择候选。工具返回 `candidateId`、`questionScope` 和配置版本，默认确认人单列。没有可明确匹配的候选时使用有效默认人；默认人为空时报告缺少确认人。Agent 在 `ask_human` 一并提交候选 ID、版本、背景、目标、已知事实、小题及必答项、完成标准、拟执行动作、影响范围和未确认时的处理方式。每份新请求必须二选一：审批用 `decisionRequired=true` 和 `questions=[]`，用 `goal` 写给确认人看的简短审批问题（标题），`background` 单独写背景，并说明拟执行动作和影响范围；同意／拒绝不是一道题。提交表单（收集信息）用 `decisionRequired=false` 并至少提供一道实际问题，不能替代明确审批。模式冲突可在同一轮修正重试，不创建确认单、不挂起任务。历史确认单的答复方式不变。Manager 根据候选 ID 解析、复验收件人并投递。
- Pi 公开扩展钩子在整批包含 `ask_human` 时阻断同批其他工具。Manager 在登记请求的事务里关闭 Session 的普通输入领取入口。Engine 核对并清空原生排队消息，将明确未被消费的引导退回平台队列，再提交门禁回执。工具收到回执后返回 Pi 原生的 `terminate: true`。
- Engine 核对 Pi 已 settle、成功工具结果与请求相关联，退出 Pi 并核对 Runner 已停稳和远程调用已结算。它在旧 Turn 的终态事务里发布待答复状态。无法证明停稳的请求显示待核对。
- Web、飞书、钉钉和企微的员工主私聊通过 MCP 提供 `list_pending_human_confirmations` 和 `submit_human_confirmation`。待确认工具支持 `page` 和 `pageSize`（默认第 1 页、每页 20 条，最多 50 条），可用 `requestId` 按完整 ID 或短码精确查询。每页都返回当前真实消息、可信引用和已送达的澄清焦点，`referencedRequests` 提供当前消息和可信上下文在本页之外提到的可答确认单。主私聊 Agent 用这些信息判断答复归属与语义。已定位但语义或答案缺失时可用 `needs_more` 登记追问。Manager 校验发出的追问后提供可信焦点。
- 已指派的人失去普通使用权后，仍可在 Web 工作区表单答复，或在外部渠道使用确认专用轮次。专用轮次只挂确认工具。Web 表单可提交结构化逐项答案，也支持历史确认单的文本答复。
- 确认人须保持活跃的工作区身份或当前渠道身份，并且仍在原确认规则中。受限渠道答复记录原始入站回执，待确认正文在出站前重新核对问题有效性、确认人和连接身份。原任务继续时复验确认人身份及原输入授权。
- 需要批准的单收到完整信息但缺明确批准时，Manager 返回 `needs_more` 和 `explicit_decision_required`，Agent 登记并发出追问。私聊提交的 `operationId` 在当前真实用户 Input 内唯一，同标识、同内容可重试。提交超时后，`get_human_confirmation_receipt` 用原确认单 ID 和原标识查询。回执区分 `needs_more`、`not_recorded`、已记录的决定和 `unknown`；有续跑时还返回 Input 的实际状态。Web 表单的答复冲突返回 409。
- 同意或有效信息在同一事务保存答复、操作回执和唯一的续跑 Input。该 Input 优先于普通排队输入，在原 Session 加载同一 Pi 原生历史。Engine 核对原 Session、输入、停稳边界和冻结的问题及答复，把拟执行动作、影响范围、完成标准与问题版本交给执行 Agent。发现范围变更时保留门禁并阻止自动续跑。拒绝取消已等候的普通输入并关闭等待。停止与归档沿 Session 的现有事务裁决。
- Session 事件展示通用状态；找人确认工具的参数和结果正文不进入公开工具事件。确认单内容与原生历史留在各自受控的读取入口。现有 Pi 原生「是／否」继续按原发起人、原会话内确认的契约运行。

三家外部渠道支持主动私聊通知和主动查询。飞书支持经核验的引用回复；钉钉、企微不从回执猜测引用。见 [渠道确认与上下文](human-dm-replies.md)。

## 任务导航的确认记录

当前工作区的活跃成员可在任务导航查看确认状态摘要（编号、版本、状态和时间）。只有通过 Web 认证的指定确认人，或按 Manager 原有权限可读取来源 Session 的人，能看到完整确认内容。只读摘要不会下发问题、背景、处理人、发起员工、答复或补问；按编号查询也适用同一规则。默认显示待处理，可切换到已处理或全部。详情读取权限不授予答复权，外部渠道身份不推断成 Web 身份。问题和背景中的 Markdown 代码块保留原文。顶部数量通过独立汇总查询读取，和清单的待处理数共用 preparing、pending、blocked 的口径。历史查询与答复分别使用独立入口。

## 内部 MCP 接口

`/mcp/human-confirmations/chat` 提供查询与答复工具，`/mcp/human-confirmations/task` 提供候选人查询。两条路由共用 Backend listener，供内部 Engine 访问，公网代理按内部 MCP 路径排除。认证拒绝 Cookie 和 Origin，要求专用 Bearer 与 `X-Kiko-Human-Input`。凭据绑定角色、Session、Engine、分配、代次和输入，Manager 每次业务调用在事务内重验当前输入。工具契约见 [tools.json](../contracts/humanconfirmation/tools.json)。

凭据随输入更新，Engine 在配置变化时重新启动 Pi 子进程并加载已有原生历史。旧 Engine 仍可使用原内部 HTTP 工具入口。新 Engine 连接旧 Backend 时，沿用原工具注册。新版本的 `ask_human` 继续使用原内部 HTTP 入口登记请求和读取停稳回执。

## 验证

迁移 56 创建人工确认规则和请求，迁移 61 将选择和权限检查扩展到四个来源，迁移 62 加入受限答复的入站和投递记录，迁移 67–70 支持主动通知、整改、补问、管理员审计和历史答复数据。迁移 83 增加 Agent 澄清焦点和确认专用输入准入。迁移 85 增加操作回执和续跑快照。发布时由 Event Hub 先应用迁移，再启用新版 Backend 和 Engine。接口定义见 [OpenAPI](../contracts/modules/manager/human-requests.yaml)。Web 确认的 PostgreSQL 与 Pi 运行时验收见 [运行时用例](../internal/platform/repository/manager_human_requests_e2e_test.go)。

## 退回修改与要求补充

- `revise` 必须附具体修改意见。请求记为 `revised`，不记为 `approved`。与原停稳、原任务身份和当前权限复验共用同一受理事务，只为原 Session 追加一次定向续跑 Input。Engine 沿原 Session 开受限整改轮次，只开放确认职责查询和 `ask_human`，继续隔离内置工具、Skill、Runner 和事项工具。本轮拟定修改稿并发起需要明确批准的新确认单。Manager 在同一事务登记新单并转移旧门禁，保留原始授权输入；受理前的失败保留旧门禁。新单有效批准后，原任务恢复执行。
- `needs_more` 必须附补充要求。追加到独立记录，原请求仍为 `pending`，不写最终答复、不创建续跑 Input。同一问题版本的相同正文重放只返回收据。收据 `state=needs_more` 表示补充要求已记录，并非确认请求的状态。此记录本身不触发模型或承诺向发起人发送通知。
- `reject` 仍是明确拒绝，沿用原停止分支。附上原因时，答复与待通知记录一并提交。后台仅向仍有权限的原任务发起人，在已核实的原私聊回告一次。Web 写入私聊消息，外部渠道使用现有主动投递；不向群聊、确认人或无法核实的对象转发，不触发新一轮模型。回告会隐藏已识别的敏感信息并限制预览长度，原说明仍随确认记录保存。不能用重放将一次修改决定覆盖成同意。退回修改不等于事项验收回退；事项需要按独立的交接与验收规则处理。
