# Platform 身份、工作区与邀请

本期默认支持无需 SMTP 的邮箱+密码注册/登录；可配置强制邮箱验证码注册，并保留验证码登录和重置密码、工作区与成员、邮箱定向邀请及无需SMTP的通用链接邀请。Google OAuth、员工及运行任务不在本期范围。机器可读契约为 `../contracts/openapi.yaml`。

## 分层与持久化

`platform/controller` 解析 HTTP、Cookie、CSRF 和错误；`platform/service` 负责验证码、身份与成员政策；`platform/repository` 通过 PostgreSQL 保存账号、挑战、会话、限流、工作区、成员、邀请；`platform/integration` 为带 TLS 的 SMTP 客户端。`app` 负责配置与装配、监听和退出，不参与业务转发。不同 Backend 副本共享 PostgreSQL，不依赖进程内验证码或会话缓存。

全局迁移 `000001_platform_identity.sql` 定义表，追加 `000002_unverified_account_default.sql` 将新账号默认验证状态改为 false，并追加000003通用邀请与个人工作区结构，均由 Event Hub 执行；旧迁移未改写、既有已验证账号保持原值。Backend 不执行 SQL 迁移、不检查 schema 版本、不等待迁移；未建表时请求返回可重试服务错误，迁移后后续请求恢复。

| 表 | 用途 |
| --- | --- |
| platform_accounts | 邮箱、明确验证状态、显示名、可选 bcrypt 密码；邮箱规范化后唯一 |
| platform_email_challenges | 用途隔离的验证码 HMAC、5 分钟有效期、错误次数、消费时刻 |
| platform_sessions | 随机会话 token 的 SHA-256、账号、30 天到期时间 |
| platform_rate_limits | 跨实例发送/登录限流计数与窗口 |
| platform_workspaces | 工作区名称、描述、版本；personal_owner_id 唯一标识账号默认个人空间 |
| platform_members | 工作区和账号组合唯一、角色、启停、版本 |
| platform_invitations | kind=email/link、定向邮箱或通用bearer、邀请者、角色、token哈希、状态；有效期1–180天，email默认1天/link默认7天 |
| platform_invitation_redemptions | 每邀请/账号兑换唯一，保证接受幂等 |
| platform_removed_members | 工作区/账号移除时刻，阻断旧邀请恢复权限，允许管理员之后新建邀请重新加入 |
| platform_invitation_deliveries | 加密邮件payload、发送状态、租约与领取代次；异步可恢复投递 |

## 平台管理员

状态：2026-11-18，已随 AI 员工市场首版实现。账号字段、一次性初始化和授权接口均已接入。

### 角色与操作

首版仅增加账号级 `is_platform_admin` 标记，不引入角色配置、权限点编辑器或部署账号白名单。平台管理员可以管理官方 AI 员工模板，并向其他已注册账号授予或撤销平台管理员资格。各平台管理员权限相同，首位管理员没有额外的永久特权。

| 身份 | 模板与账号管理权限 |
| --- | --- |
| 平台管理员 | 新建、编辑、查看草稿、发布、下架官方模板；查看平台用户列表并管理平台管理员资格 |
| 工作区 owner/admin | 管理本工作区模板和员工；这个角色本身不授予官方模板或平台管理员管理权 |
| 普通登录用户 | 浏览官方已发布模板；工作区模板及员工仍按工作区权限访问 |

平台角色与工作区角色分别判断；同一账号可以同时拥有二者。平台管理员角色不自动加入其他工作区，也不自动授予读取其业务资源、账号凭据或私聊的权限。官方模板若引用某工作区资源，仍需具备来源工作区现有资源管理权限。

「设置」的第三个标签页「平台管理」仅向平台管理员显示。API 仍独立校验平台管理员权限。管理员可在其中的「用户管理」搜索已注册用户，并选择「设为平台管理员」或「取消平台管理员」。操作成功后更新角色状态；目标用户下一次请求即可获得或失去相应权限，不要求重新登录。工作区成员管理仍使用原 owner/admin/member 角色，不把其中的「管理员」显示成平台管理员。

### 首位登录用户初始化

1. 平台尚未初始化管理员时，第一个成功建立登录会话的用户自动成为平台管理员；密码登录、验证码登录，以及注册成功后自动建立会话都参与同一个初始化过程。登录失败、发送验证码和读取 `/me` 不参与。
2. 「第一个」以数据库初始化事务成功提交为准；在同一事务内签发会话、设置账号管理员标记并记录初始化完成。并发请求通过一个数据库单例行锁裁决，只有一个账号获得初始权限。
3. 初始化只完成一次；重启、重新部署、用户退出和会话过期不会重置。不能以“当前管理员数量为零”作为再次给任意登录用户授予权限的条件。
4. 管理员可以增加其他管理员，也可以撤销管理员资格；至少保留一名平台管理员，撤销最后一名返回 `409 last_platform_admin`。首位管理员在另有管理员后可以被撤销，规则与其他管理员相同。
5. 注册仍与账号、个人工作区和会话创建共同提交；其中任一步失败，管理员初始化一起回滚。若成功回执丢失，角色已持久化，重新登录或读取当前用户即可恢复展示。

已有账号的部署按「本功能上线后，首次成功建立新登录会话」完成一次初始化；不把最早注册的账号推定为历史首位登录者，也不由现有 Cookie 的普通页面请求触发授予。初始化完成后，既有账号和新注册账号均由现有平台管理员显式授权。

### 拟新增的 API

继续使用现有 `/api/v1`、Cookie 登录和写操作 CSRF 校验，不增加内部管理入口。

| 方法与路径 | operationId | 请求、响应和权限 |
| --- | --- | --- |
| `GET /api/v1/me` | 沿用现有操作 | user 增加只读 `is_platform_admin`；登录和注册成功响应同步返回该字段 |
| `GET /api/v1/accounts` | `listPlatformAccounts` | 仅平台管理员；支持 q、is_platform_admin、page、page_size；返回账号 id、name、email、is_platform_admin、platform_admin_version、created_at |
| `PATCH /api/v1/accounts/{account_id}/platform-admin` | `updateAccountPlatformAdmin` | 仅平台管理员；请求 `version,is_platform_admin`；200 返回 account_id、is_platform_admin、version。version 对应目标账号的 platform_admin_version |

列表默认每页 20 条，page_size 范围 1–100；按 created_at DESC/id DESC 排序，响应为 `{items,total,page,page_size}`。q 长度不超过 100，按名称或邮箱大小写不敏感子串匹配，转义 LIKE 通配符。普通用户不能使用该接口搜索其他账号；返回不含密码摘要、会话或凭据。

授权修改沿用目标状态与版本检查，不要求 Idempotency-Key。持锁后先核验操作者当前权限与目标账号存在性；目标状态已经相同则返回当前值，不重复增版；需要变更时 version 必须匹配，否则返回 `409 platform_admin_version_conflict`。相同请求重试不能覆盖其间发生的相反操作。未登录返回 401，缺少平台管理权返回 403，管理员指定不存在的账号返回 404，格式错误返回 400。

客户端不能通过注册正文、普通账号编辑、工作区成员角色或邀请参数写入 `is_platform_admin`。后台每次读取账号的当前标记，不把授权固化在 Cookie 或长期内存缓存中；Cookie 仍仅代表登录会话。授权变更按现有结构化日志记录操作者、目标账号与变更前后状态，不记录凭据。

### 拟新增的数据库字段与初始化记录

| 表 | 字段与约束 | 用途 |
| --- | --- | --- |
| `platform_accounts` | `is_platform_admin boolean NOT NULL DEFAULT false`；`platform_admin_version bigint NOT NULL DEFAULT 1 CHECK (> 0)` | 账号级管理员资格及并发版本；实际角色变更递增版本，初始化授予也按一次变更处理 |
| `platform_admin_state`（新增） | `singleton boolean PRIMARY KEY CHECK (singleton=true)`；`initialized_by UUID` 可空 FK → platform_accounts；`initialized_at timestamptz` 可空；后两项必须同时为空或非空 | 迁移插入唯一行；未初始化时两项为空，成功初始化后只写一次。保留初始化事实，不因该账号后来被撤权而清空 |

不新增通用角色表、角色权限关联表或管理员账号配置项。账号和初始化记录不提供删除入口；初始化账号外键使用 RESTRICT，管理员资格被撤销不影响历史初始化记录。

### 关键事务流程

登录仍先验证当前认证方式要求的凭据，密码哈希和验证码有效性沿用既有事务内复核。需要初始化时，在账号、验证码挑战或工作区锁之前取得 `platform_admin_state` 的 FOR UPDATE 锁，重新判断 initialized_at；若为空，将本次成功登录账号设为管理员并写初始化记录，与会话一起提交。初始化已完成的正常登录不再申请该独占锁；不能先锁账号再回头申请初始化锁。注册与两种登录路径必须共用这项规则，不能仅修改密码登录入口。

授权变更取得同一单例行 FOR UPDATE 锁，再按账号 ID 顺序锁操作者与目标账号，复核当前管理员资格、预期版本和剩余管理员数量后写入。撤销最后一位管理员的判断与更新在锁内完成，因此两个管理员同时互相撤销不会把人数降到零。

官方模板普通读取直接检查当前账号角色，不取得初始化单例行锁。写入在事务内对操作者账号取 FOR SHARE 锁并核验 is_platform_admin，随后按工作区 → 模板顺序取得业务锁；角色变更会锁同一账号，因此撤权与管理写入按事务提交先后裁决。事务外工作完成后，最终写入重新鉴权；已提交动作保持原结果。工作区模板继续使用工作区角色。单例行仅协调首位管理员初始化和管理员资格变更，不作为所有官方模板请求的全局锁。

认证事务返回更新后的账号数据，避免现有登录用例预先读出的 Account 把新管理员错误显示为普通用户。所有写入都成功才返回登录成功；成功后单独读取工作区列表失败不能回滚身份结果。

### 迁移与待验收

确认后新增全局迁移，给既有账号补默认 false 和版本 1，并插入未初始化单例行；由 Event Hub 执行，不改旧迁移或添加 Backend 启动闸门。全部认证实例具备相同初始化与角色校验逻辑后才启用本功能，避免旧实例签发会话却跳过首位用户初始化。

后续验收覆盖：空库两账号并发登录仅一位初始管理员；注册自动登录、密码与验证码登录行为一致；认证或提交失败不占用初始化；重启后不重复初始化；已有 Cookie 读取不触发授予；授权和撤权对现有会话的下一次请求生效；普通用户不能自提权；最后一位管理员及并发互相撤权保护；官方模板与工作区模板各用自己的权限边界。以上为设计要求，本次未执行代码或数据库测试。

本轮简化复核保留初始化单例和角色版本：前者记录“已完成过初始化”，后者防止并发授权覆盖。两者都服务明确的业务约束；不为减少一张小表而改成每次检查管理员人数并重新初始化，也不增加通用角色/权限模型。

## 本地入门与邮箱验证策略

- 管理员可在「设置 → 平台管理 → 邮件与注册」启用邮箱验证；新实例默认关闭。未保存数据库设置时仍沿用旧配置文件或环境变量。`GET /api/v1/auth/options` 返回 `password_registration_enabled`、`email_code_enabled`、`registration_verification_required` 三个布尔值，不暴露邮件服务配置或秘密。
- `POST /auth/registrations` 使用 `method: password` 时必须提供密码，不携带 code/challenge_id；新账号 `email_verified=false`。可密码登录、建立自己的工作区，不证明邮箱归属，**不能接受邮箱定向邀请**。本期没有自动关联外部企业身份或按邮箱合并已有账号。
- 启用邮件和强制邮箱验证后，服务端拒绝密码注册，只接受验证码注册；不能靠修改前端开关绕过。保存时拒绝「邮件关闭但强制邮箱验证」组合，旧配置加载仍按原规则校验。
- `method: code` 保留原流程，省略 method 的旧客户端仍按验证码注册处理。已有邮箱唯一约束，无论是否验证都不会被重复注册覆盖。
- 为避免攻击者预注册他人邮箱，未验证账号不能直接验证码登录。真实邮箱主人需使用 **验证码重置密码**：证明邮箱、替换旧密码、设置 verified=true、撤销全部旧会话同事务完成。之后用新密码或验证码登录。旧抢注密码和旧会话不能进入后来接受的工作区；并发旧密码登录同样被锁和 hash 复核阻止。
- 无 SMTP 的部署不能完成定向邀请验证或验证码找回，这是清楚的能力限制，不通过跳过验证解决；管理员可使用无需SMTP的通用链接邀请加入工作区；仅要使用定向邮箱邀请/找回密码时才需配置邮件发送。

## 邮箱与会话

- OTP 为安全随机 6 位数字。每邮箱每用途 60 秒可重发；重发废止旧码。每个挑战最多 5 次错误，失败次数持久化提交，不随失败业务事务回滚。每 IP 发送每小时 30 次、每邮箱每小时 10 次；登录每 IP+邮箱每 15 分钟 20 次。默认不信任 `X-Forwarded-For`。反代部署设置 `KIKO_TRUSTED_PROXY_CIDRS`，仅直接来源在可信网段内才从右向左解析最多 20 段代理链，选最近非可信来源；配置必须只包含自有代理网段，不能将任意客户端设为可信。未配置时同出口可能共用限额。
- 发送失败返回 503，挑战失效；SMTP 外部 I/O 不在数据库事务内。没有生产调试码、默认密码、明文验证码日志。所有实例须使用相同 `KIKO_AUTH_SECRET`，更换该密钥会令旧验证码失效。
- 注册原子消费验证码（密码注册不需）、创建账号、个人工作区与会话。邀请 token 由页面保留，注册/登录后单独接受邀请。登录/注册只返回 user，工作区列表独立获取，刷新失败不覆盖写成功。
- 浏览器使用 HttpOnly、SameSite=Strict Cookie，HTTPS 使用 Secure。写操作须 `X-CSRF-Protection: 1`，带 Origin 时必须与配置完全相同；不启用跨域 CORS。不接受 Bearer/Cookie 混用或服务凭据。登出撤销当前会话；重置密码在账号锁事务内更新密码并撤销全部会话。密码登录签发时再次锁账号核验密码版本，防止并发重置后旧凭据获得新会话。
- 密码可选，提供时长度为 10 至 72 字节，以 bcrypt 保存。OTP 注册后可通过重置流程设置密码。

## 邀请与权限

创建邀请不创建 active 成员；link只返回可复制链接，email同时持久化异步邮件投递。链接 `/?invitation_token=...`。定向 email 邀请接受时检查当前登录邮箱已验证且等于受邀邮箱；所有邀请均检查邀请仍有效、邀请者现在仍具备相应管理权限；已有成员不会借邀请自动升级，停用成员不能借邀请恢复。重复接受成功邀请返回既有成员角色。

Owner 可邀请 admin/member，admin 只能邀请 member；Owner 不可被普通成员编辑/删除，用户不能修改自己的角色或状态。成员/工作区修改带 version；同旧版本并发只允许一个成功。所有工作区操作以工作区行锁保证授权和更新一致，首版读操作也取锁，是可优化点，不表示可无限并发。

失效邀请查询返回 HTTP 200 与明确状态，前端呈现无效链接页，不是 404；已知失效可显示邀请人邮箱，未知/伪造 token 不暴露工作区或邮箱。匿名查询只给收件邮箱掩码。接受无效邀请返回 410。保留邀请历史用于失效提示；目前无自动删除邀请或账号数据。

## 运行配置

部署配置见[启动配置](configuration.md)。以下邮件环境变量仅适用于尚未保存数据库配置、也没有旧配置文件的兼容部署；新实例通过平台管理配置邮件。

```
DATABASE_URL=postgres://...                  # 同 Event Hub 业务库
KIKO_PUBLIC_ORIGIN=https://your.example     # 开发仅允许 http://localhost 或 127.0.0.1
KIKO_REGISTRATION_VERIFICATION_REQUIRED=false # 开源本地默认；公网建议 true
KIKO_AUTH_SECRET=<至少32字节随机值>           # 不提交仓库
KIKO_HTTP_ADDRESS=127.0.0.1:8080
KIKO_TRUSTED_PROXY_CIDRS=127.0.0.1/32      # 仅同机反代时示例，按实际代理网段设置
KIKO_WEB_DIR=/absolute/path/web/dist        # 可选，只传构建产物目录
KIKO_MAIL_ENABLED=true # 仅无配置文件兼容模式
SMTP_ADDRESS=smtp.example:465
SMTP_HOST=smtp.example
SMTP_IMPLICIT_TLS=true                     # false 时强制 STARTTLS
SMTP_USERNAME=...
SMTP_PASSWORD=...
SMTP_FROM=sender@example
```

邮件禁用时服务器可以启动，密码注册可用，所有验证码接口返回403 email_code_disabled。邮件开启则配置必须完整否则启动失败。配置文件推荐入口及优先级见[启动配置](configuration.md)。网络与查询请求有时间界限；关闭时最多等待 15 秒收尾。`/healthz`、`/readyz` 表达进程 HTTP 服务已运行，不保证数据库业务表已迁移。

## 验证

`BACKEND_TEST_DATABASE_URL` 指向仅供测试的 PostgreSQL 实例，repository 测试创建随机 schema 并清理，覆盖真实唯一约束、并发验证码消费、重置撤销会话、邀请接受与 CAS。HTTP 测试用 fake 邮件 sink，不向第三方发信。`KIKO_RUN_BROWSER_TEST=1` 只启用 test 文件的临时本机浏览器夹具，不编译进生产程序。

仍需生产 SMTP 凭证及实际送达验证；本期不把 mock 邮件成功称为真实邮件到达。过期挑战、会话及限流行目前按时间逻辑失效但不自动清理，后续应由明确的维护任务按保留策略清理，不能删除有效绑定或邀请提示所需记录。

## 可复用邀请链接与个人工作区

新账号通过密码或验证码注册时，账号、默认个人工作区（owner）、会话在同一数据库事务内创建，失败全部回滚。个人工作区的 personal_owner_id 唯一，重复注册不会覆盖账号或多建空间。已有账号不自动回填。邀请注册也先创建个人工作区，再由前端独立接受邀请；过期或撤销不会回滚注册，页面应保留账号并说明加入失败。

POST invitations 可选 kind=email|link，省略仍按原 email 行为。link 默认 member，禁止 admin 和指定 email；有效期 expires_in_days 1–180，link 默认7天，email默认1天。

link 是持有即授权的高熵 bearer 链接，可供多个已登录账号使用，不依赖邮件服务、不把未验证邮箱当可信身份。每 invitation/account 兑换唯一并幂等，不把已有成员升权。email 定向邀请仍要求邮箱已验证且匹配。每次加入均检查邀请人当前权限、到期与撤销；disabled 成员不会通过邀请复活。移除记录保留时间戳，创建于移除之前的旧链接不能再加回该账号；管理员移除后新创建的邀请可重新加入。通用链接无法证明同一自然人的身份，持有人用另一个新账号加入是 bearer 模型的固有限制，应谨慎分发、限定时效，泄漏后撤销。

原始 token 仅创建响应返回一次，数据库仅存哈希；列表只有元数据，无法恢复原链接。创建请求不具备通用幂等键，响应丢失后重新创建会得到另一个链接，客户端不应自动重试创建。接受操作则按账号幂等。所有HTTP响应设置 Referrer-Policy:no-referrer，日志只记录路由模板不记录token路径；部署的代理也必须避免记录邀请URL/query。

迁移000003追加邀请类型、兑换记录、移除标记、个人空间唯一归属，未修改旧迁移。Backend仍不执行迁移。

邮箱验证码能力关闭时，后端拒绝创建新的 email 定向邀请（403 email_code_disabled），与 auth/options 的 email_code_enabled 一致；历史邀请仍可查看与撤销，link 不受影响。

## 多邮箱共用定向邀请链接

迁移 75 支持在创建邀请时提交 `emails` 数组，旧客户端仍可使用 `email`。服务端规范化并去重邮箱，在同一事务创建所有收件人记录和加密邮件。每个收件人沿用独立的邀请 ID、投递状态、兑换记录及发送限流。多人邮件共用一个链接，接受时在工作区锁内按当前账号的已验证邮箱定位记录。匿名链接检查不返回多人名单。管理员列表每个邮箱一行，`shared: true` 表示共用链接；重发仅作用于该行。撤销共用链接使该组所有待接受记录失效，已加入账号保留原角色。旧邀请沿用原凭据、角色与投递记录。发布时先应用迁移 75，再部署新 Backend。

## 定向邀请邮件投递

开启邮件后，新 email 邀请创建与投递 outbox 同事务持久化，HTTP201表示邀请已创建，不表示邮件已到达；link 不发邮件。创建后异步发送，响应与列表提供 delivery_status：pending、sending、sent、failed、unknown、cancelled；link及无投递记录的旧邀请为not_applicable。sent仅SMTP服务器已接受，不保证最终邮箱送达。发送失败不会把成功创建改成创建失败，客户端不得因此重建邀请。

Backend 投递循环在处理邮件时读取运行配置，关闭邮件时不领取新的投递；多实例共享同一数据库，持久化领取与租约避免并发重复发送，SMTP I/O不持数据库事务。发送前重新检查邀请有效性、撤销及邀请人的当前权限，失效取消发送。最后校验后与真实SMTP发送仍存在不可消除的并发窗口，撤销在接受邀请时仍会再次严格校验。实例宕机或发送结果不确定进入unknown，不自动重发；已知failed也需显式重试。固定Message-ID只是辅助，不是SMTP幂等保证。

重试接口复用原邀请与原链接；sent/pending/sending不重复排队。unknown重试必须传acknowledge_possible_duplicate=true，表示管理员已知同一邮件可能重复收到。重试重新校验权限、期限和撤销，并受持久化限流保护。

邮件链接来自可信PublicURL配置而非请求Host。outbox正文（含收件人和链接）AES-GCM加密，用AUTH_SECRET经专用固定域派生密钥，AAD绑定邀请ID；不存明文token、不写日志。多实例AUTH_SECRET必须一致且无默认值。轮换AUTH_SECRET会使既有待发密文无法解密，明确失败且不发送；需在受控操作下恢复原密钥处理待发记录，或撤销旧邀请并重建，不可降级读取明文。历史已经sent状态不因密钥变更重发。

本轮仅fake SMTP测试，不向真实收件人发信；不宣称真实邮件已送达。
