# Employee trigger rules

The original rule editor is backed by `GET/PATCH /api/v1/workspaces/{workspace_id}/agents/{agent_id}/trigger-rules` and `POST .../trigger-rules/test`. All require workspace owner/admin and the normal authenticated session/CSRF protections.

Rules retain stable ID, name, description, type, pattern, enabled and channels (`web`, `feishu`). New IDs are generated by the server; send an empty ID when adding. The list replacement uses the employee usage version CAS. It changes only keyword/regex rules; mention, history and access policy are preserved. A stale version fails rather than merging or replaying automatically. Existing anonymous patterns are read using deterministic legacy IDs and pattern-derived display names; first save persists the metadata. Both channels share this employee-level source, never independently writable channel policy.

Metadata is stored alongside existing usage JSON. Migration 52 filters disabled patterns from SQL projections; omitted enabled remains true for legacy data. No second writable trigger table is introduced. Update atomically refreshes channel projection/rules revision. Web admission reads the same projection.

Preview accepts the current **unsaved** rule list, channel and sample text. It does not save the rules, write Inbox/Input/messages, or run the employee. It uses `shared/trigger`, the same matcher as EventHub and Manager. Keyword matching splits English/Chinese commas and ignores case, per the explicit user decision. Regex is Go RE2, not JavaScript; unsupported `/pattern/flags` and unsupported constructs return `invalid_trigger_pattern`. The four UI regex templates remain ordinary preset text, not separate backend entities.

Runtime limits: 32 keyword rules, 16 regex rules; pattern 256 code points and max 1024 UTF-8 bytes; message max 65536 bytes. Disable and channel filters apply to preview as in live projection. Tests cover metadata, CAS, cross-channel projection, disabled rules, authorization and preview not changing the version or persisted pattern. Full phone/IM end-to-end validation is separate.
