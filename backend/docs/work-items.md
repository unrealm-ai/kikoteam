# 事项交接与原任务验收

从对话或触发器创建的普通任务可以首次把工作交给同工作区的员工。源任务保留原 Task、Session、归属和 Pi 历史。接手和每轮整改各自创建 Task 和 Session，归同一事项 TaskSpace。交接载荷包含结构化摘要及本次显式选择的文件版本。同一事项只有一个当前接手环节。

## 工具

| 当前执行 | Manager MCP | Pi 本地工具 |
| --- | --- | --- |
| 普通任务 | `work_item_list_handoff_employees` | `work_item_handoff`，提交目标员工和标题、目标、验收标准、摘要 |
| 接手任务 | `work_item_list_handoff_employees`、`work_item_get_current`、`work_item_read_file` | `work_item_handoff` 继续转交，`work_item_submit_result` 提交结果和证据。写入核对当前环节和事项版本 |
| 原任务验收 | `work_item_list_handoff_employees`、`work_item_get_current`、`work_item_read_file`、`work_item_accept` | `work_item_handoff` 退回整改。写入核对提交 ID 和事项版本 |

MCP 契约见 [tools.json](../contracts/workitems/tools.json)。MCP 和本地工具使用不同用途的短范围凭据，绑定活动 Session、Engine 分配及 Input。Manager 从当前可信 Input 定位接手环节或验收提交，不要求模型复述这些 ID；验收经人工确认续跑时沿用原授权 Input 的提交。接手、提交、退回和验收仍将 `work_item_get_current` 返回的 `version` 作为 `expected_version` 提交，由 Manager 校验。Pi 统一拦截同一批包含交接、提交或找人确认的其他调用，结束工具使用原生 `terminate` 等待执行停稳。

管理员在员工的「能力包」页配置接手范围，可以允许全部来源、仅允许所选来源或排除所选来源。能力包可以单独指定来源名单或继承员工接手范围。来源取本次交接的直接发送员工。迁移 118 将旧能力包和历史任务快照转换成显式规则：原本可用的设为继承，原本不可用的设为空白名单。不清空历史交接，不扩大现有权限。新包默认继承。员工发现、派发、输入领取和运行时能力检查均使用可信的事项分配记录。

交接或提交时，`file_paths` 选择当前任务项目内的普通文件，`file_ids` 选择本环节已经获准读取的版本。每次最多选择 32 项，单个文件上限 32 MiB。Manager 固定文件内容并保存 SHA-256、大小和文件名。只有已提交的交接会授权下一环节。接手人与验收人通过 `work_item_get_current.files` 取得句柄，使用 `work_item_read_file` 分块读取。继续转交、退回整改或再次提交时须重新选择需要携带的文件。读取会复核沿途的授权、来源任务和员工状态。

## 状态与恢复

1. Manager 原子保存意图及来源 Session 的排队门禁。Engine 清理原生排队消息，核对 Pi 停稳、Runner 活动与远程调用，再将停稳和源 Turn 终态一起落盘。未知结果保留为待核对。
2. Manager 重读持久证据，在短事务内提交环节及下一 Task、Session、首条 Input。多副本通过行锁共同进行派发。任务开跑、排队、待核对与验收使用已提交的状态事实。
3. 最终处理员工提交成果后，Manager 向 A 的原 Session 插入唯一 `work_item_result` Input。成果在普通 Input 之前领取，单独执行验收 Turn。原发起身份按原授权 Input 重验，触发器根任务沿原触发事件。重复对账复用已提交结果。
4. 验收通过后，A 在原 Turn 继续生成最终答复。退回整改时停止 A 的当前 Turn，向接手者派新的 Task 和 Session，补充缺陷与上一次成果。A 等待修订结果。验收轮工具说明引导 Agent 优先退给本次成果提交人，前提是仍有接手资格；缺陷明确归属其他有资格的员工时可选该员工。整改说明列出未达标项、缺陷和补改要求。派发仍以显式选择的员工为准。
5. A 的固定模型暂时不可用时，成果及唯一的验收 Input 保持已保存、待领取。模型目标、协议和授权重新满足后，Engine 在原 Session 建立验收 Turn。已停稳的交接在接手模型短暂不可用时保留原意图并延后派发。
6. 当前环节明确失败且执行已停稳时，Manager 在同一事务中记录失败原因、结束事项、解除原任务的等待。结果未知、授权失效或本轮结束却缺少提交凭据时，事项显示待核对。只有已取得停稳凭据并能验证所有相关执行已结束的交接才继续派发。停止或归档的任务继续遵守停止版本。

## 在原聊天补充事项要求

- 主 chat 通过委派 MCP 调用只读 `work_item_get_current(task_id)`。它查询本会话委派且属于当前发起人的原任务，返回事项状态、经办员工、验收标准、需求版本及最近一次补充的投递回执。MCP 同时返回本次用户 Input 的不透明补充依据 `amendment_basis`。未关联或无权读取时返回空事项。
- 用户明确补充要求时，交互 Agent 用 `work_item_amend_requirements` 只提交不透明补充依据 `amendment_basis` 和新增要求 `content`。事项、接手环节和需求版本来自签名依据，Manager 由原会话、原用户 Input、事项和规范化内容生成稳定去重键。Manager 在写入事务中按依据绑定的原 Input 核验当前轮次、发起身份和当前授权，不用后来进入模型的另一条消息顶替。在同一事务中合成验收标准、推进需求版本，并将 `work_item_amendment` Input 排入当前经办员工原 Session。Input 含 Manager 查到的经办员工和合成标准，沿当前事项授权执行。收据区分排队和原生上下文已接收。
- 首版在接手环节受理提交或转交意图时截止本次修改。补充和提交竞争同一事项锁。补充先入库时，旧事项版本的提交或转交在停稳前被拒绝，接手 Agent 可以读取新标准继续。提交先受理时，补充返回 `work_amendment_closed`。有效原 Input 下，同键同内容和版本返回原 Input 的当前回执。纯需求版本冲突返回未应用、最新标准和绑定原 Input 和同一内容的一次重试依据；交互 Agent 只在非冲突时重试一次，冲突时说明未应用并澄清。任务环节变更或权限失效不自动重试。接手者已按新版提交或转交时，尚未领取的补充输入随原环节关闭，后继环节从事项读取最新版。
- 发布成果时把需求版本记录在提交凭据里，A 的验收 Input 含该版标准及成果提交员工。A 核验实际成果，Manager 校验提交及版本。已有事项和提交的需求版本初始为 1。

## 查看进度与通知

在「任务 → 事项看板」按当前经办员工、事项状态筛选。原任务和派生任务的详情有「事项时间线」入口。列表和时间线检查来源任务的读取权限。每一笔交接、开始办理、提交、退回、验收和异常记录由系统写入。时间线显示验收或整改依据，以及各通知目标的投递状态。升级时从已有分配、提交和终态记录重建可确认的历史。

首次交接、每次退回整改、最终验收和明确失败产生独立通知。对话发起的事项投递到来源会话，触发器发起的事项沿用该任务创建时保存的目标组。最终验收等待 A 的验收 Turn 结束，再发送含最终答复的通知。通过事件和各目标投递记录去重。历史事项升级时不会补发旧通知。

Event Hub 先应用迁移 84，再启动配套的 Backend、Engine 和 Web。

## 验证

`TestManagerRuntimeWorkItemsEndToEnd` 使用隔离 PostgreSQL、真实 Engine 和 Pi、确定性模型服务。覆盖对话任务与触发器任务发起，A 经 B、C 收回成果，退回 B 后新建整改任务，A 在原 Session 验收，以及普通 Input 在验收后执行。回归还覆盖模型恢复后只领取一条验收输入、文件版本与转交授权、明确失败与未知结果、看板时间线及原目标群里程碑。测试同时检查同批写工具门禁、按角色装配工具和原生历史隔离。

`TestManagerRuntimeWorkAmendmentsEndToEnd` 使用同一运行时，验证原 chat 查询与追加退款率、B 的队列投递与旧版提交拒绝、A 的新版验收和补充与提交并发。
