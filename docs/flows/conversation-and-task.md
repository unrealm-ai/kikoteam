# 从对话委派到结果投递

> **2026-11-16 关系与生命周期已确认**：一 Task 一 task Session，共享环境归 Conversation；创建、停止、归档、首版放置及三层回收按[业务会话与共享环境生命周期](../architecture/conversation-lifecycle.md)。本页已同步目标设计，执行编排及相关机器契约仍待实现。

状态：渠道、文件发布及投递仍是后续业务参考；用户/群到 Conversation 的映射另行设计。已确认一 Conversation 含唯一主 chat、多个 Task，每个 Task 对应唯一 task Session；创建和生命周期以[专项设计](../architecture/conversation-lifecycle.md)为准。文本 Input 不依赖文件资源或 Run。

当前链路为 backend 受理 Session / Input 并分配执行归属 → Engine 串行处理 Turn → Pi 直连获准 MCP（Runner 管理 Sandbox 并代理 stdio 插件） → Pi 持久化原生历史、Engine 保存消息与可靠事件 → backend 提供查询和 SSE。未开始输入可撤回，每次 stop 都停止本次受理范围内的工作及本 Session 后台进程，重试也重新确定范围，归档只读；故障后新 Input 加载原生会话，不自动续跑旧 Turn。详见[运行时与隔离](../architecture/runtime-and-isolation.md)。以下企微案例留待后续业务阶段重新确认。

主 chat 内的委派入口按[task_delegation MCP](../../backend/docs/task-delegation-mcp.md)：Pi 调 Backend 业务工具，Manager 原子创建同一 Conversation 下的 Task、唯一 task Session、首条 Input 和来源关联，返回受理身份后主 chat 可继续交流。工具的列表、查询、追加和停止复用同一业务规则。某轮结束由 Manager 保存回报，再接整体对话的上下文 / 唤醒入口；不对已返回的创建 tools/call 再发送第二个最终结果，也不把一次 Turn 结束视为 Task 业务完成。委派创建、查询、追加和停止，以及逐 Turn 自动回报/唤醒和有来源 Inbox 的渠道投递已接入，实际成功以各自回执为准，详见[输入与任务回报](../../backend/docs/session-input-and-task-report.md)。主 chat 的直接回答、委派边界、已有任务补充/查询/停止及受理后不轮询规则见上述专项文档的“主 chat 交互策略”。

以企微群成员定向请求“根据这份表格生成周报”为例。前提是机器人已绑定当前企业并在线，成员可以使用该员工，附件类型、下载方式及目标群发送能力均在已验证范围内。

| 步骤 | 参与方 | 提交点与用户可见行为 |
| --- | --- | --- |
| 1. 收到消息 | 企微经已建连接推送 → event-hub → 内部 backend | event-hub 主动向企微建连，再从连接上的事件取得来源和消息 ID。backend 按工作区、机器人、群及发送人受理；重连收到同一事件时复用原回执。 |
| 2. 识别委派 | 业务层 → Backend | 核验 Conversation 和父级准入，原子建立 Task、唯一 task Session、配置快照及首条 Input；具体渠道材料另行设计，不建 Run。 |
| 3. 开始执行 | Backend → Engine | 首次任务由 Backend 登记唯一共享环境和管理 Engine；后续同会话任务复用该放置，容量不足排队。指定 Engine 准备环境，Runner 获取配置/启动 MCP，Pi 留在 Engine。 |
| 4. 生成报告 | Pi → builtin MCP / stdio 代理 / 远程 MCP | Pi 直接访问已配置 MCP；Sandbox 内 stdio 插件由 Runner Gateway 转接。环境中的文件与命令操作由[builtin 的 11 个工具](../../sandbox-runner/docs/builtin-mcp.md)提供；报告发布与平台文件流程仍待后续设计。追加输入先持久排队，Engine 开始处理后再展示执行状态。 |
| 5. 确认结果 | Engine、backend、后续文件能力 | Pi 保存原生历史，Engine 提交执行完成事实；报告发布和下载需后续文件方案定义。业务层核对后完成 Task 并创建原群 Delivery，本期不预定 Runner 的产物上传工具。 |
| 6. 返回原群 | event-hub → 企微 → backend | event-hub 按绑定身份及目标权限使用原机器人连接发送，向 backend 回报渠道结果。Web 可按事件游标续读进度，按当前权限下载产物。 |

## 渠道边界

飞书 WebSocket、钉钉 Stream、企微智能机器人均由 event-hub 持有连接。各自的群消息、话题、历史和附件能力独立验证。企微群的定向请求以平台认证事件为依据；如允许补读近期上下文，则仅在请求触发后，按当前任务范围读取获准的群历史。正文里的昵称或 @ 字符不能建立可信身份。Web 发起的委派从 backend 直接进入同一业务受理流程。

## 主会话输入合批与消息前缀（2026-11-18 已确认，实施中）

本节是 2026-11-18 确认的目标规范，覆盖此前“群历史拼在当前 Input 正文、原生 committed 推进历史边界”和“false 暂时阻挡后续 true”的过渡方案。代码交付及测试结果另行记录，不以本节宣称已完成全部实现。沿用原生 Pi prompt/steer，不增加定制 Node / Pi SDK 宿主，也不新增角色注入扩展。

### 渠道 Inbox 与 Input 分工

Inbox 是该员工的可靠入站事件，Input 是等待进入该员工主会话上下文的输入；两个集合不同。事件过滤、使用权限、是否触发 Agent loop 是三个独立判断，不能靠正文前缀替代。

- 群及群话题：Event Hub 按**每位员工自己的绑定及规则**筛选，只有可信 mention 命中该员工，或正文命中该员工关键词，才进入该员工 Inbox。普通群消息和其他员工的定时消息不主动复制进该员工 Inbox/Input；若它们确实命中该员工 @ 或关键词，则按该员工的事件流程处理。这是跨员工事件路由的目标边界；当前飞书实时入口保留防机器人互相触发限制，非 `user` sender 会被忽略，即使命中关键词/@ 也暂不触发另一员工。它们仍可能进入按需群历史。不能把这两种读取路径混为一谈，也不能给所有员工广播上下文。
- 私聊及私聊话题：直接进入对应员工 Inbox，由 Manager 判断权限、员工状态及准入，不套用群 @/关键词过滤。
- 群内无权限 @：可以生成固定拒绝 Delivery；无权限关键词命中但未 @ 该员工：静默拒绝，不发固定提示。两者的原文及固定拒绝均不写 Input，不推进群历史边界。若同时命中 @ 和关键词，按 @ 的拒绝规则处理。
- 私聊无权限：生成固定拒绝；被拒原文和固定拒绝仍不写 Input。不借群历史机制把被拒私聊带入上下文。
- 有权限且命中触发的群事件、获准私聊消息，以及平台内部消息按自身业务语义写入 Input；Input 的来源类型不自动决定触发标志。定时提醒在本方案中为 false，任务回报等既有生产者不因本节擅自改成 false。

### 主会话与话题独立（2026-11-18 确认，本次实施）

主会话与每个话题各自拥有独立会话身份、主 chat Session、Input 队列、Pi 原生会话及历史边界。同一父会话下不同话题不共享合批成员或原生上下文，也不拿主会话水位截断话题历史。群话题和私聊话题都按可信渠道 thread/topic ID 定位，不用标题或正文猜测。

话题权限配置继承父会话，但入站、入 Input、执行和发送时都重新检查当前父级及员工权限；创建话题不复制出一份永久有效的授权。主会话旧映射和历史保留，无话题 ID 仍路由旧主会话，不能把既有主会话自动搬成某个话题或把其中旧消息猜测拆分。

话题事件路由、话题历史 API、可靠锚点及回复到原话题的能力分别验收。某渠道只能区分实时话题却不能可靠读话题历史时，仍维持 Input/Pi 隔离，并明确历史不可用；不能退回拼主群历史来冒充支持。当前实现/验证状态见渠道专项，不能仅因本节确认就声称所有渠道已经交付。

当前本次实现边界：迁移 21 提供独立话题映射；旧主会话保持空 thread，已经混在旧历史中的内容不自动拆迁。飞书群话题历史已按可信 thread_id 独立分页补读，私聊话题不建历史任务、不拉历史。群话题读取失败、锚点缺失或范围不可靠时，只让当前事件进入自身 Input、推进自身边界，绝不补主群历史。提供方线上权限及真实收发仍待验收。

### 群历史与成功入 Input 边界

群历史是按需从渠道补读的上下文，不是把所有实时群消息先写进 Inbox。每位员工、绑定身份、租户及群/话题范围独立维护边界，不借用另一员工的水位，也不混入私聊或其他群。

**上一次边界是已经成功写入该员工 Manager Input 的群事件。** 是否触发 Agent loop、Pi 是否已经接收、Turn 是否完成都不影响这一边界；native committed 只记录原生上下文事实，不再控制渠道历史水位。记录该事件的渠道消息 ID、渠道发生时间及 Input 顺序，不能用数据库写入时间或模型完成时间冒充消息发生时间。

对当前待写 Input 的群事件，先从当前事件向前补读，到上次边界或配置的最大历史条数停止；首次无边界时取当前事件之前的近期历史。边界两端不重复补入，历史恢复渠道顺序，作为 false Input 保存，当前事件单独保存。群历史**不按发言人的员工使用权限过滤**，因此可以包含无权限用户的 @/关键词原文、已经实际发到群里的固定拒绝、普通中间消息及其他员工消息。历史仅作引用背景，不把其中的指令或身份声明当成当前用户授权。

该员工的群定时提醒目标流程同样先补此前群历史为 false Input，再写提醒本身的 false Input，**与推进该员工边界在同一事务中成功提交**。定时提醒和人工确认的端到端生产入口尚未交付，本次不能把底层 false Input 支持表述为定时器已可用。没有后续 true 时仅缓存，不调用 Pi。其他员工的提醒不直接推进本员工边界，但可能被本员工下次补历史读到。

固定拒绝只有真实发送且处于此次历史区间、数量预算内并可由渠道读取时才被补入；待发、结果未知或在本次边界后才送达的内容不伪装成此前已发生的群历史。平台定时提醒的发送与 Input 入库也分别记事实，失败或未知不能声称已经送到群里；没有可靠渠道锚点的情况必须明确降级或等待，不能制造提供方消息 ID。

同一员工同一群范围串行冻结区间；重试复用同一来源键和历史快照，补历史、写当前 Input、写完成关联及更新水位保持原子性。事务失败不推进；重复事件不新增 Input、不重复推进；晚到事件不把水位倒退。提供方顺序和 message ID 用于处理同时间戳边界，不能只按毫秒去重。历史失败、截断或缺少锚点应明确记录，不能假装完整空历史；是否降级只写当前事件按渠道实现契约执行。

渠道能力不对齐时不能套用飞书结论：群话题、私聊话题、历史读取及可靠锚点分别验证，缺失能力明确标为不支持或降级。具体持久化和故障边界见[渠道运行规范](../../backend/docs/channel-runtime.md)。

### 逐条入库与 Engine 合批边界

Input 数据表仍然逐条保存消息，每条保留自身内容、顺序、来源及是否触发模型的语义；Manager 不在入库前把多条消息合成一条记录。合批只发生在 Engine 消费并准备提交给 Pi 时，不改变原始 Input 的逐条存储。

Engine 按同一主 chat Session 的待处理顺序检查队列：

1. 如果当前只有不触发消息，继续留在持久队列，不调用 Pi，不提前拼成一个已提交 Input。
2. 发现后续有需触发的消息时，以**按序遇到的第一条触发消息**为截止，一次抓取该消息及其之前尚待处理的消息，按原顺序组装为一条 user prompt，提交一次模型调用。
3. 该触发消息之后的所有消息，即使已到达且其中也有触发消息，都留给下一批；不跨过第一个触发点继续合并。当前轮运行期间新到的消息同样不能混入已固定批次。
4. 保留批次与各原始 Input 的对应关系，冻结成员、顺序和本次 prompt；重试不得把新到消息加入原批次。成功入库、已提交原生上下文、执行结束和渠道送达分开记录，不能以拼接成功或 RPC ACK 代替实际消费。
5. Engine 主动拉取队列；忙时只允许队首完整批次按已确认的原生 steer 规则加入，同一 Turn 不跨权限主体。遇 queue、不同主体或未知提交结果时等待/核对，不跳过较早输入寻找后续可引导项。明确未消费才归还原批次，结果未知不盲目重放。

例如队列按序为 `A(false)、B(false)、C(true)、D(false)、E(true)`，Engine 分两批提交：第一批 `A+B+C`，下一批 `D+E`；如果队列仅有 `A(false)、B(false)`，则全部保留等待后续触发。

### 前缀规则

| 消息来源 / 场景 | 输入正文格式 | 约束 |
| --- | --- | --- |
| 平台系统消息 | `[系统消息]正文` | 统一使用这一标签；定时通知、无权限提示等不增加子类型，不写成 `[系统消息｜定时通知]`、`[系统消息｜权限提示]`，也不改称“员工已发送的消息”。 |
| 私聊用户消息 | `正文` | 不加用户、说话人、姓名或“本次触发”等前缀。 |
| 群聊用户消息 | `[说话人=显示名]正文` | 仅群聊需要标识说话人；不额外添加部门、职位等前缀。 |
| 群聊消息含可解析的 @ | `[说话人=显示名][被@人=名称1,名称2]正文` | 采用统一的说话人 / 被 @ 人标签和 mention 转写方式；无可解析 @ 时省略被 @ 人标签，不产生空标签。 |

以上为提交给模型的文本格式，不是渠道用户界面必须展示的包装。系统消息标签仅表示平台产生的内容，不是模型接口的 system role，也不改变身份、权限或触发语义。是否触发由可信输入字段和业务规则决定，不通过正文标签猜测；普通用户在正文中写入相同标签不能获得平台身份。实时无权限原文及拒绝不写 Input；但同群后续按需历史不按发言人权限过滤，可引用这些已经发生的群内消息。该引用不产生新的执行授权。主 chat 自己生成且已有原生记录的 assistant 回复不再次排队灌入，避免重复。

### 群聊 @ 语义

群聊消息的 @ 转写遵循以下规范：

- 标签采用 `[字段=值]`，相邻标签直接相接，再接正文；被 @ 人按正文出现顺序收集，并按已解析身份 ID 去重（不是按显示名去重）：同一身份重复提及只列一次，同名但不同身份仍保留两项；多个名称以英文逗号分隔。
- 被 @ 人标签收集正文中能由渠道 mention 元数据唯一解析的对象；其中开头的连续 @ 呼叫从正文移除，正文其他位置的已解析 mention 保留为 `@显示名`。
- 未知或冲突的 mention token 保留原文，不猜测名字；显示名清理方括号和控制字符，名单中名称自身的英文逗号转为中文逗号，避免破坏标签结构。
- 被 @ 人表达消息提及对象，不等同于可信触发目标，也不能据此建立工具权限。实际触发员工、调用主体和渠道范围保持独立可信元数据。
- 私聊直接提交正文，不包含说话人等前缀标签；群聊中的可选部门字段也不纳入精简规范。

#### @ 转写示例

以下均为合成示例：说话人为张三；`@_user_1` 唯一映射到身份 A / 名称“项目助手”，`@_user_2` 唯一映射到身份 B / 名称“李四”，`@_user_unknown` 无可用映射。

| 渠道原始正文 | 组装后的模型输入 |
| --- | --- |
| `@_user_1 @_user_1 汇总进展` | `[说话人=张三][被@人=项目助手]汇总进展` |
| `@_user_1 请和 @_user_2 核对` | `[说话人=张三][被@人=项目助手,李四]请和 @李四 核对` |
| `请让 @_user_2 核对` | `[说话人=张三][被@人=李四]请让 @李四 核对` |
| `@_user_unknown 请核对` | `[说话人=张三]@_user_unknown 请核对` |

若身份 A 与身份 B 的显示名都叫“项目助手”，两者同时被提及时名单仍为 `[被@人=项目助手,项目助手]`，不能仅因同名而合并。前导移除只处理连续且可识别的 @ 呼叫，遇到未知或冲突 token 即停止移除；例如 `@_user_unknown @_user_1 请核对` 输出为 `[说话人=张三][被@人=项目助手]@_user_unknown @项目助手 请核对`。这里展示名仅供模型理解，真实身份和授权仍保存在可信元数据中。

### 组装示例

私聊的多条输入按顺序组织；用户正文不加前缀：

```text
帮我跟进今天的交付。
[系统消息]今天 16:00 有项目例会。
现在进展怎么样？
```

群聊按说话人和可解析的 @ 信息组织；最后一条是否触发仍由输入元数据表示：

```text
[说话人=张三]客户希望明天交付。
[系统消息]今天 16:00 有项目例会。
[说话人=李四][被@人=项目助手]汇总一下当前进展。
```

### 实施验收要点（本节不代表验收结果）

- 私聊普通消息无自动前缀；系统消息只有精确的 `[系统消息]` 标签，无子类型或“本次触发”标签。
- 群聊能识别说话人，@ 对象按身份 ID 去重（同名不同身份不合并）、前导呼叫移入标签、正文内 @ 保留、未知或冲突 token 不误替换；不把可读标签当授权依据。
- 多条不触发输入不调用模型；后续触发只提交一次有序合批，生成期间新消息不混入已固定的批次。检查重启保留、重试去重及“已接收但回执丢失”边界，不能盲目重放结果未知的模型调用。
- 原始消息、来源身份和合批成员关系保持可追溯；跨员工、跨会话不混批。群历史不按发言人权限过滤，但不会把历史内容变成当前执行授权。
- 无权限 @ 有固定拒绝、仅关键词命中静默；两类事件均不写 Input、不推进水位，后续历史仍可能读到原文。
- 定时提醒之前先补历史，历史及提醒均 false；成功入 Input 即推进边界，不等待 native receipt。重试、并发、晚到、事务回滚均不能重复或倒退水位。
- 每员工事件过滤正确，其他员工普通/定时消息不主动复制；当前飞书非 user sender 不触发其他员工，但仍可进入按需历史。群/私聊/话题能力逐项验证。

## 用户遇到异常时

- **附件无权读取。** 告知具体材料未就绪或无权访问，保留已接收的任务输入，待补充获准材料。任务不能借另一个群的权限读取附件。
- **入站原生附件读取失败。** 每个附件最多认领 3 次，下载和保存共用次数；租约过期也计数。若文件已经发布而回执丢失，先以同一条消息及附件序号的存储回执核对，不重复写文件。部分附件最终失败时保留正文与其余成功的附件；没有正文也没有成功附件时，明确告知附件无法获取。
- **最终事件迟到。** 若指向旧执行代次或更早 Turn，保留原证据，不能覆盖当前任务结果。
- **发送明确失败。** Web 仍显示任务已完成，产物可下载，投递显示失败。按原目标及渠道约定重试 Delivery，无需重新执行报告。任务回传附件按文件分别计数，最多认领 3 次（含发送前租约过期）；只有已明确未发出的可重试故障或明确拒绝才重试。达到上限或遇到不可重试故障时，本文件投递记失败，其他文件和文字回复继续，不重跑任务。
- **发送结果未知。** 使用原投递身份查询厂商可提供的回执。无法查实时保持未知，不能把重连或成功上传附件当作已送达的证明。

需要人工选择统计口径时转入[人工继续流程](human-and-handoff.md)。

停止主 chat 不停止已委派任务；停止/归档某项任务只处理对应 Session。Conversation 归档先关闭全部入口，再归档和收尾所有 Session，最后按授权回收环境运行资源；工作文件和历史保留，不能因一份报告完成就销毁共享环境。
