# 触发、分配与接管

业务定时和 Webhook 仍是后续入口。Backend 统一受理 Conversation 下的 Task/Session/Input，首版一 Task 一 task Session，不建 Run；负责注册、容量及执行分配，详见[Backend 调度](../../backend/docs/engine-dispatch.md)及[生命周期](../architecture/conversation-lifecycle.md)。来源业务 key 的路由策略另行确定。

“每周五生成交付报告”和“收到业务系统的 Webhook 后生成报告”都应生成可追溯的业务任务。入口不同，backend 负责的身份、权限、配置和幂等校验相同。

## 两类入口

| 入口 | 谁接收或发起 | 如何识别一次触发 |
| --- | --- | --- |
| Webhook | 任一 Backend 副本接收入站请求，核验绑定、来源与请求认证 | 使用绑定和稳定来源事件标识去重，记录请求摘要；同标识内容冲突可查。 |
| 定时计划 | 活跃 event-hub 扫描到期时刻，按计划时区计算，核验绑定仍启用，调用 backend 受理 | 绑定标识、版本及应触发时间共同决定一次触发。实际扫描时间只做诊断。 |

任务记录绑定的业务身份、员工、目标和来源，按预定权限运行。旧项目对停机期间已过且从未登记的计划时刻有跳过行为；迁移时保留该语义，恢复已登记的工作要沿用原触发记录。修改计划版本或停用绑定后，迟到的旧作业应可识别。

## 从持久意图到一次执行

1. Backend 核验来源并解析 Conversation，在事务中保存触发回执、Task 和唯一 task Session；立即执行时连同首条 Input 提交。待办若后续支持，显式开始只向原 Session 提交 Input，不新建 Run。父会话归档后不得绕过准入重新开启原执行。
2. Backend 首次为 Conversation 登记唯一环境、宿主和管理 Engine，后续 task 固定分配到该 Engine，容量不足排队；chat 独立调度。按父级及 Session 锁、环境唯一约束和容量条件更新裁决并发，提交后通知，丢失通知由周期扫描补偿。
3. Engine 只领取当前归属的工作，同一 Session 按序执行。容量暂时用尽时保留已受理输入，超出等待预算时给出可查询的失败原因。
4. backend 的周期维护使用独立数据库锁选出一个执行者，扫描失联 Engine 和持久待办；即时分配不依赖该角色。event-hub 仍须取得自己的选举锁、完成迁移并核对在途业务触发和投递后才恢复渠道业务。其失锁只停止所属迁移、业务触发及发送，不批量取消 Input 或停止健康 Engine，详见 [event-hub 生命周期](../../event-hub/README.md#退出与接管)。

event-hub 换主或 backend 维护角色切换都不批量更换 Session 的 Engine。backend 先核对持久归属、Engine 状态及旧执行隔离事实，仅在实际重新分配时提升代次；恢复步骤见[运行时与隔离](../architecture/runtime-and-isolation.md)。数据库锁不撤回已经发出的渠道请求，响应丢失的投递沿原身份查询，无法查证时保留未知，不盲目重发。

## 验收边界

同一期计划在滚动重启期间被扫描两次，只产生一个有效业务结果；相同 Webhook 被两个 Backend 副本同时接收，返回同一受理事实。Engine 在收到通知前重启，已提交的工作仍能被找到；旧 Engine 恢复后，迟到提交不能改写新代次的结果。

仅持锁连接断开而普通连接池、渠道网络仍可用时，旧 event-hub 也必须停止所属业务工作，不能换连接继续关键主实例写入；备用实例在 PG 实际释放锁前不得开始工作。正常 Engine 不因 event-hub 换主而被重分配。另验收两 backend 并发分配只有一个归属、容量只预留一次、维护扫描丢失后待办可重新发现；发送未知结果继续沿原投递身份核对，见 [event-hub 验收要求](../../event-hub/README.md#验收要求)。
