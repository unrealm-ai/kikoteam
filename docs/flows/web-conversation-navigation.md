# Web 对话导航与会话任务：设计方案

状态：2026-11-18，**用户已确认目标，仅设计、未开发**。用户在实现前改为先整理方案；本轮不增加导航 API、迁移、前端、通知或未读功能。下列端点和存储方式为建议，不代表可调用的既有接口。

## 已确认目标

1. 当前工作区内，把当前用户可见且已有消息的 Web 私聊与 Web 群放入同一个倒序导航列表，支持稳定 cursor 分页。空私聊、空群不占主列表；群只有一个入口，不按员工重复显示。
2. 点击后按该对话分页读取消息，不展开内部员工执行记录来冒充群消息。
3. 右侧查询该会话关联、当前用户获准查看的任务。Web 群需要真正的群关联任务摘要，不以现有公开 Session 禁止群访问为由直接返回空列表。
4. 搜索可找到当前工作区内用户**可使用的 AI 员工**与用户**已经加入的 Web 群**；它们即使暂无消息也能被搜索到。
5. 右上创建群对应后端创建群能力，可添加工作区用户与 AI 员工；本阶段不做任何前端界面或实时通知。

首版只针对真实 Web 身份。其他 IM 的用户身份未打通时，不按群名、显示名或相同字符串 ID 推断该用户可读渠道群历史。

## 导航选群与员工配置选群不是同一种权限

- **导航、搜索、打开消息中的群**：用户当前加入的群。退群或被移除后不能打开群或继续读消息/任务列表；工作区 owner/admin 不因此绕过群成员限制。
- **统一通知或群共享配置中的群**：AI 员工所在群，操作人按员工管理权限配置；不要求操作人也是群成员，但只能取得配置所需的必要群元数据，不能由此读取群消息。
- 两者可以复用底层渠道 adapter、稳定群标识和元数据结构，但必须使用不同的业务授权入口和每次查询条件。不能复用“员工群候选可见”来证明“人类群消息可读”。
- 统一选人指对应渠道真人。Web 创建群选择工作区用户；用户 ID 与员工 ID 是不同主体，不按名字合并，也不能以员工身份冒充人类成员。

## 已核实的数据事实

- Web 固定私聊按 workspace + user + employee 解析；`manager_conversations.web_user_id` 标识人类归属。导航应严格选择当前用户的 Web 私聊，不把历史通用 Conversation 或渠道 Conversation 当成私聊。
- 私聊的 chat Session 存储 `manager_session_events`，已有 `user.message` / `agent.message`、可靠事件序号与倒序高水位分页。工具、thinking、状态事件不能单独使一段空私聊成为“已有消息”。
- Web 群共享 `manager_web_group_messages` 单份流及 seq；各员工有独立内部 Conversation、Input 和边界。导航按 group_id 合并，不泄露内部 Conversation、Session 或输入队列。
- 当前公开 Session/Task 读取路径明确不开放 Web 群内部会话。新增群任务摘要应是独立的最小只读投影，不改这些旧接口的授权，不通过构造内部执行上下文绕过它们。
- Platform 已有 Web 群创建/更新/退出、群角色与成员数据；新增设计优先复用它们，而非再造群实体。实际候选用户/员工接口是否满足最小字段和当前授权，实施时逐项核对。

## 导航列表与稳定分页

建议独立读取入口，例如 `GET /api/v1/workspaces/{workspace_id}/conversation-navigation`。每项只给类型、稳定资源 ID、标题/员工展示信息、最新消息时间及后续读取所需的公开定位标识，不返回最新消息正文、工具记录或群内部会话集合。

排序规则建议为：首屏快照内的最近真实消息时间降序，再以类型和稳定 ID 唯一打破同一时间并列。不得只对实时变化的 last_message_at 做普通 keyset：翻页时新消息可能把未读到的行移到前页，造成遗漏。

**建议使用短期物化排序快照**，而非宣称一个时间上界已经解决所有并发问题：

- 首屏在一致性读取中固定可见条目的 ID、类型、排序位置与当时最新消息时间；不缓存消息内容、任务正文或授权结论。
- cursor 签名绑定 workspace、user、snapshot、位置、筛选及期限；第二页起从快照继续，权限每页实时重验。已退出群的条目跳过，不能为了保持快照完整而继续暴露。
- 新消息或新出现的会话不会插进旧快照；用户刷新首屏获取新排序。明确“稳定分页”是首屏集合的稳定遍历，不是同时持续刷新列表。
- 建议 TTL 15 分钟、每用户/工作区最多 5 个活跃快照、每快照最多 5,000 项，均为实施前可调整的工程建议。达到上限必须显式提示，不静默截断并声称全部遍历；过期 cursor 明确报错要求刷新。
- 应限制快照字节体积、创建频率，并实现有界清理。逻辑过期不等于物理删除；若采用请求驱动清理，需明确无人访问期间不会及时回收，不能承诺严格物理 TTL。
- 不保存长期数据库事务或连接供 HTTP 后续页使用；不因客户端游标而信任旧成员状态。

本方案未创建快照表、未预留实际迁移内容。实现时需与其他工作合并后的迁移编号及数据库版本重新核对。

## 消息分页

- 私聊：按当前用户和工作区核验固定 Web 私聊，再定位其 chat Session；优先复用已有可靠事件读取。对话视图筛选真实 user/agent message，仍以权威序号分页；如调用方需要完整原生事件，该能力与导航返回分开声明。
- 群聊：读取共享消息表，建议增加最新页/向旧页读取、固定高水位及 cursor；seq 为稳定排序。新消息不插入旧页，刷新或单独前向读取再获取新增消息。本次不做订阅、推送、未读数。
- 每次请求重新检查当前工作区成员与群成员。新成员可以读加入前历史；退出后不能打开群。成员变更与读取需沿现有锁/事务约定处理，不能只在首次取 cursor 时授权。
- 群消息不能通过“每员工 Input 拼接”还原：这会重复、遗漏普通消息，并暴露不属于共享群流的模型背景。

## 会话任务列表

### 私聊

只查询该私聊 Conversation 的任务，沿现有 Task/Session 授权；工作区、当前用户、会话过滤同时成立。无来源 TaskSpace 任务不因业务 key、同一员工或标题相似而出现在右侧。

### Web 群

新增独立摘要投影，按 `web_group_id` 聚合该群内部各员工 Conversation 关联的 Task。仅当前 active 群成员可读，每页重新授权；不把管理工作区或管理员工作为群成员替代。

建议字段严格限定：`task_id`、`title`、`lifecycle`、`execution_state`、员工 ID/名称/头像及必要分页时间。不得返回 Session ID、输入、结果摘要、回告正文、来源用户私密字段、工具、沙箱、原生记录或凭据。

“群关联”须由实际关联证明：Task 的 Conversation 确实属于该 Web 群。不得把同员工其他私聊任务、其他群任务或无来源 TaskSpace 任务混入。当前任务标题属于最小摘要的一部分，实施时仍须核对标题生成策略，不能用原始私密输入填充公开群标题。

这不授予 Task 详情或 Session 详情权限。点击任务详情若现有授权不允许，应明确拒绝或仅继续显示这份摘要，不复用管理员/内部执行通道读取全文。建议按 Task 创建时间与 ID 倒序稳定分页；状态实时变化不改变该排序。

## 搜索与创建群

建议独立搜索入口，例如 `GET /workspaces/{workspace_id}/conversation-search?q=...`，返回区分类型的必要员工/群元数据：

- 员工以当前用户的可使用范围和启用状态筛选，不能直接返回工作区全员管理列表。
- 群以当前用户实际成员身份筛选，不因员工已加入群而向用户展示导航目标。
- 查询参数、cursor 绑定工作区/用户/搜索词，拒绝重复/未知参数；名称匹配不改变授权。
- 搜索结果可以包含尚无消息的员工或群，打开或发消息后才按实际消息事实进入主导航。

创建群复用 Platform 群模型及既定 owner/admin/member 权限：创建人是群主；工作区管理员不自动成为每个群的管理员。添加成员须核对当前工作区有效用户，添加员工须核对真实工作区归属及允许的管理/使用政策。不能由搜索某人或某员工可见推导任意修改群的权限。尚未明确的更细管理政策不由本设计擅自扩权。

## 后续验收矩阵（尚未执行）

- 空私聊/空群不在导航，真实消息出现才入列；同群多员工仅一项；同毫秒稳定并列。
- 连续翻页期间插入消息、创建会话、撤销成员、刷新首屏：旧快照无重复，授权撤销立即过滤，新首屏有最新排序。
- cursor 篡改、跨用户、跨工作区、过期、快照淘汰与上限均明确失败。
- 消息倒序/高水位、多页边界、群用户加入前历史与退出后拒绝；不能跨群或进入员工内部 Session。
- 群任务跨员工聚合有真实结果；其他群、其他私聊、TaskSpace、内部输入/工具/沙箱不可见；当前成员退出后 cursor 无效或空授权拒绝。
- 搜索可用员工而非全员、只搜已加入群、零消息结果、名称重名及跨租户隔离；创建群重复提交与越权添加沿既有 API 验证。
- 使用独立测试 PostgreSQL 验证事务与权限，HTTP 测鉴权/参数/响应最小字段；不连接运行数据库，不调用外部渠道。
