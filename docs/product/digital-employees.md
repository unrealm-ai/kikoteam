当前按[Agent 会话与执行底座](agent-sessions.md)规划核心资源及后端 API。业务会话、Task、执行 Session 和共享 Sandbox 的最小关系与生命周期已按[专项设计](../architecture/conversation-lifecycle.md)确认；群范围、任务结果、文件资料、人工协作、模板及事项交接仍为后续参考。Session 关联 Conversation，首版一 Task 一 task Session；不恢复群范围或 parent_session_id 参数，Input 仍只定义文本。

## 1. 产品定位与命名

团队可以把一个岗位的职责、工作方法和业务工具配置成一位 AI 员工。成员在 Web 或工作群找它办事，能看到任务进展，必要时参与确认，最后在约定的位置收到结果。团队验证过的岗位可以发布为模板，让其他人用自己的账号和数据复用。

**界面统一叫「AI 员工」，领域对象统一叫 `Agent`，主标识为 `agentId`。** 同一位员工可以在 Web、私聊和多个群里工作。换名称、改模型、更新技能或增加渠道时，成员仍能找到原员工和有权查看的历史。旧版中表示员工的 `Entity`、`entityId`、`Employee` 是历史对照名。迁移须保留原员工与权限、渠道、任务和记录的关联。

| 参与者 | 最常做的事 | 成功体验 |
| --- | --- | --- |
| 业务成员 | 找员工、聊需求、交代任务、补充材料、查看结果 | 知道找谁、做到哪一步、结果在哪里 |
| 员工搭建者 | 写岗位指令、组合技能与插件、配置员工、试用、制作模板 | 能用一条代表性任务验证这个岗位，并让同事复用 |
| 工作区管理员 | 邀请成员、配置模型与插件接入、管理渠道与共享资源、授权发布 | 能解释谁可以调用哪位员工、它用哪个账号做什么 |
| 平台维护者 | 发布预置模板、技能及插件版本 | 不同工作区能使用同一岗位蓝本，并独立绑定业务系统 |

搭建者是一组管理权限，可由现有成员承担。产品分别判断员工管理权、员工使用权、插件接入管理与账号选用权和模板发布权。管理页面按可执行操作展示入口。

官方模板由平台管理员管理，工作区模板仍由工作区 owner/admin 管理。首位成功登录用户自动成为平台管理员，后续由管理员在平台用户管理中给其他账号授权；平台角色不替代工作区角色。详细规则见[平台管理员](../../backend/docs/platform-auth.md#平台管理员)。

## 2. 产品对象与关系

| 界面名称 | 英文名 | 用途 |
| --- | --- | --- |
| AI 员工 | `Agent` | 工作区内持续承接工作的身份。每位员工有名称、职责、配置、使用范围和业务记录。 |
| AI 员工模板 | `AgentTemplate` | 描述一个可复用岗位。平台可预置，团队也可编写或从已有员工提取。一个模板能创建多名独立员工。 |
| 岗位指令 | `systemPrompt` | 写明服务对象、职责、表达方式、交付标准、何时求助。成员在员工目录看到的是简短的职责介绍。 |
| 能力包 | `CapabilityPackage` | 员工绑定的资源组合与使用范围；工作区模板复制给员工，不与模板后续修改自动联动。 |
| 技能 | `Skill` | 封装一种可复用的方法，说明何时使用、所需输入、处理步骤和产出，可附脚本、示例、参考材料。 |
| 插件 | `Plugin` | 一份 CLI 或 MCP 能力定义，可附带 Skill，声明运行、接入及认证要求。 |
| 插件授权 | `PluginAuth` | 保存具体账号、授权目标、凭据引用和授权状态；普通环境参数仍称接入设置。 |
| 模型配置 | `ModelProfile` | 平台或工作区管理的一条具体模型完整调用配置，可供多个 Agent 引用。 |
| 会话运行模式 | `chat / task` | chat 采用平台默认配置，task 使用 Agent 的一套执行配置；不是两份 Agent 角色配置，也不表示父子会话。 |
| 员工配置版本 | `AgentConfigVersion` | 保存即生成的岗位指令、模型选择、能力包及包内技能/插件版本、员工插件账号引用和操作范围，无草稿发布流程。 |

搭建者在员工页写岗位指令，绑定能力包，在包内选择技能和插件操作；需要复用整套岗位时，另存为 AI 员工模板。例如「编写研发周报」是一项技能，可以要求工单插件提供查询操作，也可以选用代码变更查询。「整理会议笔记」可以仅使用成员上传的材料。员工可通过获准能力包直接调用插件操作，也可在运行技能时调用它们。两种路径都由「使用范围」判断谁能用、从哪里用、能做哪一步。

工作区里的资源可以被多名员工引用。员工模板属于后续业务规划；首版 Sandbox 是 Engine 本机的 Mac/Linux 项目目录和同账号进程，不做安全隔离，不提供会话级特殊环境配置，容器仅保留扩展。见[领域模型](../architecture/domain-model.md)及[裸 Sandbox](../../sandbox-runner/docs/local-sandbox.md)。

## 3. 用户从哪里开始

| 一级入口 | 成员看到什么 | 管理者可做什么 |
| --- | --- | --- |
| 首页 | 最近对话、进行中的任务、等我确认、可用员工 | 查看需要补配置的员工并进入对应设置 |
| AI 员工 | 按名称和职责找员工，进入对话、查看相关任务 | 新建、试用、编辑、启停、另存为模板 |
| AI 员工市场 | 按工作目标浏览官方精选与工作区模板，查看交付样例和接入要求 | 从模板创建员工，制作、发布和下架获准管理的模板 |
| 任务 | 按员工、来源、状态查看有权访问的任务，查看进展、产物和送达情况 | 定位失败环节，处理可重试的投递 |
| 事项看板 | 在已开启事项协作的工作区查看事项、当前负责人、交接和进度 | 配置交接接收范围，核对阻塞环节 |
| 资源库 | 浏览获准可见的技能、插件和能力包模板，查看用途和示例 | 发布资源版本，在插件详情维护接入设置，管理工作区模型和默认选择 |
| 设置 | 查看工作区信息及本人相关设置 | 管理成员、邀请、角色和工作区功能开关 |

员工详情以「概览、对话、任务、配置」组织。概览回答「它负责什么、谁能用、现在能做哪些工作」，给出第一条可直接委派的示例。配置页按「岗位与模型、技能与插件、使用范围、渠道、触发器、人工确认与交接」分组。成员在聊天或任务页就能完成日常操作。

## 4. 创建、试用与模板发布

**从模板创建。** 从「AI 员工市场」或「AI 员工 → 新建 → 从模板创建」进入同一模板列表。详情先展示典型委派和交付样例，再介绍模板预设的完整能力、模型及接入要求。创建向导分为「岗位设定、模型与接入、确认创建」三步，固定来源版本，能力、技能、插件及操作清单整体带入并只读展示，无需再次勾选；实际创建要求选择可用模型，初始全员可用，黑名单为空。员工创建后在其名下连接业务账号、确认模板所需授权并完成首次试用；可稍后接入的系统未连接时，对应能力保留为待接入，已就绪能力可单独试用。详细页面、状态与恢复路径见[创建员工流程](digital-employee-market.md#5-从模板创建员工)。

**从空白创建。** 自行搭建员工时填写名称、职责简介和岗位指令，预选可用的工作区默认模型，由搭建者按岗位需要配置能力包。此能力配置入口不混入从模板创建流程。创建后补齐插件账号并核对实际操作范围，初始全员可用，黑名单为空。后续可在「使用范围」收窄权限。只靠文字处理的岗位可直接进入首次对话。接群、设置定时和配置跨员工交接均在后续员工设置中完成。

**试用与启用。** 试用使用实际选定的模型、使用范围和插件接入设置，试用前列出目标系统及可能发生的写操作。员工概览分别展示「能否对话」「哪些技能可用」「哪些渠道在线」。搭建者用样例任务检查交付物后，将员工开放给所选成员或渠道。当前底座中，停用 Agent 后禁止新会话和新输入，未开始的输入拒绝执行，当前轮正常收尾；重新启用不恢复旧排队输入，旧会话可沿用原快照。已有工作的进展和停止入口仍可查；业务账号撤权后展示实际验证结果。后续委派业务沿用这条执行边界。

**制作模板。** 作者可从「AI 员工市场 → 管理模板」新建，也可从员工详情「另存为模板」。预览中逐项检查岗位指令、示例和参数，把具体团队名、工单项目等业务信息替换为创建时填写的值；私有服务地址不作为岗位参数替换。每次保存有变化的内容自动累计版本，最新未发布版本为草稿，点击发布才切换市场版本并冻结分发依赖；平台发布到官方精选，团队发布到本工作区。编辑不改变原版本在市场中的内容和已发布状态；下架阻止新建员工，既有员工独立维护。完整内容与检查见[模板制作与发布](digital-employee-market.md#4-模板制作与发布)。

| 可随模板复制 | 在目标工作区重新确定 | 归原员工或工作区 |
| --- | --- | --- |
| 职责、岗位指令、参数、完整能力包配置、技能与插件固定版本、预设操作清单、接入要求、模型能力要求、示例任务与交付样例 | 员工名称、实际模型、插件所用账号与环境、对应账号授权及成员使用范围、渠道机器人、确认人、交接对象、触发身份与通知目标 | 密钥、业务账号凭据、成员名单、真实群聊、历史任务、文件及交接记录 |

模板方案采用**复制创建**，模板的草稿和发布不等于 Agent 配置的生命周期。Agent 保存配置即生成新版本并供新会话使用，已有会话沿用快照，后续操作仍核验当前权限。模板和创建流程的产品细节统一维护在[AI 员工市场设计](digital-employee-market.md)。

## 5. 一位员工的配置

### 岗位与模型

**官方模型与积分（2026-11-18，已实现）**：原有模型选择中加入官方选项，后台为每位员工自动管理代理 Key，按员工固定扣费账户结算；新用户默认赠送 1000 积分，可配置，允许已放行调用结算为负数。完整规则与 UI 见[官方模型与积分设计](official-models-and-credits.md)，API、数据库与独立子模块见[技术设计](../../backend/docs/model-proxy.md)。该功能不提供 Key 管理页面，也不向任务或会话流程增加计费字段。

ModelProfile 保存名称、服务地址、协议、具体模型和认证信息。协议范围包括 Chat Completions、Responses 和 Anthropic Messages，实际接入由 Harness 验证。Agent 只选择一个模型配置，思考强度及其他生成参数全部跟随 Harness。模型配置更新自动影响所有引用它的新会话，已有会话固定原配置；凭据和当前权限另行核验。

Agent 只保留一套任务执行配置，聊天模式由平台预设。模型联通、真实对话和工具执行分别验证，连接成功不等于完整能力已可用。前台与后台的业务组织在后续阶段设计。

chat 与 task 是可独立创建的统一 Session 运行模式。当前不按群或用户自动复用，不建立父子关系、自动反馈或级联控制，不交付业务委派 MCP。创建时不能覆盖配置，Input 当前只有文本；使用 Skill 的意图交给 Harness，不单设字段。

### 技能与插件

Skill 是包含 SKILL.md 的普通目录，可带脚本、参考资料和模板。Plugin 选择 CLI 或 MCP 一种类型，可附带多个 Skill，并声明运行及认证要求。PluginAuth 管理具体账号授权，支持静态凭据、OAuth 及 CLI 登录的完整生命周期；无认证插件可不绑定。一个插件可以有多份授权，具体账号在员工绑定时授权；同一员工多个包使用同插件时的账号共用该员工的一份插件授权，各包工具范围可不同。员工不直接绑定技能或插件，账号授权关系不授予工具使用权。

Skill 每个版本保存完整目录，而非只保留正文；统一资源库保留既有 ZIP、Git、Markdown 和手动入口的交互，四入口真实接通为本轮待审阅方案，具体边界见[资源与能力包迁移设计](../../backend/docs/platform-capabilities.md)。本地默认 `~/.kiko/workspaces/`，S3 使用同一工作区逻辑路径；能力包只引用固定版本，不复制资产或账号秘密。

Skill 和 Plugin 更新生成新版本。新建能力包或新绑定资源默认选择当时最新可用版本并固定，已绑定项仅提示有新版，由用户显式升级并保存；插件附带 Skill 随插件版本固定。权限和认证状态在后续调用时重验，升级资源不自动授予新增工具权限，Token 刷新不生成插件版本。使用范围内的工具默认直接执行，首次登录或重新授权通过插件授权流程完成。

### 创建与维护权限

工作区成员可以浏览员工名录和简版「概览」，显示头像、名称、岗位职责和可用状态；允许使用的员工可进入现有对话。卡片和详情按钮默认进入概览，使用权限不等于查看配置。只有对该员工有管理权限的人看到六个详细配置 Tab；尝试直接打开管理 Tab 的链接也回到概览。非管理者的员工响应不包含岗位行为规范、模型配置标识或模板参数，员工能力包配置接口拒绝访问；对话历史沿用各自权限。


工作区有效成员可从空白或已发布的可用模板创建 AI 员工。新员工默认工作区全员可用，默认确认人沿用创建人的 Web 账号；官方模型仍按工作区 owner 扣费。

员工管理按当前主体和目标员工判断。工作区 owner/admin、仍是有效成员的创建人和显式维护人可配置同一员工，包括修改维护名单；不赋予管理工作区、发布共享资源、管理工作区共用连接或读取凭据的权限。员工专用连接按员工权限管理。技能与插件仍从现有共享池选择。创建人和管理员不需要列入维护名单；迁移时一次性将已有员工的创建人补为所属工作区 owner；不改原人工确认人或历史计费记录。迁移完成后新旧员工使用同一授权规则。

「权限和共享」页底部的维护人配置固定为个人白名单，可添加多个 Web、飞书、钉钉、企微身份，不接受部门、群、继承使用范围或黑名单。Web 授权与对应 工作区成员关系绑定；渠道按当前员工渠道的绑定、租户、身份代次和个人 ID 保存，企微使用已核验回调身份。当前版本开放 Web 配置和 Web 维护权限；渠道名单为后续 IM 管理 MCP 保留，不自动映射为 Web 登录身份，不新增 IM 写入口。员工使用范围、维护名单和人工确认人相互独立。

### 使用范围与群共享

**2026-11-19 已确认设计**：员工和能力包各管一层。员工配置统一归 AI 员工，不按各渠道重复维护名单；渠道绑定与机器人凭据保持独立。各渠道的人、部门和群使用可验证的原始身份，不按显示名合并。选择器与群共享见[统一选人与跨渠道群共享](identity-selection-and-group-sharing.md)。

| 要回答的问题 | 配置位置与规则 |
| --- | --- |
| 谁可以使用员工？ | 员工选「全员可用＋黑名单」或「仅白名单」。只选具体人员、飞书/钉钉部门（可指定含子部门）；企微只选已核验联系人，Web 只选工作区账号。不再新增员工级群名单。 |
| 在群里如何使用员工？ | 员工须实际在群且通过现有群及成员准入。「群内可用」默认开启：群成员不受人员白名单约束，但黑名单仍生效。关闭时按同一份人员范围判定，不等于禁用群聊。私聊不受此开关影响。 |
| 获准使用员工后，可以用哪些能力？ | 每个包的私聊、群聊、触发器场景各自启停、独立授权；详细语义见[能力包授权设计](../../backend/docs/platform-capabilities.md#能力包按场景授权)。始终先判员工/触发入口的准入，再看包的范围和工具；包不能扩大上游授权。 |
| 能读取另一个群的内容吗？ | 群、话题、私聊默认独立。群共享另外配置：项目组内各群互通，信息同步定向授权读取，可选择目标群或指定人。能选中群、能使用员工、能使用包、能读取群历史是四个不同权限。 |

新名单不应无提示覆盖既有授权。旧员工群名单、白名单与黑名单叠加的旧策略，在无法等价转换时保留原拒绝边界，待管理员重新确认；不能自动删除黑名单扩大访问。

例如，员工在客服群和研发群均可用；「发布」包可以只开群聊并要求发布群和指定值班人员同时命中，在私聊里则不开放。另一个报表包可给指定定时任务使用，与群聊授权无关。

### 渠道与机器人

Web 是创建后即可进入的交互入口。飞书、钉钉、企业微信在员工的「渠道」页分别接入，按渠道支持的方式扫码创建或手动绑定。管理员核验应用和租户身份，查看通讯录同步情况，再发一条测试消息确认收发。员工准入统一在「使用范围」配置。首次绑定直接使用当前模式和名单，白名单模式缺少当前渠道人员或部门时，渠道页提示前往配置。

每个渠道分别显示配置已保存、凭据已认证、连接在线、最近一次真实收发。页面按渠道展示定向消息、群上下文、历史补读、附件、会议资料、云文档和结果发送的实际支持情况，以及尚缺的授权。换绑机器人时先展示受影响的身份映射、名单和共享规则，完成后重新核对。成员可从问题所在项进入处理，例如连接在线但文档读取被拒时，定位到那份文档的访问权。

确认换绑后，旧渠道身份对应的人员、部门和群条目失效。使用范围及能力包按剩余名单求值，失效的黑名单条目可能扩大权限。群共享和定时通知跳过失效条目对应的方向或目标，仍有效的目标照常处理。

### 触发器与自动运行

| 入口 | 如何设置 | 如何跟踪 |
| --- | --- | --- |
| 定时触发 | 填任务说明、周期、时区、执行身份和结果目标，在「使用范围」核对本触发器可用的技能与操作，预览下一次触发时间 | 查看启停状态、计划时间、对应任务及投递回执 |
| Webhook | 绑定外部来源、认证方式、稳定事件标识、任务输入、执行身份和目标 | 按来源事件查看已受理、重复、拒绝或任务结果 |
| 渠道事件 | 按该渠道能力配置定向请求，或经授权的关键词触发，以及允许的群和任务动作 | 记录来源应用、会话和原始事件，与正常聊天分别显示 |

新建规则先保存为停用，管理员验证执行身份、开放能力和结果目标后启用。自动化有独立的业务身份，在各能力包的「触发器」场景按具体触发器收窄授权。同一来源事件或同一期计划只创建一次有效任务。停机期间尚未登记的过期计划按原有规则跳过，已经受理的任务可继续追踪。停用后历史触发和任务仍可查。[触发与派发流程](../flows/triggers-and-dispatch.md)

## 6. 从一句委派到一份可用结果

| 成员动作 | 产品行为与可见结果 |
| --- | --- |
| 在 Web 或群里聊需求 | 保持持续对话（Conversation），在可信成员、群或话题范围内使用获准上下文。明确委派后给出可打开的任务引用。 |
| 创建待办或立即开始 | 待办可先记下目标，显式开始后进入执行。后台任务（Task）使用独立会话（Session），前台继续对话。任务页显示来源、员工、采用的配置、输入和进度。 |
| 追加要求或取消 | 将补充明确关联到任务，区分已收到与执行已采用。取消先展示已请求，停稳后更新结果；已经发生的外部操作保留记录。 |
| 回答一个待决定的问题 | 后续按问题选择确认人；核对答复身份、版本及父会话准入，停稳后在原 Task/Session 受理一个新 Input，由 Engine 执行新 Turn，不建 Run；重复答复只生效一次。 |
| 交给另一位员工 | 在开启事项协作的工作区，首次有效交接建立事项（WorkItem）。接手员工负责新的处理环节（Assignment），使用自己的任务、会话、模型和授权。交接单写明目标、进展、待办和获准移交的材料。 |
| 查看与接收成果 | 任务完成时登记摘要和获准下载的产物。发送回原群或指定目标单独记录投递（Delivery）。任务页可同时显示「已完成 · 发送失败」，明确失败时可按原目标重试投递；结果未知时先核对原回执。 |

例如需要财务选定统计口径时，使用「人工确认」，原员工拿到答复后继续做同一份报告。把初稿交给合规员工审核时使用「事项交接」，接手方拿到获准的初稿和审核要求。成员能在同一事项上追踪两位员工各自负责的工作。[对话到投递](../flows/conversation-and-task.md) · [人工确认与事项交接](../flows/human-and-handoff.md)

上述指定确认人流程和事项交接属于后续业务参考。当前会话底座只受理独立 Session 的文本输入与控制，不建立 WorkItem / Assignment、业务父子关系或文件对象；缺少信息时通过普通新 Input 继续。

## 7. 贯穿案例：支付组周报助手

1. 平台发布「研发周报员」模板，预设岗位指令、周报能力包、工单汇总及代码变更汇总和相应操作清单，提供周报示例。工单系统必需接入，代码仓库可稍后连接。
2. 支付组选择模板，创建「支付组周报助手」，填写项目范围，沿用工作区模型，完整带入预设能力，无需再次选择。创建后为该员工连接「支付组只读账号」并确认模板所需查询授权；同员工其他能力包引用同一插件时共用此账号，各包仍保留各自的预设操作范围。代码仓库尚未连接时，代码变更汇总保留为待接入，界面提示本次报告覆盖工单。
3. 搭建者从 Web 委派「整理本周进展，每项结论附工单链接」，检查实际交付后向支付组开放。随后绑定企微机器人，测试群内收发，设置每周五的触发计划和结果接收群。
4. 负责人在群里补充「退款项目单列」。成员能看到补充是否已被采用。涉及财务口径时由指定确认人答复，周报完成后在任务页下载并投递到原定群。若需要合规员工复核，可把初稿作为移交材料发起事项交接。
5. 团队将验证过的版本另存为「业务线周报员」工作区模板。另一小组选用相同技能，填入自己的项目、模型和插件账号，独立完成第一份周报。

## 8. 交付顺序与验收

以下是完整平台的后续交付参考。当前按[会话底座阶段](agent-sessions.md#8-分阶段交付与验收)建设文本、工具和认证，并落实已确认的业务会话/任务关系及生命周期；渠道路由和任务结果见相应业务设计，工作文件和固定交付版本的归属见[存储目录方案](../architecture/storage-paths.md)。旧功能作为迁移清单保留，不直接复制旧参数结构。

| 阶段 | 可交付的用户行为 | 验收样例 |
| --- | --- | --- |
| 首条业务链路 | 在 Web 从模板创建员工，整体复用预设能力，填写岗位信息、选择模型并完成接入；从空白创建时由搭建者配置能力包。确认使用范围后完成后台任务并取回产物 | 当前批次只验证远程 MCP；CLI / stdio 留后续。从模板创建无需选择能力。缺必需账号时能定位到接入设置并补配，可稍后连接的系统未接入时保留对应能力，并说明结果覆盖范围。 |
| 团队复用 | 编辑员工、发布工作区模板、按版本复制创建，配置新员工的使用范围 | 两个团队用同一模板和各自的业务账号完成同类任务；已在途任务仍使用接纳时的配置。已有员工可保留原关联并另存为模板。 |
| 日常协作 | 接入三类 IM，管理群共享、触发器、人工确认、交接与投递 | 按渠道分别验证。重复事件只产生一次任务；人工答复一次有效；接手员工只读获准移交材料；投递失败后仍可下载原产物。 |

完整平台首版以「第二个团队能独立完成第一项真实任务」为闭环。观察从选模板到首个成功任务的耗时、创建后完成首个任务的员工比例、模型或插件接入导致的中断步骤，以及已完成任务的结果送达情况。AI 员工市场首版提供官方精选和工作区模板；社区公开投稿、团队间跨组织分发、付费交易和模板升级差异合并列入后续评估。

## 9. 既有员工与授权迁移

旧版能力包同时记录资源组合和授权。2026-11-16 最新决定保留员工绑定能力包及其使用范围，不再将能力包拍平为员工直接绑定资源。工作区能力包模板复制给员工，复制后独立维护；资源在包内固定版本，插件定义在统一资源库，账号在员工绑定时授权。迁移时保留原规则的**有效授权结果**。同一操作出现在多个旧包时，逐条保留每条有效授权所依赖的成员、会话、触发器或交接来源组合。例如，甲只能在一群查询、乙只能在二群查询，迁移后仍须保留这两组配对，单独合并人员名单和群名单会产生额外授权。停用项、例外和拒绝规则按原行为核对；在途任务和等待人工的任务继续引用原快照。

验收时对照同一员工、身份、来源、技能与操作的迁移前后结果，覆盖允许、拒绝和多个旧包重叠三种情况。原账号或环境的绑定归入对应插件的「接入设置」，核对执行所用身份、目标及操作权限。迁移矩阵记录各场景的实际验证状态。
