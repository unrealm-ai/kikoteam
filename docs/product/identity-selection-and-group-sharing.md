# 统一选人与跨渠道群共享

状态：2026-11-18 用户已确认的目标设计，**尚未实施**。本文不声明三类渠道的目录、选群或共享读取已经交付，也不改变现有接口及权限判断。现有飞书目录和各组件局部实现不能代表本设计已完成。

## 已确认的统一选择规则

统一选人逻辑用于员工使用范围、能力包、群共享指定人及后续人工确认。可选择 Web 工作区账号，以及飞书、钉钉、企微的联系人。员工使用范围及能力包可额外选择飞书、钉钉部门；企微不支持选部门。群共享指定人和确认人应是可核验的具体真人。统一的是选择逻辑和身份表达，不是把不同来源的人自动合并，也不意味着这些场景的业务授权规则相同。渠道联系人不要求先注册 Web 账号。

统一选群支持跨渠道选择，群共享的来源群和目标群可以来自不同渠道。不得施加“只能同渠道共享”的产品限制；某渠道暂不具备目录或读取能力，应展示具体不可用原因，而不是把跨渠道需求改成同渠道。

群共享策略和通知群目标共用统一选群逻辑与候选能力，而不是分别建设各渠道的选群页面和身份映射。统一选群通过渠道 adapter 获取候选：飞书、钉钉、企业微信分别实现其群发现、分页和覆盖范围；后续接入 Web 平台群聊时新增对应 adapter，不更改共享策略和通知的业务接口。adapter 报告来源、可用性、覆盖范围及不支持原因，不能把不同渠道的候选混成无来源群。

选人采用相同的 adapter 思路：Web 工作区账号和各渠道各自提供候选查询、身份命名空间、来源和可用性，再由统一选择器提供一致的交互。人员、部门、群分别使用类型化主体引用；是否能选、能否使用或发送仍由各业务场景按当前来源和权限分别验证，复用选人/选群不复用授权结果。各入口对允许的主体类型、访问范围和通知/共享权限可有不同约束，不以候选出现或相同名称自动授权或合并身份。

### 群候选来源与实施阶段

统一选群界面和群共享策略安排在后续阶段，与统一选人一起实施。本轮渠道迁移只建设或保留群发现的底层能力，不代表已经交付完整群列表、统一选群或群共享。

候选发现按渠道实际能力接入，统一界面需展示渠道与来源，不能把部分列表标成全部已加入群：

- **飞书**：目标是通过机器人所在群列表接口分页查询，并结合入群、退群等事件更新状态；具体以应用授权和实际接口回执为准。
- **钉钉**：从机器人收到的群内 @ 消息记录发现群，保留群 ID 和可取得的群名；仅覆盖收到过相关消息的群，不保证覆盖所有已加入群。
- **企业微信**：既可通过机器人近期群列表接口查询最近 7 天范围，也可根据定向机器人消息发现群；两种来源均不保证完整覆盖。

上述是原系统来源与 Kiko 目标接入方式，并非本轮实际线上能力承诺。群候选需绑定员工、渠道、应用/连接和可信租户范围，显示群名及来源；未能取得群名时提供可辨认的兜底。候选出现不等于可读取或可发送，仍须执行时检查绑定、授权和渠道能力。群不可用、退群、权限失效或换绑后保留策略并标明状态，不擅自映射至同名群。各渠道的群发现、列表覆盖和失效判断需分别验收。

每个人选保留工作区、Web/渠道来源、应用或绑定、租户、身份命名空间及原生标识；每个群保留相应来源、应用或绑定、租户和群标识。显示名仅用于展示，同名不表示同一身份，改名不改变身份。不能按姓名、群名或看似相同的 ID 自动关联 Web 与渠道账号，也不能把一种命名空间的 ID 当作另一种使用。具体存储字段与 API 待实施设计确定。

## 多条独立群共享策略

界面类型面向场景命名：建议将互相共享称为「项目组」，将定向共享称为「信息同步」。名称尚可调整，不构成独立授权规则；界面必须同时说明「所选群两两双向互通」或「来源→目标单向共享」，不能仅凭名称推定方向或权限。

每条策略除策略类型外，用户还可填写自定义「策略名称」以区分各条策略。策略类型（例如项目组/信息同步）对应下面明确的共享方向；自定义名称仅用于展示和辨识，不决定方向、不授予权限，也不能作为匹配身份或策略授权的依据。名称是否必填、是否要求唯一尚未确定，本设计不预设这些限制。

可配置多条独立策略，每条自行选择一种模式，不能把不同策略的人员、来源与目标名单先合并再判断：

| 模式 | 含义 | 示例（仅说明方向） |
| --- | --- | --- |
| 信息同步（建议名称；定向共享） | 明确来源群 → 目标群，目标可以在本策略允许的范围读取来源；不隐含反向授权 | 飞书 A → 钉钉 B，不因此允许 A 读取 B |
| 项目组（建议名称；互相共享） | 所选群两两双向共享；群可以来自不同渠道 | 飞书 A、钉钉 B、企业微信 C：A↔B、A↔C、B↔C |

每条共享规则也可选择「指定人」作为共享目标，使用上面的统一选人逻辑；这是独立于员工使用范围的配置，默认不向全群公开。本次设计保留此目标能力，不将共享限定为群到群，也不把员工使用名单直接当成共享接收名单。指定人目标如何与「项目组」两两双向模式组合仍待确认，不从群间方向示例推导额外授权。

保留指定人与本条策略的关系。默认不做传递闭包：一条 A→B 加另一条 B→C 不自动得到 A→C；两条互相共享策略重叠也不自动扩大为全部群互通。共享不合并 Conversation、Input 队列或 Pi 会话，也不把来源群全部内容自动复制到目标上下文；实际读取仍受授权边界约束。

## 授权、失效和审计边界

- 能选中人员或群只表示取得明确候选，不等于获得员工使用、能力调用、资料读取、对外投递或人工批准权限。各入口仍核验自己的业务权限。
- 配置保存和实际读取/投递分别校验操作者、工作区、员工、策略方向、指定人、来源与目标的真实身份、当前渠道绑定及授权状态。读取来源与向目标披露是两项校验，不因其中一项通过而跳过另一项。
- 换应用、换租户、撤权、人员离开、机器人退群或目标不可用时，不猜测替代身份、不转发到其他群、不退回管理员身份。旧选择保留可解释的失效状态；后续访问按当前权限拒绝或阻断。已经向外披露的内容不能宣称可撤回。
- 人工确认必须绑定具体问题及其版本、可信确认身份和原任务；普通消息、同名账号或其他来源的“同意”不能代替有效答复。
- 审计须能解释命中了哪条策略、哪个版本、何种方向，实际人员身份、来源与目标、当时授权结果、读取/披露范围及投递结果；受理、执行和送达状态分开记录。

## 待落地与建议

待做：统一候选查询与选择组件、三渠道联系人/群适配、身份引用与配置迁移、四处业务接入、多策略存储与授权求值、共享读取/披露路径、失效处理、审计、契约和回归验收。旧能力包只支持 Web 名单的限制仍是当前实现事实，不能因本文修改而在界面宣称已支持渠道联系人。

以下是实施建议，不是新增的用户决定：候选项展示渠道/租户以区分同名；配置页预览每条策略产生的方向边；保存使用配置版本检查并显示不可用原因；测试覆盖跨渠道同名不同人、重叠策略不串权、A→B→C 不传递、撤权及目标换绑。多策略冲突的求值细节、指定人目标与项目组双向模式的组合方式、可共享材料种类与历史范围、跨来源身份显式关联流程、群话题在共享中的粒度，仍须单独设计，不根据选择器自行推定。

## AI 员工级统一配置（最新决定，取代旧绑定级名单目标）

2026-11-18 用户明确按全新平台、全新数据库设计，本轮不考虑历史配置兼容或旧绑定名单迁移。此前为旧客户端/旧名单保留的兼容说明只描述旧实现，不再约束此目标模型；不据此授权删除现有工作区数据或直接执行数据库重建。

所有相关业务配置统一归 AI 员工级，而不是每条渠道绑定独立维护一套业务授权。使用范围、能力包范围、群共享指定人、人工确认及触发配置都使用相同的来源身份表达；按业务目的限制候选：员工使用范围只选人员或支持的部门，不选群；能力包的群聊场景、群共享和通知群各按自身用途选群；触发器授权选触发器而非人或群。不把各用途的名单合并成一个授权集合。

渠道连接设置仍独立维护各自凭据、连接状态、可信应用/租户身份和可用能力；连接配置不再作为独立业务名单的目标归属。员工级规则中的渠道选择仍精确指向可信来源，不因“统一”跨租户合并同名人员、群或相同字符串 ID。

配置项按真实能力限制：关键词触发仅向飞书与 Web 群开放；钉钉、企微不得展示为支持普通群关键词监听。选项不可用时明确原因，不能静默转成其他渠道、其他群或更宽授权。其他能力逐项按真实接入能力校验，不由渠道连接成功推断全部可用。

当前绑定级 access/trigger 字段、旧客户端兼容路径和页面仍可能处于改造中，不能把它们写作最终产品语义。员工级持久模型、契约与前端接线按新平台方案实施，验收以实际完成报告为准。

Web 群规则同时保持：群消息每群一份，各员工独立触发与授权后进入不同 Input；新加入人员和员工可看加入前群历史，退出或被移除后不能看后续，加入不要求重置已有 Pi。详见[Web 群专项](../flows/web-group-conversations.md)。
