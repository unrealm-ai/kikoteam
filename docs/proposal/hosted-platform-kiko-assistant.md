# 商业托管版 · KIKO 平台助手

状态：设计提案，尚未实现。本文不改变现有 spec、接口或部署行为。

## 1. 目标与首期范围

KIKO 助手的默认配置由代码提供，不使用员工模板。商业托管版每个新工作区创建成功后（注册自动创建或用户手动创建），异步检查发放条件；条件满足则创建一名 KIKO 助手。它解决两件事：

1. **体验员工主动完成工作**：不要求先建员工、选模型、装插件或绑定企业 IM。从客户投诉、服务告警、会议跟进中任选一个场景，点卡向普通私聊发一条预设消息，走真实的任务流程。用户可实时看处理过程、按原流程补充要求，并收到主动回告及产物。
2. **创建自己的 AI 员工**：用户通过对话提出需求，KIKO 整理配置草稿。用户确认后，在选定工作区创建能在 Web 对话的员工，随后可接入飞书或企微。也可通过同一助手修改已有员工的名称、职责、提示词和模型，并推荐可用的 Skill／MCP；能力包与渠道由用户在现有设置页独立操作。

除在市场上方增加有条件展示的引导外，不改市场原有功能、自托管默认入口、企业工作区角色；助手复用平台现有的工作区所有者（owner）扣费规则，不新增计费机制。首版不让 KIKO 代用户创建企业应用、申请租户权限或发送外部通知，不公开通用管理 MCP；工作区级工具契约为后续已认证的外部 Agent 保留接入方式。

### 五个定制点

**KIKO 助手是工作区内的普通 AI 员工，不新增员工类型。** 除下列发放、入口和两个内置能力包的定制外，名称、头像、职责、提示词、模型、员工使用范围、普通能力包、Skill／MCP、渠道绑定均按普通员工的权限和流程配置。助手初始选平台默认模型，创建后可以按普通规则更换。日常 Web 或已绑定渠道的对话、任务执行、人工确认、回告和积分扣费不另做一套。

| 定制点 | 规则 |
| --- | --- |
| 1. 平台开关与自动创建 | 平台管理增加「KIKO 助手」开关，默认关闭。商业托管版注册自动建区和用户手动建区成功后走同一个发放检查；只有开关打开且平台默认模型有效才创建。用代码默认值，不复制官方模板或 1 号员工。助手、两个能力包和工作区的 `assistant_agent_id` 一并写入；技术失败重试时重新校验，按工作区幂等。开关只管发放。 |
| 2. 助手导航 | 当前工作区的助手 ID 指向本工作区内已启用的员工，且当前用户有该员工的 Web 使用权限，才显示导航。默认本工作区有效成员全员可用。不由平台开关、能力包启停或体验完成记录控制。点击进入「对话」里的助手私聊，不发送消息。 |
| 3. 体验卡和市场入口 | 在第 2 条基础上，体验包须启用，当前用户须有体验包的 Web 私聊使用权限，且至少一个场景已上线。市场上方保留体验入口，助手空对话按首次体验规则展示卡片；有历史不覆盖。卡面、预设消息和配套样例数据由当前代码提供，不按工作区保存副本。点卡只提交一条预设消息，复用同一私聊、普通执行和回告，不改变工具授权。 |
| 4. 员工管理 MCP 身份 | Manager 从可信登录和执行上下文注入实际使用人、当前工作区，模型无须知道或传入这两个参数。只封装原页面业务，不新增管理规则；查询直接返回列表，基础配置由用户在现有表单保存，能力配置单独保存。 |
| 5. 两个内置能力包 | 发放时默认启用「AI 员工管理」（初始白名单仅工作区创建者）和「体验能力包」（默认继承员工的私聊使用范围）。两个包默认只勾选私聊，不勾选群聊和触发器；具备员工管理权限的用户可以按现有能力包规则修改使用范围。管理包私聊默认使用个人白名单，可选 Web、飞书、钉钉和企微账号；体验包私聊默认继承员工的使用范围。工作区只保存内置包标识、启停和授权，不保存工具定义。工具清单、描述及参数由当前代码解析；用户不能手工增删、复制包或改工具。限制仅针对这两个包，不影响助手的普通能力配置。 |

## 2. 用户路径

### 入口与默认页面

- 首次登录仍进入「AI 员工市场」。市场上方按展示条件放 KIKO 助手引导。若先上线创建功能，主按钮为「帮我创建员工」；至少一个体验场景端到端可用后，才把「体验 AI 员工」作为主按钮。创建入口仅在管理包启用且当前用户有权使用时展示，没有已上线且可用的操作则不展示引导卡。不自动打开助手、不自动跑体验；现有邀请链接和深链接仍落到各自页面。自托管默认不展示这套入口。
- **统一落点：现有「对话」页面里，当前用户在当前工作区与 KIKO 助手的一对一 Web 私聊。** 会话和普通员工私聊一样打开或复用，不做独立助手页、体验会话、演示中心或悬浮窗。
- **点左侧「KIKO 助手」**：入口在「AI 员工市场」下方、「AI 员工」上方，使用独立图标。点击只打开上述私聊，不发消息。已有历史时定位到最新消息；没有历史时，按展示条件显示体验场景卡或普通欢迎页。
- **点市场上方「体验 AI 员工」**：先打开场景选择，不发消息；点具体卡后打开同一条私聊，并发送一条预设消息。在助手私聊内点具体卡，留在当前页并发送同样的一条消息。不自动跳到任务详情：任务进展和回告留在私聊，用户需要时从任务入口打开详情。点「帮我创建员工」则进入同一助手对话，可跳过体验。
- 刷新保留当前页；切换工作区时加载目标工作区里当前用户的助手私聊，不携带旧工作区的对话、草稿或执行数据。

### 头像设计

下述 A 方案是新建助手的默认头像参考，作为平台内置资源提供，不覆盖用户后来选择的其他头像；换成普通头像时，导航和对话正常使用该头像，不强制套用 A 的动效。

选定[原版像素风对比图](../product/assets/kiko-assistant/avatar-original-a-reference.png)的最左列 **A**：薄荷绿块状圆脸、炭黑五官。保留原图用于核对，B、C 和后续 A1–A4 不作为开发参考。

- **导航（NAV）**：用原图首行的方眼静态头像；小尺寸仍要清楚，不随任务状态变化。
- **安静（IDLE）**：用原图中行的横眼表情；进入对话时可轻眨一次，平时静止。
- **干活（WORK）**：用原图末行的竖眼和像素点；仅在助手正在回复或当前用户在本工作区的任务实际执行时，允许轻微动效。排队和等待确认等具体阶段以任务卡为准。
- 动效只用于对话页顶部，不影响历史消息头像。遵循系统「减少动态效果」偏好：保留表情变化，关闭动画。参考图是静态设计稿，不是运行时素材或动画成品。

### 展示条件与历史

每个工作区最多记录一个助手员工 ID（工作区的 `assistant_agent_id`，或等价的一对一关联），不按员工名称、模板或列表顺序推断。导航以当前工作区的关联为准：有属于该工作区的助手、员工已启用，且登录用户通过该员工的 Web 使用范围才显示。助手默认采用普通员工的「全员」范围，即本工作区有效成员，不限于创建者；修改员工使用范围后按当前规则判断。没有管理包权限不隐藏导航。改名不丢入口；停用隐藏，重新启用后恢复原入口及获准访问的历史；删除则在同一事务清除关联，不自动补建。不能关联到其他工作区的员工。

平台发放开关只控制新建，不控制已创建助手的导航；更换平台默认模型或关闭发放也不隐藏已有入口。员工已启用但其已选模型后来不可用时，保留导航与有权读取的历史，调用沿用普通员工的错误提示，不把模型故障当成停用。市场引导还须至少有一个已上线且对当前用户可用的操作。

| 入口 | 展示条件 |
| --- | --- |
| 左侧「KIKO 助手」导航 | 当前工作区的助手存在、已启用，且用户有 Web 使用权限；不受两个能力包启停或体验完成记录影响。 |
| 「帮我创建员工」 | 助手可用、管理包启用，当前账号在该包的 Web 私聊范围内且有员工创建权限。关包不影响聊天或体验。 |
| 市场及对话里的「体验场景」入口 | 满足导航条件、体验包启用，当前账号有包的 Web 私聊使用权限，且至少一个场景已上线。关闭体验包隐藏体验入口和卡片，不影响普通聊天或管理包。 |
| 助手对话框内自动展示的场景卡 | 满足体验入口条件，并且当前工作区的助手私聊没有历史、当前账号未成功体验。已有历史则保留历史和手动入口，不自动铺卡。 |
| 市场助手引导 | 有上述可用操作之一才显示；体验可用时主按钮为「体验 AI 员工」，否则只显示可用的创建入口。体验完成不隐藏市场的体验入口；在市场点开后仍可选场景。 |


积分不足与模型未配置分开处理：积分不足不隐藏入口，用户可看历史；需要调用平台模型时，模型代理按所在工作区 owner 的余额做准入校验；余额不足则拒绝新的平台模型调用，按现有失败流程提示，不把体验标记为成功。隐藏入口不删除或改写历史。

### 场景卡与真实执行

三个场景复用同一套对话卡片和任务详情，只有通过验收的场景才展示，每张卡片只说明发生的事件和预计交付。客户投诉标为「推荐」，不替用户选择或启动。

| 场景 | 卡片文案 | 按钮 | 主能力 | 用户会拿到 |
| --- | --- | --- | --- | --- |
| 并行跟进客诉（推荐） | 一单显示签收却没收到，另一单退货已签收却没收到退款。 | 同时跟进两单 | 一次交办，多个任务并行推进 | 每单各有一条关键发现、下一步和可复制的客户回复。 |
| 会议后跟进 | 会后行动基本明确，但上线后谁看漏斗还没定。 | 开始跟进 | 先推进，缺关键信息时发起人工确认，收到答复后继续 | 确认前的行动清单、确认后的最终清单及可复制的群消息草稿。 |
| 自主恢复线上告警 | 支付成功率突然下降，看看员工能不能止损并把服务拉回正常。 | 开始恢复 | 自主完成排查、恢复、验证和回告 | 影响范围、已执行的恢复动作、恢复证据和仍需修复的问题。卡面标明演练、不操作真实线上。 |

未对话时默认把客诉排在首位，不替用户选。每张只验证一个主能力：客诉并行执行多个独立任务、会议等待人工确认后续跑、告警自主恢复并验证。后台执行和主动回告是共同底座，不额外增加操作。点击一次就开始，不先让用户编辑提示词、上传文件、选模型或连接账号。体验入口说明内置体验工具使用样例数据；若用户同时配置了真实工具，不保证该次一定使用样例，结果来源以实际命中的工具为准。客诉和会议的体验 MCP 只查样例，会议的人工确认走现有平台流程；告警恢复动作也只返回样例结果，不写外部系统。按现有平台模型计费规则提示。

**体验卡只是普通输入的快捷入口。** 点击后在同一助手 Web 私聊提交一条自然的用户消息，模型可见文字不出现「体验」「模拟」或专用指令，继续使用既有主对话和任务流程。不会额外建会话、贴执行标签、更换工具集或预设下一步。真实的任务状态、回告和产物照旧。

**工具按员工当前配置走。** 执行侧体验包中的 MCP 对模型声明正常业务名称和说明（如 `get_order`），与普通工具一样由既有规则按轮次和权限解析。开启体验包时，后续正常问订单同样可以命中它，不要求由卡片触发；关闭体验包、配好同类真实 MCP 后，走真实 MCP。二者并存不做体验卡优先或自动切换，沿用现有工具选择规则，不扩大任何权限。三个场景的体验 MCP 都无状态：不新增状态表、不写样例文件、不在内存或缓存记录处理进度、确认答复或工具调用次数。查询只按显式参数从代码内置样例取数据；任务进度、人工确认和工具结果仍由平台原有流程管理。体验工具没有真实凭据或外部请求。告警恢复工具只返回一次模拟操作的回执，不修改样例文件、不持久化任务状态，也不写真实系统。用户界面可用工具来源标识说明实际命中的是内置样例还是已连接资源，不能按是否点击过卡片来推断。体验包关闭后隐藏对应入口。

**卡面和样例统一由代码提供。** 每个场景用稳定标识关联标题、说明、按钮文案、样例输入和配套样例数据。市场与对话复用同一套场景定义，不给工作区或助手保存卡片副本。随代码发布更新，已有助手也读取新版；卡面与提交的样例输入来自同一套定义。历史里已发送的消息、任务和产物不改写。

三张体验卡默认走一对一私聊；群聊消息是可查询的样例资料，不因修改包的使用范围而增加真实群监听或发群消息的演示工具。主对话不新增工具，模拟 MCP 在执行 Agent。

### 三套样例输入（v1）

样例与任务约束作为版本化 fixture 提供。用户可展开「样例材料」看原始证据；预期结论和验收口径只给测试，不喂给模型。样例统一使用合成数据，不含真实订单、日志、成员身份或链接。下面的日期和时间是样例业务时间，不依赖用户点击当天；同一私聊可反复使用；工具数据来自代码维护的样例，不根据历史猜测业务事实。

| 场景 | 模型初始收到 | 可调用的内置样例工具 | 暴露证据的时机 |
| --- | --- | --- | --- |
| 客诉 | 一条消息内的两起投诉、各自订单号及交付目标 | `get_order`（订单和售后规则）、`get_delivery_evidence`（物流、签收及核查记录）、`get_support_thread`（既往客服对话与承诺） | 只返回截至样例投诉时的证据与客服历史。 |
| 会议 | 会议结束事件、样例会议标识与交付目标 | `get_meeting_notes`（讨论、承诺与决议）、`get_release_plan`（里程碑和依赖）、`list_project_chat`（会后群聊片段与消息时间） | 始终返回固定原计划和会后群聊，不写值守人。确认答复从现有任务上下文读取，不回写样例，也不新增体验 MCP 工具。 |
| 告警 | 支付告警、样例事件标识和恢复目标 | `get_payment_metrics`（成功率和分组）、`get_release_evidence`（灰度、日志和恢复规则）、`get_incident_timeline`（值班记录和处置记录）、`rollback_release`（只回滚指定样例发布） | 不传回执返回告警指标；传入本任务的有效回滚回执才返回对应的回滚后观测窗口。 |

工具名是设计暂定名，模型看到的是正常业务查询或受限恢复操作；实现只访问本地样例，不调用真实业务接口。模拟群聊只读当前场景预置的一个样例群，按已发生事件和消息时间返回短片段；没有真实群 ID、历史搜索、发消息、@ 或加入群的入口。样例段落中列出的订单、会议和告警证据是工具响应的来源，不是初始提示词；预期结果仍只作验收。

#### A. 并行跟进客诉：两单同时查，各自回报

卡片点一次，在助手私聊发送下面**一条普通用户消息**。主对话沿用现有任务工具，为每笔订单各创建一个独立执行任务，不在卡片处理层批量创建、不等第一单查完才提交第二单。任务标题可包含订单号，任务进度和结果按现有流程在同一私聊中分别展示和回告；先完成的那单先回，不必等另一单。

> 有两起客诉，帮我拆成两件事同时查，哪件先查清就先告诉我。
>
> 1. ORD-1042：显示前台签收，但一号楼前台没找到，客户今晚要用。
> 2. ORD-1087：退货昨天已签收，客户今天还没收到退款，想知道卡在哪。
>
> 每单给我最关键的发现、建议下一步和一段可复制给客户的回复。先别实际发消息或退款。

| 样例 | 工具返回的证据（不随首条消息发送） | 该单验收 |

#### B. 会议后跟进：先整理，确认关键缺口后继续

- **触发事件**：「新人引导改版会（MEET-301）刚结束，帮我先整理确认过的行动和风险。最终清单要写明上线后谁看漏斗；要是没有定，就先请人确认，收到答复后再交付清单和群消息草稿。别直接发群。」
- **样例会议**：周三 14:00，目标是周五 17:00 小流量上线。阿岚：「周四 12:00 前交三个页面的最终文案。」小程：「收到文案后接入，周四 18:00 前给预览。」晓宁：「周五 12:00 前跑完 iOS、安卓验收，前提是周四晚交付的预览可用。」主持人总结：「周五 15:00 看验收决定上不上；没通过就继续走旧流程。」

- **容易误读的两条**：阿岚提议「欢迎邮件也顺便改吧」，主持人明确「下期再做」。数据同学说「上线后得看漏斗」，参会人没有认领，也没有定截止时间。

- **验收**：答复前不编造值守人、不假装已完成；答复后在同一个任务中使用真人填写的名字，不回写会议纪要、群记录或样例工具。空答复或没找到可用确认人时，按现有流程说明缺口，不编负责人。重新体验仍查到固定的未认领记录。最终清单不把欢迎邮件列入本期，不写成「已批准上线」，也不把安卓未就绪当作验收失败。

#### C. 自主恢复线上告警：定位问题、回滚止损、验证恢复

- **首条样例输入**：「10:05，支付成功率告警（INC-207）。帮我查清影响并恢复服务，确认指标回稳后告诉我做了什么、还有什么没解决。只处理这条告警关联的验证环境，不操作其他环境。」不给排查步骤、目标版本或恢复结论。
- **初始证据**：09:55–10:00，总成功率 99%；10:00–10:05，总成功率 90.6%，失败主要集中在安卓 20% 灰度：240 次尝试中 174 次失败，非灰度组 960 次中 6 次失败；iOS 仍为 99%。10:00 刚启用安卓签名 v3，失败日志指向时间戳单位不符合预期。把日志写成首要线索，不声称已复现或修好代码。
- **恢复动作**：样例值班手册预授权把 INC-207 关联的安卓签名 v3 灰度回滚到上一个健康版本；在这个明确范围内不再找人确认。助手自行判断并调用恢复工具。服务端只接受样例注册的告警和发布标识，不接受真实环境、任意 URL 或命令，不持有生产凭据。工具按固定样例返回操作结果；成功时返回绑定当前任务、告警及发布版本的可校验 `rollback_receipt`。回执由工具自身生成并可无状态验证，不新建状态表、缓存或进程内状态；重复调用按同样条件得到同样结果。模型通过已有的任务工具结果记住回执，不自行填「已回滚」。
- **验证恢复**：操作回执只证明回滚已提交或已生效，不等于服务已恢复。助手须调用 `get_payment_metrics(incident_id, rollback_receipt?)` 再查监控：不传回执返回初始告警指标；回执无效或不属于本任务则拒绝，不返回恢复指标；传入有效回执后，按样例返回回滚后的观测结果。若时间线要展示回滚记录，也由回执推导。成功样例返回两个不同的 5 分钟窗口（1.6% 和 1.1%）；两窗均低于 2% 才算恢复，不需真实等待十分钟，重复查询也不会推动样例进度。未回稳、无法验证或操作失败时，准确说明已做到哪一步、下一步要谁介入，不宣称成功，不擅自扩大处置范围。
- **交付和验收**：能在任务时间线上看到诊断、真实调用内置恢复工具、回读指标、最终回告。回告区分「通过回滚恢复服务」和「签名代码仍待修复」，给出后续修正及重新灰度前的验证建议。另测回滚失败和动作成功但指标未回稳，两种都不得回告已恢复。验收无回执、有效回执、非法回执及跨任务复用；新建体验不继承旧回执，仍查到初始告警。体验展示清楚标为样例环境，真实生产接入及授权不在首期范围。

#### 体验质量验收

- **先交付能确定的部分。** 客诉和告警不要求用户补输入；会议先整理已有信息，只在缺少最终清单所需的值守人时走正式确认流程，不在 MCP 内等人。
- **回告先说发现，再给可用产物。** 回告至少包含一个本场景独有的具体事实，不只说「已处理，见附件」；用户能直接预览或复制。体验成功以结果已可在发起者的 Web 对话打开为准。
- **先验证客诉。** 用新人视角实际点击，记录点击到首条真实进展、首单可打开结果和两单全部交付的时间，以及结果后的追问、复制或创建入口使用情况；不把点击本身当作体验成功。先测首轮产物质量和真实状态链路，再开启其他卡片。
- **各卡主验收。** 客诉从同一输入拆成两个独立任务，验证执行有重叠、逐单回告并各自提供可用回复草稿；会议实际发出提交卡，收到答复后在原任务续跑；告警必须实际执行样例恢复动作、回读指标并证明恢复，不能只给诊断建议。主动回告与补充信息沿用默认能力。客诉和告警不需二次操作；会议的确认是该场景本身的验收项，不另建体验交互机制。
- **多来源核对。** 不以调用次数作为质量指标；要能用会后群聊补充会议计划，用历史会话避免让客户重复排查，用值班记录区分有人提议与已经执行。初始样例不包含触发时刻之后的证据；告警恢复后的指标由有效回滚回执选择样例分支，不靠保存状态或累计查询次数。
- **跨场景与权限回归。** 同一账号先试客诉再试告警，不能混用地址或数据；同一私聊先开启体验包、再关闭并接入真实 MCP，后续任务必须反映员工当前包权限；工具返回样例时向用户标明来源；分别用工作区创建者和普通成员验收。未授权的创建入口不出现，体验仍可用；免费赠送或平台积分口径不因样例变更。

### 首次体验与工作区切换

- **体验完成按平台账号记录。** 有权使用助手的不同成员各自记录体验进度，A 完成不影响 B；记录不授予助手或管理工具的使用权。同一账号尚未完成体验时，切到另一个有助手入口的工作区仍可体验。
- **首次成功交付才算完成。** 单纯打开页面、点击按钮、受理、执行失败或取消，不改变完成标记。以服务端确认该场景所需任务全部成功且结果能在发起者的 Web 对话中打开为准（客诉卡是两单），不以设备本地状态或是否打开产物为准。如需关联卡片来源与任务结果，仅在服务端记录体验完成所需的来源，不写入模型输入，不参与工具选择、任务权限或执行分流。
- **对话按账号和工作区隔离。** 再进助手优先显示该工作区的历史；无历史且未成功体验时显示已上线的场景卡，无历史但已在别处体验时显示普通欢迎页。若已有历史、但还没有成功体验，保留明显的场景入口，不覆盖历史。体验入口和体验卡分开：助手和体验包均可用时，顶部「体验场景」入口常驻；体验卡不常驻。首次体验成功后，卡片不再自动占用对话首屏，切换工作区也不重新铺卡。用户主动点「体验场景」时，仍可打开全部已上线的场景卡并重新体验。

### 对话创建与修改员工

用户可直接说「建个售后跟进员，整理投诉并生成处理建议」。助手拟定名称、头像、职责、提示词和模型，预填现有员工创建／修改表单。用户核对改动后点一次原有「创建员工／保存配置」。表单中的未保存配置是页面状态，不新增后端草稿、发布、审批或组合提交。普通页面的手工编辑和全部既有 API 保持不变。

Skill 和 MCP 由助手调用资源查询工具获取当前账号有权使用的选项，不需要用户先打开资源库。模型可按需求自行选出推荐项，也可列出几个选项让用户选；推荐不是安装。基础配置保存后，要增删或调整能力包、Skill 或 MCP，由用户在现有能力包页面单独操作，沿用原保存接口。飞书／企微继续在现有渠道设置页接入，不提供新的管理 MCP 工具。不得读取或回显密钥。

## 3. 平台设置与助手创建

### 发放开关与默认配置

「设置 → 平台管理」增加 **KIKO 助手**开关，**默认关闭**，部署升级不自动打开。商业托管版在开关已开启且有已启用、通过校验的平台默认模型时，才为新创建的工作区自动发放助手。注册自动创建的默认个人工作区和用户手动创建的工作区采用同一判断；缺任一条件，工作区照常创建。不回退到工作区模型。自托管不自动发放。没有模板选择、发布版本或 1 号员工的前置条件，也不对任何已有员工自动挂载内置包。

名称、头像、描述、职责和提示词是代码内置默认值；用现有普通员工创建规则初始化，引用平台模型，不复制任何已有员工、官方模板、运营资源、凭据、渠道绑定或历史。助手沿用通用员工创建默认值：普通使用范围为「全员」（本工作区有效成员），默认确认人是该员工创建人的 Web 账号。自动发放的助手由工作区创建者创建，因此确认人初始为该创建者，不另设体验确认规则。管理包白名单独立初始化，默认仅工作区创建者。后续按普通员工规则编辑、停用或调整范围；付款人按第 5 节判断，不从员工创建者或确认人推导。修改代码中的默认值只影响之后创建的助手，不覆盖已有实例或用户设置。

### 工作区创建与异步发放

- 注册仍一次性提交账号、默认工作区和钱包；手动建区沿用原事务。两条路径都在工作区创建成功后进入同一异步发放流程，读取当前平台开关和平台默认模型。条件满足就创建，缺任一条件则跳过；助手发放失败不回滚注册或工作区创建，也不对存量工作区静默补发。幂等键是工作区 ID，不是账号 ID；同一个人新建多个满足条件的工作区，每个工作区分别发放。
- 发放因技术问题失败才重试；每次重试重新校验当前平台开关和默认模型可用性。重试不是绕过门槛，也不是在页面另起一条创建链路。
- 发放以工作区为幂等边界：普通员工创建、两套能力包初始化、保存助手员工 ID 和标记发放成功在同一事务完成；重复消费返回原结果。未发放成功前没有可点击的助手入口。员工删除后，发放成功记录不重置，不自动创建替代员工。

## 4. 身份、会话与工具

助手会话按账号、当前工作区和员工实例隔离；切换工作区不继承旧会话或草稿授权。新建员工有自己的实例和配置，不共享助手会话、运行凭据或权限。

### 内部能力包与外部扩展

- **内部：`backend/internal/manager/mcp/platform`。** 首期把「AI 员工管理」注册为平台内置能力包，只在自动创建的 KIKO 助手上初始化并展示该包，不上插件市场，也不自动给其他员工挂载。包默认启用，初始私聊白名单仅本工作区创建者的 Web 账号；私聊名单支持 Web、飞书、钉钉及企微个人，不接受部门、群或继承加黑名单。其他场景范围见下表。以后确有复用需求，再评估向其他员工开放显式挂载。
- **执行侧体验包：`backend/internal/manager/mcp/demo`。** 与员工管理 MCP（`backend/internal/manager/mcp/platform`）分开实现。同一助手默认初始化一套「体验能力包」，默认继承员工的私聊使用范围，Web、飞书、钉钉和企微私聊均可使用。IM 无需新增卡片，按自然语言在普通私聊触发，使用对应渠道的原有回告流程；不改变 Web 体验卡位置或首次完成标记。和普通能力包一样按执行轮次取当前有效工具，不看输入是否来自体验卡；群聊、定时和 Webhook 默认不勾选，可按现有能力包规则打开；不新增独立的交接入口。
- **两套内置包都只开放启停和使用范围。** 所有工作区（含平台运营工作区）规则一致。有员工管理权限的人可启停及调整本工作区内谁可使用；不能手工增删或复制这两套包、增删替换包内 MCP，或修改内置标识和版本。能力包身份由服务端内置标识判断，不按名称识别；工作区配置只记包的稳定标识、启停和授权范围，不复制工具定义。前端展示工具清单（只读）及两项可编辑配置，后端同样拒绝越界更新。使用范围只能收窄员工使用权，不授予工作区管理角色，也不允许跨工作区；每次调用按本轮实际的已验证身份校验目标员工权限。员工的其他能力包、Skill、MCP 和渠道照常配置。停用此包不等于停用助手。
- **两个内置包的工具定义从代码动态解析。** 配置页展示和运行时注入使用各自包在服务端注册的同一份定义，包括工具清单、工具名称、描述和参数 schema。平台更新代码后，已有和新建助手的后续工具解析都用当前定义，不逐个更新工作区或复制工具版本，不重置各工作区已配置的启停和授权，也不覆盖员工自己的名称、头像、模型等普通配置。运行中的轮次沿用现有工具快照，不热改已下发的 schema；代码升级须兼容仍可能收到的旧调用，不能靠保留工作区副本实现兼容。新增工具仍须通过现有身份、资源与操作权限检查，紧急撤权按实际调用校验生效。
- **外部：`backend/internal/webgw/mcp`（GW/MCP，后续开放）。** 单独定义对外鉴权、授权范围、工具参数和错误适配；通过 KIKO 平台账号授权并显式指定目标工作区。内部短时委派凭证和外部 OAuth 凭证不能互用。不因为内部工具可用而开放公网接口。
- **共用业务层。** 两个入口各自把可信身份和入参转换成同一套业务请求，复用页面已有的员工查找、配置读取、资源选项和员工创建／编辑业务能力，不另建草稿或保存业务。不相互转发 HTTP，不复制授权、校验和写入规则。内外可有不同的 MCP schema，不把外部鉴权参数塞进内部工具。

管理 MCP 有两道独立的授权。先验当前助手及管理包：员工启用、当前来源和主体有权使用助手，且通过管理包对应场景的授权（默认仅私聊白名单）；再验本次操作：Manager 从可信的 Web 登录或渠道入站上下文注入工作区、真实主体和会话来源，现有员工业务服务按目标员工进行判断。包授权本身不授予员工管理权，也不把助手创建人、工作区 owner、平台管理员或付款人的身份借给调用者。模型参数不含工作区、调用人或权限角色。

- **更新目标员工**：只接受同工作区目标。工作区 owner/admin、仍有资格的员工创建人，或目标员工的显式维护人可更新；不是任一角色时返回 `employee_management_forbidden`，对用户提示「你没有修改这位 AI 员工的权限，请联系管理员」。平台管理员身份不会单独绕过工作区隔离；只有按通用员工业务规则本来就有该工作区权限时才可操作。创建人和工作区管理员直接按规则授权，不写进维护人名单。
- **创建员工**：沿用通用员工创建规则（有效工作区成员可创建，默认工作区全员可用）。渠道要创建，必须能解析出该工作区的真实有效平台成员，以便明确记录创建者和默认 Web 确认人；无法确认时提示到 Web 完成，不代填系统账号。更新则可以使用目标员工明确授予的已验证渠道维护人身份，不要求把渠道身份猜成 Web 账号。
- **渠道身份**：只使用平台已校验的 Web 成员，或当前渠道工作区范围内的已验证个人身份；以提供方、租户、绑定及其身份代次和用户 ID 按该渠道规则校验，企微用已核验的回调身份。不同机器人的 ID 不可直接等同；没有可信关联就拒绝，不按显示名、邮箱或模型自报的身份匹配。 **两机器人验收**：目标员工 E 的选人引用属于 E 的机器人绑定，而 KIKO 助手 H 的私聊主体属于 H；例如飞书两个应用的 OpenID 不能直接比较。只有双方可获得并验证同一租户下可比的 User ID、适用范围内的 Union ID，或已有的显式核验关联时才允许跨绑定操作；缺证据时不放行。绑定失效、账号离开或被撤权后，旧上下文、旧建议不能继续操作。绑定渠道本身不会开放管理包。

### 内置能力包授权范围

| 范围 | 员工管理包 | 体验包 |
| --- | --- | --- |
| 私聊 | 固定个人白名单，默认仅工作区创建者的 Web 账号。可用统一选人添加 Web、飞书、钉钉、企微个人账号；不支持部门、群、继承使用范围或黑名单。空名单即无人可用。 | 默认继承员工的私聊使用范围（含已接入且获准使用的 Web、飞书、钉钉和企微），可按现有范围规则收窄。 |
| 群聊 | 默认不勾选。可按现有群聊范围规则开启。 | 同左。 |
| 触发器（定时、Webhook） | 默认不勾选。可按现有触发器授权规则开启。 | 同左。 |

**勾选场景不等于授予操作权限。** 群聊打开后，管理工具按本轮已验证的实际发起人校验；主动触发时只承认可信执行上下文中经授权且可重新验证的主体。没有合格主体、而操作要求真人身份时不执行，不借用机器人、工作区 owner 或配置人的身份；不向未获授权的群受众回显员工私有配置。体验包即使启用其他场景，仍只访问样例，回告按现有渠道规则投递。

工作区不复制内置工具定义。配置保存时校验人选归属与种类，调用时重验包和目标权限。**管理包白名单与任一员工维护人白名单独立**，分别由各自配置管理，互不自动同步。助手导航、Web 市场引导和体验卡的条件不因新增渠道授权而改变。

### 内部 MCP：封装现有员工页面能力

目标是封装现有页面能力，不增加独立管理规则。覆盖「创建员工」和「修改员工配置」两条流程。内部工具不查询、枚举或切换工作区，也不在任何工具参数中暴露 `workspace_id` 或调用人 ID；Manager 在起始请求中把实际登录人或已验证渠道主体与来源工作区绑定到已认证执行上下文，并在每次调用重新校验。工具只接受目标员工 ID 或资源筛选等业务参数。

| 工具（名称待接口评审） | 参数 | 返回或行为 |
| --- | --- | --- |
| `list_employees` | `query?, cursor?` | 搜索当前工作区内有权查看的员工，返回 ID、名称及是否可管理；有同名时由用户确认目标。 |
| `get_employee_setup` | `employee_id` | 返回授权可见的现有配置、配置版本及模型、Skill、MCP 引用；不返回密钥。 |
| `list_employee_setup_options` | `kind, query?, cursor?` | 按模型、Skill 或 MCP 查询当前工作区可选项、默认项和可用性，不返回密钥。 |
| 创建员工 | 现有表单基础字段 | 复用现有创建业务，只由用户点击当前 Web 表单的创建操作提交，不给模型直接写入。 |
| 修改员工 | 员工 ID、现有配置版本及基础字段 | 复用现有更新业务。Web 保留本人点击保存；渠道私聊可在用户明确要求修改、已确认不含歧义的字段后，用实际渠道主体调用同一更新业务。不得更新其他工作区或绕过版本校验。 |

前三项为只读工具。Web 的创建／修改仍走既有表单。渠道首期设计只开放经目标鉴权的基础配置修改，不追加草稿存储和模型代确认；创建引导到 Web 完成。后续可开放给目标员工添加工作区共享 Skill 等配置操作，仍用同一目标鉴权和资源授权，只选共享池，不新增资源发布、更改凭据或后台账号绑定权限。助手可直接用资源查询结果作推荐，无须引导用户先跳资源库。能力包、Skill／MCP 绑定和渠道仍由原页面单独保存。

### 外部 GW/MCP：显式选区，后续开放

- `list_workspaces(cursor?)` 仅返回账号当前有权访问且外部授权覆盖的工作区，返回名称、ID、角色和是否具备员工管理权限。该工具只读，不改变平台默认工作区或 Web 选区。
- 外部 Agent 让用户选定目标，再在每次员工工具调用中显式传入 `workspace_id`。缺失就提示选择，不默认选个人工作区或第一个工作区；不提供会改变全局状态的「切换工作区」工具。后端逐次复核有效成员关系、授信范围、操作权限及资源归属，能列出 ID 不代表有权写入。
- 后续通过平台账号的远程 MCP OAuth 授权。外部工具和认证参数独立，不进内部模型契约；现有第三方登录只用于识别平台账号。内外复用业务服务，外部是否开放最终提交及对应的本人确认另行评审。

助手在查资料或预填时应核验当前员工管理包的开关和成员范围；入口拿不到最新授权就不再应用已有建议。实际保存（Web 或内部 MCP 的受权渠道更新）复用现有员工业务服务进行主体、目标、资源、模型和配置版本校验；记录真实来源、主体和目标，不额外引入草稿令牌或第二套更新规则。

## 5. 模型与计费

| 对象 | 模型选择 | 计费边界 |
| --- | --- | --- |
| KIKO 助手及其演示任务 | 初始化时引用平台默认模型，用户之后可按现有规则换模型 | 使用平台模型时扣助手所在工作区 owner 的积分，不按发起体验或发消息的人扣；换用自备模型后不扣平台积分。 |
| 用户新建的其他 AI 员工 | 页面与助手共用规则：优先预选目标工作区可用的默认模型，没有再预选平台默认模型；显式选择的可用模型优先 | 使用平台模型扣新员工所在工作区 owner 的积分；工作区自备模型不扣平台积分。 |

**助手不新增计费逻辑。** 沿用现有员工模型凭据、工作区 owner 的账号钱包、余额准入和实际用量结算；对话、演示、任务、重试和主动回告中发生的平台模型调用按同一规则结算，不引入按使用者扣费、平台代付或独立团队钱包。体验入口说明费用由工作区 owner 承担，不因此向其他成员显示其余额或账单。积分不足不影响查看原本有权限的历史和产物。普通员工旧 Key 的绑定切换由平台扣费迁移负责，助手无需额外迁移。

默认模型顺序只在创建时生效；保存具体模型引用，默认项后续变化不替换已有员工，也不在执行时自动回退。没有可用默认模型时提示选其他有权使用的模型或先完成配置。

## 6. 开发顺序与验收

1. **内置配置、发放和导航**：验证开关默认关闭、显式关闭、缺可用平台默认模型都不创建助手，注册和手动建区照常；两种建区入口复用同一工作区级异步发放检查；不依赖模板或已有员工。覆盖异步重试与并发发放，工作区内仅一份助手关联。验证改名入口不丢、停用隐藏、重新启用恢复、删除清除关联且不补建；平台开关关闭不误隐藏已创建且启用的助手，验证有效成员默认能看助手和体验、默认只有创建者能用管理包；不向无权用户或其他工作区暴露入口。导航和现有「对话」入口应打开同一条助手私聊，点击导航不发消息。用 owner、非 owner 管理员和普通成员验证：助手体验及普通员工的平台模型调用只扣所在工作区 owner 的积分；自备模型不扣平台积分；默认确认人仍是员工创建人的 Web 账号，与付款人独立。
2. **创建／编辑和 Web 闭环**：验证内部员工管理 MCP 复用页面查询及鉴权、不把调用人或工作区作为模型参数；助手预填后用现有表单保存基础配置，能力包在原页面单独保存，旧 API 不变。覆盖版本冲突、管理包撤权和工作区切换。两套内置包只在自动创建的助手上展示；管理包默认仅创建者，体验包默认继承员工私聊使用范围，各自停用只影响相应入口和能力，前后端均禁止手工增删、复制或修改两个内置包的工具清单；验证管理包接受四端个人白名单但拒绝部门与跨工作区授权，两包默认只有私聊，群聊和触发器默认不勾选；可以分别启用且沿用既有范围校验，关掉后不再可用；管理工具不接受无可信主体的触发任务代真人改配置；仅有管理包授权、没有目标员工管理权时不改配置；覆盖已验证渠道维护人更新成功、撤权/换绑即时拒绝、Web 授权不能自动用于 IM，普通员工及普通能力包不受影响。本阶段只展示可用的创建入口。回归验证在不重建助手、不修改工作区配置的情况下，代码变更后已有助手的配置页和新运行读取同一份最新工具清单、描述和参数定义，原有启停和授权保持不变。
3. **同会话体验**：优先跑通客户投诉的「卡片提交一条样例消息 → 主对话新建两个客诉任务 → 并行查证 → 原私聊分别回告和交付」，通过后才启用体验主按钮；另两个场景各自通过实际调用内置样例工具的验收后上线。覆盖体验与真实任务共享同一私聊、按现有规则由每轮有效能力包决定工具、主对话任务工具契约不变、市场场景卡与对话场景卡均在同一助手私聊只发送一条普通输入且不自动跳任务详情、关闭体验包后可由已配置的真实工具处理下一次请求、失败不记完成。验证仅有体验包权限但无员工使用权限时，市场和对话均不显示体验入口，直接请求也不能启动；体验成功后空对话不再自动铺卡，市场和手动入口仍可用。验证代码更新后已有助手的市场和对话展示新版卡面，点击发送与之对应的新版样例输入，旧消息不改写。
4. **渠道续接**：结果页跳现有渠道设置，用户在该页本人授权，不新增 MCP。取消扫码、缺权或连接失败不影响 Web。外部 MCP 单独评审认证及开放范围。

首体验观测：各场景选择率、首次开始体验到拿到真实产物的耗时与完成率、体验后继续在同一会话布置日常任务的比例、草稿到创建完成的比例。统计不采集工作内容、附件正文或认证材料。
