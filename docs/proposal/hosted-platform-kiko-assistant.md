# 商业托管版 · KIKO 平台助手

状态：设计提案，尚未实现。本文不改变现有 spec、接口或部署行为。

## 1. 目标与首期范围

KIKO 助手的默认配置由代码提供，不使用员工模板。每个新工作区创建成功后（注册自动创建或用户手动创建），异步发放一名 KIKO 助手，不要求已配置模型，也不补建存量工作区。它解决两件事：

1. **体验员工主动完成工作**：不要求先建员工、选模型、装插件或绑定企业 IM。从客户投诉、服务告警、会议跟进中任选一个场景，点卡向普通私聊发一条预设消息，走真实的任务流程。用户可实时看处理过程、按原流程补充要求，并收到主动回告及产物。
2. **创建自己的 AI 员工**：用户通过对话提出需求，KIKO 根据明确的 Web 请求在当前工作区创建员工。也可按权限修改已有员工的基础配置、模型及已有能力包的共享 Skill／MCP 挂载；渠道仍由用户在现有设置页操作。

除在市场上方增加有条件展示的引导外，不改市场原有功能、自托管默认入口、企业工作区角色；助手复用平台现有的工作区所有者（owner）扣费规则，不新增计费机制。首版不让 KIKO 代用户创建企业应用、申请租户权限或发送外部通知，不公开通用管理 MCP；工作区级工具契约为后续已认证的外部 Agent 保留接入方式。

### 五个定制点

**KIKO 助手是工作区内的普通 AI 员工，不新增员工类型。** 除下列发放、入口和一个内置体验能力包的定制外，名称、职责、提示词、模型、员工使用范围、普通能力包、Skill／MCP、渠道绑定均按普通员工的权限和流程配置。未显式选择模型的助手发送时优先使用可用的工作区默认模型，其次使用平台默认模型；之后也可显式绑定模型。日常 Web 或已绑定渠道的对话、任务执行、人工确认、回告和积分扣费不另做一套。

| 定制点 | 规则 |
| --- | --- |
| 1. 自动创建 | 注册自动建区和手动建区都自动入队，不检查平台开关或模型；旧工作区不补建。用代码默认值，不复制官方模板或 1 号员工。助手、能力包和工作区的 `assistant_agent_id` 一并写入；技术失败按工作区幂等重试。 |
| 2. 助手导航 | 当前工作区的助手 ID 指向本工作区内已启用的员工，且当前用户有该员工的 Web 使用权限，才显示导航。默认本工作区有效成员全员可用。不由模型、能力包启停或体验完成记录控制。点击进入「对话」里的助手私聊，不发送消息。 |
| 3. 体验卡和市场入口 | 只有助手导航可用、体验包已启用、当前 Web 登录用户有该包的 Web 私聊使用权限，且至少一个场景已上线，才显示体验入口。群聊及触发器权限不参与判断。市场上方保留体验入口，助手空对话按首次体验规则展示卡片；有历史不覆盖。卡面、预设消息和配套样例数据由当前代码提供，不按工作区保存副本。点卡只提交一条预设消息，复用同一私聊、普通执行和回告，不改变工具授权。 |
| 4. 员工管理 MCP 身份 | Manager 从可信登录和执行上下文注入实际使用人、当前工作区，模型无须知道或传入这两个参数。只封装原页面业务，不新增管理规则；查询直接返回列表，基础配置和能力包按现有页面的保存粒度分别更新。 |
| 5. 内置体验能力包 | 发放时默认启用，私聊默认继承员工使用范围，群聊及触发器默认不启用。工作区不保存工具定义；管理工具独立内置，不是能力包。 |

## 2. 用户路径

### 入口与默认页面

- 首次登录仍进入「AI 员工市场」。市场上方按展示条件放 KIKO 助手引导。若先上线创建功能，主按钮为「帮我创建员工」；至少一个体验场景端到端可用后，才把「体验 AI 员工」作为主按钮。若展示创建入口，按助手可用和 Web 员工创建权限判断，没有已上线且可用的操作则不展示引导卡。不自动打开助手、不自动跑体验；现有邀请链接和深链接仍落到各自页面。自托管默认不展示这套入口。
- **统一落点：现有「对话」页面里，当前用户在当前工作区与 KIKO 助手的一对一 Web 私聊。** 会话和普通员工私聊一样打开或复用，不做独立助手页、体验会话、演示中心或悬浮窗。
- **点左侧「KIKO 助手」**：入口在「AI 员工市场」下方、「AI 员工」上方，使用独立图标。点击只打开上述私聊，不发消息。已有历史时定位到最新消息；没有历史时，按展示条件显示体验场景卡或普通欢迎页。
- **点市场上方「体验 AI 员工」**：先打开场景选择，不发消息；点具体卡后打开同一条私聊，并发送一条预设消息。在助手私聊内点具体卡，留在当前页并发送同样的一条消息。不自动跳到任务详情：任务进展和回告留在私聊，用户需要时从任务入口打开详情。点「帮我创建员工」则进入同一助手对话，可跳过体验。
- 刷新保留当前页；切换工作区时加载目标工作区里当前用户的助手私聊，不携带旧工作区的对话、草稿或执行数据。

### 头像设计

助手固定使用「方案 4：新像素 LED 点阵精灵」的薄荷绿头像。由工作区记录的助手 ID 识别，不依赖员工名称或用户设置。员工页不显示更换入口；后端写接口不允许更换，员工管理 MCP 不提供头像参数或返回值。已有助手和新助手统一使用该头像，不需要迁移员工数据；普通员工不变。

- **导航（NAV）**：右上角保持方眼静态图，不随状态变化。
- **安静（IDLE）**：私聊顶部显示横眼表情。
- **干活（WORK）**：发送、助手主对话执行中或当前私聊有任务正在执行／停止中时，显示竖眼和像素点。仅在忙闲切换时播放一次短动效，不循环；等待人工确认不算执行中。开启系统「减少动态效果」时只换表情，不播放动画。

### 展示条件与历史

每个工作区最多记录一个助手员工 ID（工作区的 `assistant_agent_id`，或等价的一对一关联），不按员工名称、模板或列表顺序推断。导航以当前工作区的关联为准：有属于该工作区的助手、员工已启用，且登录用户通过该员工的 Web 使用范围才显示。助手默认采用普通员工的「全员」范围，即本工作区有效成员，不限于创建者；修改员工使用范围后按当前规则判断。不按目标员工管理权限隐藏导航。改名不丢入口；停用隐藏，重新启用后恢复原入口及获准访问的历史；删除则在同一事务清除关联，不自动补建。不能关联到其他工作区的员工。

模型不控制入口。助手已启用且当前用户有使用权时仍显示导航、市场引导、员工卡片和获授权的体验卡。尝试发消息或点击体验时，若无可用模型，后端不接收输入；Web 以固定配置提示卡替代当前体验卡，允许管理员跳到工作区共享模型池，普通成员联系管理员。配置后返回，体验卡重新按原权限展示，不自动重发，也不计为体验完成。

| 入口 | 展示条件 |
| --- | --- |
| 左侧「KIKO 助手」导航 | 当前工作区的助手存在、已启用，且用户有 Web 使用权限；不受体验能力包启停或体验完成记录影响。 |
| 「帮我创建员工」 | 助手可用，且当前 Web 账号有员工创建权限。 |
| 市场及对话里的「体验场景」入口 | 满足助手导航条件、体验包启用、当前 Web 登录账号有包的 Web 私聊使用权限，且至少一个场景已上线。仅有群聊、触发器或其他渠道的私聊权限不显示 Web 体验入口和卡片；这些场景的开启或关闭不改变 Web 展示。关闭体验包或撤掉该用户的 Web 私聊包权限后隐藏入口和卡片，不影响普通聊天或内置管理工具。 |
| 助手对话框内自动展示的场景卡 | 满足体验入口条件，并且当前工作区的助手私聊没有历史、当前账号未成功体验。已有历史则保留历史和手动入口，不自动铺卡。 |
| 市场助手引导 | 有上述可用操作之一才显示；体验可用时主按钮为「体验 AI 员工」，否则只显示可用的创建入口。体验完成不隐藏市场的体验入口；在市场点开后仍可选场景。 |


积分不足与模型未配置分开处理：积分不足不隐藏入口，用户可看历史；需要调用平台模型时，模型代理按所在工作区 owner 的余额做准入校验；余额不足则拒绝新的平台模型调用，按现有失败流程提示，不把体验标记为成功。隐藏入口不删除或改写历史。

### 场景卡与真实执行

三个场景复用同一套对话卡片和任务详情，只有通过验收的场景才展示，每张卡片只说明发生的事件和预计交付。客户投诉标为「推荐」，不替用户选择或启动。

| 场景 | 卡片文案 | 按钮 | 主能力 | 用户会拿到 |
| --- | --- | --- | --- | --- |
| 并行跟进客诉（推荐） | 一单显示签收却没收到，另一单退货已签收却没收到退款。 | 同时跟进两单 | 一次交办，多个任务并行推进 | 每单各有一条关键发现、下一步和可复制的客户回复。 |
| 会议后跟进 | 会后行动基本明确，但上线后谁看漏斗还没定。 | 开始跟进 | 先推进，缺关键信息时发起人工确认，收到答复后继续 | 确认前的行动清单、确认后的最终清单及可复制的群消息草稿。 |
| 自主恢复线上告警 | 支付成功率突然下降，看看员工能不能止损并把服务拉回正常。 | 开始恢复 | 自主完成排查、恢复、验证和回告 | 影响范围、已执行的恢复动作、恢复证据和仍需修复的问题。卡面标明演练、不操作真实线上。 |

未对话时默认把客诉排在首位，不替用户选。每张只验证一个主能力：客诉并行执行多个独立任务、会议等待人工确认后续跑、告警自主恢复并验证。后台执行和主动回告是共同底座，不额外增加操作。点击一次就开始，不先让用户编辑提示词、上传文件、选模型或连接账号。体验入口说明内置体验工具使用样例数据；若用户同时配置了真实工具，不保证该次一定使用样例，结果来源以实际命中的工具为准。客诉和会议的体验 MCP 只查样例，会议的人工确认走现有平台流程；告警恢复动作也只返回样例结果，不写外部系统。按现有平台模型计费规则提示。

**体验卡只是普通输入的快捷入口。** 点击后在同一助手 Web 私聊提交一条自然的用户消息，模型可见文字不出现「体验」「模拟」或专用指令，继续使用既有主对话和任务流程。不会额外建会话、贴执行标签、更换工具集或预设下一步。真实的任务状态、回告和产物照旧。

**工具按员工当前配置走。** 执行侧体验包中的 MCP 对模型声明正常业务名称和说明（如 `get_order`），与普通工具一样由既有规则按轮次和权限解析。开启体验包时，后续正常问订单同样可以命中它，不要求由卡片触发；关闭体验包、配好同类真实 MCP 后，走真实 MCP。二者并存不做体验卡优先或自动切换，沿用现有工具选择规则，不扩大任何权限。三个场景的体验 MCP 都无状态：不新增状态表、不写样例文件、不在内存或缓存记录处理进度、确认答复或工具调用次数。查询只按显式参数从代码内置样例取数据；任务进度、人工确认和工具结果仍由平台原有流程管理。体验工具没有真实凭据或外部请求。告警恢复工具只返回一次模拟操作的回执，不修改样例文件、不持久化任务状态，也不写真实系统。用户界面可用工具来源标识说明实际命中的是内置样例还是已连接资源，不能按是否点击过卡片来推断。体验包关闭后隐藏对应入口。

**卡面和样例统一由代码提供。** 每个场景用稳定标识关联标题、说明、按钮文案、样例输入和配套样例数据。市场与对话复用同一套场景定义，不给工作区或助手保存卡片副本。随代码发布更新，已有助手也读取新版；卡面与提交的样例输入来自同一套定义。历史里已发送的消息、任务和产物不改写。

三张体验卡默认走一对一私聊；群聊消息是可查询的样例资料，不因修改包的使用范围而增加真实群监听或发群消息的演示工具。主对话不新增工具，模拟 MCP 在执行 Agent。

### 三套样例输入（v1）

样例与任务约束作为版本化 fixture 提供。用户可展开「样例材料」看原始证据；预期结论和验收口径只给测试，不喂给模型。样例统一使用合成数据，不含真实订单、日志、成员身份或链接。下面的日期和时间是样例业务时间，不依赖用户点击当天；同一私聊可反复使用；工具数据来自代码维护的样例，不根据历史猜测业务事实。

| 场景 | 模型初始收到 | 可调用的内置样例工具 | 暴露证据的时机 |
| --- | --- | --- | --- |
| 客诉 | 一条消息内的两起投诉、各自订单号及交付目标 | `get_order`（订单和售后规则）、`get_delivery_evidence`（物流、签收及核查记录）、`get_support_thread`（既往客服对话与承诺） | 只返回截至样例投诉时的证据与客服历史。 |
| 会议 | 会议结束事件、样例会议标识与交付目标 | `get_meeting_notes`（讨论、承诺与决议）、`get_release_plan`（里程碑和依赖）、`list_project_chat`（会后群聊片段与消息时间） | 始终返回固定原计划和会后群聊，不写值守人。确认答复从现有任务上下文读取，不回写样例，也不新增体验 MCP 工具。 |
| 告警 | 支付告警、样例事件标识和恢复目标 | `get_payment_metrics`（成功率和分组）、`get_release_evidence`（灰度、日志和恢复规则）、`get_incident_timeline`（值班记录和处置记录）、`rollback_release`（只回滚指定样例发布） | 不传回执返回告警指标；传入本任务的有效回滚回执才返回对应的回滚后观测窗口。 |

工具名是设计暂定名，模型看到的是正常业务查询或受限恢复操作；实现只访问本地样例，不调用真实业务接口。模拟群聊只读当前场景预置的一个样例群，按已发生事件和消息时间返回短片段；没有真实群 ID、历史搜索、发消息、@ 或加入群的入口。样例段落中列出的订单、会议和告警证据是工具响应的来源，不是初始提示词；预期结果仍只作验收。

#### A. 并行跟进客诉：两单同时查，各自回报

卡片点一次，在助手私聊发送下面**一条普通用户消息**。主对话沿用现有任务工具，为每笔订单各创建一个独立执行任务，不在卡片处理层批量创建、不等第一单查完才提交第二单。任务标题可包含订单号，任务进度和结果按现有流程在同一私聊中分别展示和回告；先完成的那单先回，不必等另一单。

> 有两起客诉，帮我拆成两件事同时查，哪件先查清就先告诉我。
>
> 1. ORD-1042：显示驿站代收，客户就在驿站却找不到，在线等回复。
> 2. ORD-1087：收到的商品型号不对，客户明早活动要用。
>
> 每单给我最关键的发现、建议下一步和一段可复制给客户的回复。先别实际发消息或退款。

| 样例 | 工具返回的证据（不随首条消息发送） | 该单验收 |
| --- | --- | --- |
| ORD-1042：签收未收到 | 便携投影仪，实付 629 元，选择星桥园区 1 号门驿站自提。14:22 标为驿站代收、无代收人，照片立牌却写 7 号门。16:12 客户在 1 号门驿站，货架和登记均未找到，在线等回复；客服承诺 16:50 前更新；7 号门尚未核实。签收证据冲突时先查承运记录和交接人，核实前不承诺退款或补发。 | 点明 1 号门和 7 号门不一致，误投是推断不是定论。客服现在先查承运记录及 7 号门驿站，不让客户再查 1 号门，保留 16:50 进度承诺。 |
| ORD-1087：错发型号，明早要用 | 订单为黑色 X2，拣货记录却发了银色 X1。客户已上传照片、保留包装，明早 08:00 活动要用，优先换正确型号。附近库存未核实。 | 区分错发与物流问题；建议先核实就近库存、换货时效及明早前的可行替代，不宣称已换货或承诺到货。 |

**并行验收**：同一条用户输入实际生成两个不同的任务 ID，各查自己的订单、物流和客服记录，不串单。资源充足的测试环境中，让一单保持运行时验证另一单已开始、可以先完成并回告；只有两个任务 ID、但实际串行，不算并行通过。正式运行仍遵循原有并发配额，资源不足可以正常排队；不伪造进度。单单失败不阻塞另一单的回告，这张卡只有两单都成功且结果可查看时才记为体验完成。推荐追问：「把 ORD-1042 的回复缩到 70 字以内，保留更新时间。」

#### B. 会议后跟进：先整理，确认关键缺口后继续

- **触发事件**：「MEET-301 刚结束，帮我把会上定的事往前推进，别只整理纪要。先核对材料，推进能做的事；如果有会影响上线、现有材料不能确定的事项，发提交卡来确认，收到答复再补齐。」题面不告诉模型缺哪个负责人。
- **样例会议**：周三 14:00，目标是周五 17:00 小流量上线。阿岚：「周四 12:00 前交三个页面的最终文案。」小程：「收到文案后接入，周四 18:00 前给预览。」晓宁：「周五 12:00 前跑完 iOS、安卓验收，前提是周四晚交付的预览可用。」主持人总结：「周五 15:00 看验收决定上不上；没通过就继续走旧流程。」
- **发布计划**：旧计划上写「周五 17:00 上线」，这是目标，不是批准；依赖为最终文案 → 预览 → 双端通过 → 周五 15:00 放行判断。
- **容易误读的两条**：阿岚提议「欢迎邮件也顺便改吧」，主持人明确「下期再做」。数据同学说「上线后得看漏斗」，参会人没有认领，也没有定截止时间。
- **会后模拟群聊（周三）**：14:18，小程：「先用占位文案跑骨架，不等最终文案；正式预览还是要拿到定稿。」14:22，晓宁：「iOS 用例先准备，安卓环境在修；环境好了也不等于已经验收完。」14:28，数据同学：「漏斗口径可以来问我，发布后的值守我还没认领。」14:35，晓宁：「安卓联调环境已恢复并自检通过，双端验收按原定时间推进。」所有已认领交付时间不变。
- **模型交付**：先列三条已认领行动、周五 15:00 的上线判断点、可提前做的事，区分安卓环境自检通过与尚待验收。找不到值守人时，用现有人工确认工具发一张提交卡，请确认人填「上线后谁负责看漏斗？」；按现有规则找确认人，没匹配规则时用员工默认确认人。任务等待答复并由原流程续跑，再交付最终清单和群消息草稿。
- **验收**：答复前不编造值守人、不假装已完成；答复后在同一个任务中使用真人填写的名字，不回写会议纪要、群记录或样例工具。空答复或没找到可用确认人时，按现有流程说明缺口，不编负责人。重新体验仍查到固定的未认领记录。最终清单不把欢迎邮件列入本期，不写成「已批准上线」，也不把安卓环境恢复当成验收完成；不要针对已经有结论的环境再发确认。

#### C. 支付成功率下跌：按 trace 查日志，回滚止损、验证恢复

- **首条样例输入**：「支付成功率突然下降，触发 INC-207。失败请求 trace ID：tr-pay-207-a81f。请按 trace 查日志，对照告警指标、发布记录和手册；按授权恢复，复查两个独立监控窗口。」不在输入里给目标发布版本或预告根因。
- **初始证据**：Android 支付成功率 91.6%，iOS 99.7%。trace 日志 SIGNATURE_MISMATCH，命中 android-signature-v3；发布记录显示灰度开始与异常出现相邻，其他端、网关、支付供应商无异常。手册允许在其余端正常、Android 低于 95% 时撤回该灰度。
- **恢复动作**：样例值班手册预授权把 INC-207 关联的安卓签名 v3 灰度回滚到上一个健康版本；在这个明确范围内不再找人确认。助手自行判断并调用恢复工具。服务端只接受样例注册的告警和发布标识，不接受真实环境、任意 URL 或命令，不持有生产凭据。工具按固定样例返回操作结果；成功时返回绑定当前任务、告警及发布版本的可校验 `rollback_receipt`。回执由工具自身生成并可无状态验证，不新建状态表、缓存或进程内状态；重复调用按同样条件得到同样结果。模型通过已有的任务工具结果记住回执，不自行填「已回滚」。
- **验证恢复**：操作回执只证明回滚已提交或已生效，不等于服务已恢复。助手须调用 `get_incident_metrics(case_id, rollback_receipt?, window?)` 再查监控：不传回执返回初始告警指标；回执无效或不属于本任务则拒绝，不返回恢复指标；传入有效回执后，按样例返回回滚后的观测结果。若时间线要展示回滚记录，也由回执推导。成功样例返回两个不同的 5 分钟窗口（99.4% 和 99.6%）；两窗均高于 99% 才算恢复，不需真实等待十分钟，重复查询也不会推动样例进度。未回稳、无法验证或操作失败时，准确说明已做到哪一步、下一步要谁介入，不宣称成功，不擅自扩大处置范围。
- **交付和验收**：能在任务时间线上看到诊断、真实调用内置恢复工具、回读指标、最终回告。回告区分「通过回滚恢复服务」和「签名代码仍待修复」，给出后续修正及重新灰度前的验证建议。另测回滚失败和动作成功但指标未回稳，两种都不得回告已恢复。验收无回执、有效回执、非法回执及跨任务复用；新建体验不继承旧回执，仍查到初始告警。体验展示清楚标为样例环境，真实生产接入及授权不在首期范围。

#### 体验质量验收

- **先交付能确定的部分。** 客诉和告警不要求用户补输入；会议先整理已有信息，只在缺少最终清单所需的值守人时走正式确认流程，不在 MCP 内等人。
- **回告先说发现，再给可用产物。** 回告至少包含一个本场景独有的具体事实，不只说「已处理，见附件」；用户能直接预览或复制。体验成功以结果已可在发起者的 Web 对话打开为准。
- **先验证客诉。** 用新人视角实际点击，记录点击到首条真实进展、首单可打开结果和两单全部交付的时间，以及结果后的追问、复制或创建入口使用情况；不把点击本身当作体验成功。先测首轮产物质量和真实状态链路，再开启其他卡片。
- **各卡主验收。** 客诉从同一输入拆成两个独立任务，验证执行有重叠、逐单回告并各自提供可用回复草稿；会议实际发出提交卡，收到答复后在原任务续跑；告警必须实际执行样例恢复动作、回读指标并证明恢复，不能只给诊断建议。主动回告与补充信息沿用默认能力。客诉和告警不需二次操作；会议的确认是该场景本身的验收项，不另建体验交互机制。
- **多来源核对。** 不以调用次数作为质量指标；要能用会后群聊补充会议计划，用历史会话避免让客户重复排查，用值班记录区分有人提议与已经执行。初始样例不包含触发时刻之后的证据；告警恢复后的指标由有效回滚回执选择样例分支，不靠保存状态或累计查询次数。
- **跨场景与权限回归。** 同一账号先试客诉再试告警，不能混用地址或数据；同一私聊先开启体验包、再关闭并接入真实 MCP，后续任务必须反映员工当前包权限；工具返回样例时向用户标明来源；分别用工作区创建者和普通成员验收。未授权的创建入口不出现，体验仍可用；免费赠送或平台积分口径不因样例变更。

### 首次体验与工作区切换

- **体验完成按平台账号记录。** 有权使用助手的不同成员各自记录体验进度，A 完成不影响 B；记录不授予助手或管理工具的使用权。同一账号尚未完成体验时，切到另一个有助手入口的工作区仍可体验。
- **首次成功交付才算完成。** 单纯打开页面、点击按钮、受理、执行失败或取消，不改变完成标记。以服务端确认该场景所需任务全部成功且结果能在发起者的 Web 对话中打开为准（客诉卡是两单），不以设备本地状态或是否打开产物为准。如需关联卡片来源与任务结果，仅在服务端记录体验完成所需的来源，不写入模型输入，不参与工具选择、任务权限或执行分流。
- **对话按账号和工作区隔离。** 再进助手优先显示该工作区的历史；无历史且未成功体验时显示已上线的场景卡，无历史但已在别处体验时显示普通欢迎页。若已有历史、但还没有成功体验，保留明显的场景入口，不覆盖历史。体验入口和体验卡分开：满足上表 Web 私聊展示条件时，顶部「体验场景」入口常驻；体验卡不常驻。首次体验成功后，卡片不再自动占用对话首屏，切换工作区也不重新铺卡。用户主动点「体验场景」时，仍可打开全部已上线的场景卡并重新体验。

### 对话创建与修改员工

用户可在 KIKO Web 私聊明确要求创建员工。后台任务用当前登录账号和工作区复用员工创建服务，默认确认人还是创建人的 Web 账号。已核验的 IM 私聊维护人可管理当前工具允许的配置，不支持通过 IM 创建员工。Web 页面和原有接口不变，不引入后端草稿。

## 3. 平台设置与助手创建

### 默认发放与配置

托管和自托管的新工作区都默认创建助手，不再提供平台发放开关。系统助手允许不绑定具体模型；普通员工仍须绑定一个可用模型才能创建。不存在模板、版本发布或 1 号员工的前置条件，也不会给任何已有员工自动挂载内置包。

名称、描述、职责和提示词是代码内置默认值，头像由平台固定；沿用普通员工的默认配置但不绑定具体模型，不复制任何已有员工、官方模板、运营资源、凭据、渠道绑定或历史。助手沿用通用员工创建默认值：普通使用范围为「全员」（本工作区有效成员），默认确认人是该员工创建人的 Web 账号。自动发放的助手由工作区创建者创建，因此确认人初始为该创建者，不另设体验确认规则。后续按普通员工规则编辑、停用或调整范围；付款人按第 5 节判断，不从员工创建者或确认人推导。修改代码中的默认值只影响之后创建的助手，不覆盖已有实例或用户设置。

### 工作区创建与异步发放

- 注册仍一次性提交账号、默认工作区和钱包；手动建区沿用原事务。两条路径都由新工作区插入事件入队。助手发放失败不回滚注册或工作区创建。幂等键是工作区 ID，不是账号 ID；同账号新建多个工作区分别发放。升级不回放存量工作区队列。
- 仅技术失败重试，重试不检查模型配置，不走页面补建。
- 发放以工作区为幂等边界：普通员工创建、体验能力包初始化、保存助手员工 ID 和标记发放成功在同一事务完成；重复消费返回原结果。未发放成功前没有可点击的助手入口。员工删除后，发放成功记录不重置，不自动创建替代员工。

## 4. 身份、会话与工具

助手会话按账号、当前工作区和员工实例隔离；切换工作区不继承旧会话或草稿授权。新建员工有自己的实例和配置，不共享助手会话、运行凭据或权限。

### 内置员工管理 MCP

助手收到挂载请求时先查看目标员工的默认插件。目录中的 `distribution=all_agents` 表示平台统一分发。员工状态为 `available` 时直接说明已默认继承、可在任务中使用；平台待配置、已停用或员工待绑定付款账户时说明对应原因。重复添加只返回 `already_inherited` 及当前状态，能力包版本保持原值。

一个内部 MCP 端点承载 5 个工具，由执行 Agent 在 Web、飞书、钉钉或企微的合格私聊任务中挂载。只有 KIKO 助手的 Web 私聊加载 5 个；KIKO 的 IM 私聊和普通员工私聊只加载 3 个。普通员工和 IM 私聊的目标绑定为当前员工。群聊、定时、Webhook、结果回告、事项交接及确认续跑不挂载，不改变主对话工具。主对话把明确的管理请求委派给执行任务。

| 工具 | 参数与行为 |
| --- | --- |
| `list_employees` | 仅 KIKO Web，按名称或精确 ID 分页查当前工作区员工，返回概览。 |
| `create_employee` | 仅 KIKO Web，复用工作区成员创建权限和页面创建服务；用户明确要求才调用。未指定模型时优先工作区默认模型，之后平台默认模型。创建不传头像，系统从平台支持的头像中随机选一张并保存。 |
| `get_employee` | 概览和 `capability_packages` 分页都返回只读的 `default_plugins`。概览展示平台启用状态，有管理权限时还能看到目标员工的付款绑定是否就绪，以及可查配置目录。 |
| `list_employee_resources` | 有效工作区成员可从 Web 私聊只读查询共享模型、Skill 和 MCP，包括启用且已上架的官方 Skill 与插件；目录与员工管理权限分开，不授予安装权限。IM 私聊仍按当前员工管理权限查询。按模型／Skill／MCP 分类，支持名称、精确 ID、分页；返回 ID、名称、短摘要、来源和版本，不返回工具详情和凭证。KIKO Web 的创建流程可用 `purpose=create, resource_type=model` 查询模型，不要求对任何已有员工有管理权限；只需把返回的短 `id`（例如 `m42`）填入 `model_id`；来源仅作展示。后端解析时先查当前工作区，再查平台，并保留原 UUID 作为数据库关联。 |
| `update_employee` | 和 get 共用 `config_key`，每次保存一项。只支持档案、岗位约束及已有能力包增删共享 Skill／MCP；不上传或发布资源，不改群配置、权限、维护人、启停、渠道或触发器。 |

配置 key 为 `profile`、`instruction`、`model`、`capability_packages`。模型只读，切换模型只在页面执行；创建员工仍可指定模型。MCP 不返回头像 ID；普通员工可在页面更换，KIKO 助手头像固定。保存使用 get 返回的员工版本或单个能力包版本。能力包改的是挂载，不动其它固定版本、权限或共享资源本身。更新后可按同一 key 读回。Web 原有功能不裁剪；切换到平台付费模型仍在 Web 确认积分扣费。验证 GitHub Skill 不等于发布或安装：无目标管理权限返回明确拒绝，有权限但没发布时不得安装。

Manager 注入活跃执行 Input 绑定的真实工作区、身份和当前员工，模型不传这些授权信息。MCP 校验目标与操作，底层保存事务重验，不能借管理员身份；没有目标管理权仍可查概览。Web 管理权是工作区 Owner / 管理员、目标员工创建人或维护人。渠道管理权承认目标机器人的已验证个人维护人；绑定、租户、身份代次、连接版本必须有效。不拿两个机器人各自的 OpenID、姓名或邮箱做推断；没有可信跨绑定关系不开放跨机器人配置管理。对外 `backend/internal/webgw/mcp` 只预留业务复用，首期不开放。

管理工具在真正保存的事务内再次检查原任务轮次、调用身份及来源员工的当前使用权限；更新还要检查目标员工的管理权限。与撤权或停用竞争时，先完成的状态变更为准。读取结果和此前已签发的凭证都不替代写入时的权限。 管理 MCP 和体验 MCP 的凭证按执行轮次刷新，不进入 Pi 的静态配置；只有凭证或工具准入变化时沿用当前进程，无资格的下一轮移除旧工具。模型等真正的静态配置变化仍按原规则重建进程。

### 内置体验包

`backend/internal/manager/mcp/demo` 独立于管理 MCP。只给 KIKO 助手自动开通；默认继承员工私聊使用范围，群聊及触发器不默认启用。工作区只保存启停和授权，不复制工具定义。包内工具清单随代码更新，前端只读，不可手工增删、复制或改写定义。迁移 107 清理旧管理占位包，不影响体验包或用户自建包。

### 外部 GW/MCP：显式选区，后续开放

- `list_workspaces(cursor?)` 仅返回账号当前有权访问且外部授权覆盖的工作区，返回名称、ID、角色和是否具备员工管理权限。该工具只读，不改变平台默认工作区或 Web 选区。
- 外部 Agent 让用户选定目标，再在每次员工工具调用中显式传入 `workspace_id`。缺失就提示选择，不默认选个人工作区或第一个工作区；不提供会改变全局状态的「切换工作区」工具。后端逐次复核有效成员关系、授信范围、操作权限及资源归属，能列出 ID 不代表有权写入。
- 后续通过平台账号的远程 MCP OAuth 授权。外部工具和认证参数独立，不进内部模型契约；现有第三方登录只用于识别平台账号。内外复用业务服务，外部是否开放最终提交及对应的本人确认另行评审。

## 5. 模型与计费

| 对象 | 模型选择 | 计费边界 |
| --- | --- | --- |
| KIKO 助手及其演示任务 | 未显式绑定时优先使用可用的工作区默认模型，没有再用平台默认模型 | 使用平台模型时扣所在工作区 owner 的积分，不按发起者扣；自备模型不扣平台积分。 |
| 用户新建的其他 AI 员工 | 页面与助手共用规则：优先预选目标工作区可用的默认模型，没有再预选平台默认模型；显式选择的可用模型优先 | 使用平台模型扣新员工所在工作区 owner 的积分；工作区自备模型不扣平台积分。 |

**助手不新增计费逻辑。** 沿用现有员工模型凭据、工作区 owner 的账号钱包、余额准入和实际用量结算；对话、演示、任务、重试和主动回告中发生的平台模型调用按同一规则结算，不引入按使用者扣费、平台代付或独立团队钱包。体验入口说明费用由工作区 owner 承担，不因此向其他成员显示其余额或账单。积分不足不影响查看原本有权限的历史和产物。普通员工旧 Key 的绑定切换由平台扣费迁移负责，助手无需额外迁移。

默认模型顺序只在创建时生效；保存具体模型引用，默认项后续变化不替换已有员工，也不在执行时自动回退。没有可用默认模型时提示选其他有权使用的模型或先完成配置。

## 6. 开发顺序与验收

开发先做工作区发放与导航，再把三张体验卡和无状态样例 MCP 跑通。其后单独收紧员工详情的查看权限。正式员工管理 MCP 统一讨论和评审，Web 与 IM 是同一能力的入口，GW 后续复用业务权限与执行逻辑。以下为分场景验收清单。

1. **内置配置、发放和导航**：注册和手动建区在无模型时都能自动发放；存量工作区不补建。覆盖异步重试和并发发放，工作区内仅一份助手关联。验证改名不影响入口、停用隐藏、重新启用恢复；有权限用户仍能打开助手并查看体验卡，不向无权用户暴露入口。点击导航不发消息。体验和聊天首次提交无模型时不入队、不计完成；模型有效后重新选择体验或发送。验证工作区默认优先、平台默认兜底及平台模型仍使用工作区 owner 积分。
2. **管理 MCP 闭环**：检查 KIKO Web 5 个工具、其余私聊 3 个，群聊或合成轮次不挂载。覆盖 get → update → get、版本冲突、撤权、换绑、不能跨工作区、用户配置不受影响，以及已验证渠道维护人和普通使用者的权限差异。GitHub Skill 验证后，分别验证无权限、共享池无资源、获准挂载三种结果。
3. **同会话体验**：优先跑通客户投诉的「卡片提交一条样例消息 → 主对话新建两个客诉任务 → 并行查证 → 原私聊分别回告和交付」，通过后才启用体验主按钮；另两个场景各自通过实际调用内置样例工具的验收后上线。覆盖体验与真实任务共享同一私聊、按现有规则由每轮有效能力包决定工具、主对话任务工具契约不变、市场场景卡与对话场景卡均在同一助手私聊只发送一条普通输入且不自动跳任务详情、关闭体验包后可由已配置的真实工具处理下一次请求、失败不记完成。验证仅有体验包权限但无员工使用权限时，市场和对话均不显示体验入口，直接请求也不能启动；体验成功后空对话不再自动铺卡，市场和手动入口仍可用。验证代码更新后已有助手的市场和对话展示新版卡面，点击发送与之对应的新版样例输入，旧消息不改写。
4. **渠道续接**：结果页跳现有渠道设置，用户在该页本人授权，不新增 MCP。取消扫码、缺权或连接失败不影响 Web。外部 MCP 单独评审认证及开放范围。

**Web 体验入口验收**：助手导航不可用时不展示；导航可用但只有体验包的群聊、触发器或 IM 私聊权限时也不展示。满足 Web 私聊授权及场景上线条件时展示市场和对话入口，群聊和触发器关闭或打开均不影响；撤掉 Web 私聊授权后隐藏。对话内自动展示卡片仍受空对话和首次体验规则控制。

首体验观测：各场景选择率、首次开始体验到拿到真实产物的耗时与完成率、体验后继续在同一会话布置日常任务的比例、发出创建请求到成功建员的比例。统计不采集工作内容、附件正文或认证材料。
