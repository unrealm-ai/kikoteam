# 用版本标签发布双架构镜像

这份提案记录最初的双架构标签发布设计。现行流程在 `main` 推送和正式标签推送时构建 Linux AMD64 镜像，触发条件和托管部署指针的更新规则见[镜像发布规范](../spec/tagged-multiarch-release.md)。

## 原提案的发布规则

- **产品版本只认 Git 标签 `vX.Y.Z`**，例如 `v1.2.3`。目标提交必须可从 `main` 追溯；不要求是当前分支顶端。提交 SHA、候选镜像名和工作流运行号仅用于定位和验证，不能当作产品版本。普通 PR 与 `main` 提交保留现有 CI，不发布产品版本或推进部署指针。
- 同一标签、同一提交原生构建六个镜像：`backend`、`event-hub`、`agent-engine` 各构建 `linux/amd64`、`linux/arm64`，不用跨架构模拟代替验收。沿用现有三个 GHCR 包及其名称，不新增包；官方版本引用由每个包对应的双架构 OCI 索引提供。
- 每种架构用该次构建的候选摘要运行完整栈冒烟，并通过真实打包的 Engine、Pi 与内置 MCP 跑通具备工具调用的任务。核对镜像确为目标架构、数据库迁移和服务就绪，避免以本机源码或另一架构的旧镜像替代。两种架构均通过才发布版本标签、`latest` 和 `verified-deploy`。两架构之一失败或缺少可信验收，不能推进任何正式引用。
- 同一正式版本不可指向另一提交。旧版本即使补发成功，也只能拥有自己的版本引用；版本号按数字段比较，不能因旧标签、重跑或并发作业晚完成而回退 `latest` 或 `verified-deploy`。部署指针最后更新，并关联本次验收通过的三份镜像索引摘要，使部署端能核对完整一批。

## 验收用例

| 场景 | 预期 |
| --- | --- |
| 普通 PR 或 `main` 推送；格式错误的标签；标签指向 `main` 不可达提交 | 保留常规 CI；没有正式发布或部署指针推进 |
| 同一提交获得合法标签 | 两架构原生构建共六项，按摘要启动全栈；两边均验证 Engine / Pi / MCP，再核对三个正式索引均含两个正确的平台摘要 |
| 任一架构缺失、运行错误架构、冒烟失败或任务失败 | 保留既有正式版本和当前 deployment 指针，不把候选标成已验收 |
| 先发布较新版本，再补发或重跑较旧版本；同版本标签改指向其他提交 | 旧版本不得回退 `latest` 或 `verified-deploy`；同版本不同提交不得覆盖 |

静态检查和模拟发布测试只证明触发、发布门禁、索引与指针规则；两架构运行验收要以实际 CI 记录为准。原生 Linux ARM64 发布验收不等于 Apple Silicon Mac 上的 Docker Desktop 实机体验；如需后者，另在 M 芯片真机用隔离项目、端口和数据卷验收 pull、启动与任务。本文不创建标签、不推送，也不触发发布或部署。
