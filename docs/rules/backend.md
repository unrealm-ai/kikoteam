## Go 实现与测试

声明各模块拥有的数据和对外操作。HTTP、命令行、渠道、定时入口和后台任务通过同一业务用例执行业务校验。由程序入口装配配置、数据库、时钟、外部客户端等依赖，业务模块通过所需的接口协作。小模块可以保持一个包。

分层按实际复杂度引入，不强制所有模块具备相同目录。采用 controller / service / repository / integration 时，分别表达入口适配、业务用例、持久化适配和外部客户端；业务用例通过所需接口依赖存储与外部能力，由入口装配具体实现，不依赖协议处理器。跨模块调用应暴露明确用例，避免绕过状态所有者、循环导入和无边界公共包。Backend 的具体顶层名称、目录及当前命名过渡见[模块命名与内部分层](../../backend/README.md#模块命名与内部分层)，不将其布局强制套用于其他组件。

跨网络、数据库和子进程的调用传递 `context.Context`，设置可取消的等待边界；退出路径负责回收连接、计时器、goroutine 和子进程。错误包装保留原因并注明失败步骤。

Go 代码用 gofmt 格式化。组件具备模块与测试后，在相应模块运行 go test 和 go vet，有共享可变状态的路径用并发测试验证。实现布局以后可考虑如 `event-hub/internal/channels/` 或 `agent-engine/internal/runtime/`；这些示例不决定 Go module 的数量或源码目录。

## HTTP 接口与客户端

本节默认约定适用于平台自行定义的资源型 HTTP API。第三方事件回调、身份授权回调和 MCP 等协议入口遵循各自的交互、输入与响应约定，由适配器衔接内部业务用例，不套用本节的资源路径和响应外形。新增或变更入口都须核对[身份与业务写入](#身份与业务写入)，不能仅在已有接口改变访问范围时才检查认证与授权。

### 契约优先

每个提供 HTTP 接口的服务组件有自己的契约目录。以下为组件内部布局示例，实际路径随组件方案确定。只有组件内多个模块共同使用的定义才放入 `components/`。

```text
<服务组件>/contracts/
  openapi.yaml                     # 该组件的契约入口
  modules/
    <业务模块>/
      paths/                       # 按资源组织的路径定义
      schemas/                     # 该模块的请求与响应模型
  components/                      # 该组件共用的参数、响应和模型
```

- HTTP 接口直接用手写的 OpenAPI 3.1 YAML 定义，作为唯一机器可读契约源。
- 接口归提供服务的组件维护。每套 API 有一个 `openapi.yaml` 入口，按业务模块组织操作、请求和响应类型，入口在 `paths` 下列出各条路径，每个路径项用相对 `$ref` 指向模块文件。模块内的 `$ref` 从引用所在文件解析。对外 API 和内部 API 需要独立发布时，各设入口。
- 先评审操作、认证、请求、成功与错误响应以及代表性示例，再实现 handler 和客户端。已发布接口的变更要检查现有调用方，尤其关注新增必填字段、收紧取值范围、默认排序变化及错误语义变化。
- 每个操作声明稳定的 `operationId`、接受的身份类型、授权要求、幂等与重试条件；涉及并发、分页、异步受理或流式响应时，补齐对应行为和查询方式。`operationId` 用于契约命名和代码生成，不是请求实例标识或业务去重键，不能因 handler 重命名而随意变化。
- 工具链接入后，对各入口分别校验规范和引用，再打包为单文件供文档、SDK 和服务端类型生成使用。变更提交到模块 YAML，生成物由工具更新。实现完成后，以实际 HTTP 请求验证关键成功和失败行为。

对外契约可以同时包含要求认证和允许匿名的操作，不按凭据类型复制同一套业务契约。接口面、实际入口路径及契约目录由提供服务的组件确定；Backend 组件的方案见 [API 接口设计](../../backend/docs/http-api.md)。协议适配器单独记录其输入、响应、认证与回执约定。

### 路径与操作命名

按调用边界和用途划分接口面，认证要求单独声明。内部专用、对外发布和允许匿名是不同概念，不用 `public` 同时表达后两者。Web、SDK 和不同凭据调用同一业务能力时，复用资源路径与业务用例；管理员身份本身不是内部接口的划分依据。

资源集合使用小写复数名词，详情沿用集合路径并追加资源 ID；明确的单例资源或内容子资源可使用单数或不可数名词，其含义由组件设计说明。路径中的多词名称用连字符；路径参数、JSON 字段和查询参数用 `snake_case`，参数名明确所指资源。枚举值采用小写，必要时用下划线。以下仅为命名示例，不预设组件资源：`service-accounts/{service_account_id}`。

普通增删改查由资源路径和 HTTP 方法表达。不能自然表达为增删改查的业务动作，统一使用 `POST <资源路径>/<动作>`，多词动作用连字符；不混用冒号动作或额外的 `actions` 层。每个动作仍须独立定义权限、重试语义和状态变化；异步动作说明受理响应及结果查询方式，不能用 GET 执行写操作。

资源标识用于稳定引用，规则见[资源标识与命名](#资源标识与命名)。路径参数定位资源，查询参数控制读取条件，请求体承载写入内容。归属层级在组件设计中统一，集合与详情不随调用方另起路径；请求体不提供与路径归属相冲突的独立可写字段。

### 版本与兼容

API 主版本表达契约兼容性，与产品发布、SDK 包版本分开管理。同一接口面内的业务模块使用一致的版本入口；对外与内部接口面可以独立演进。具体版本路径由组件设计维护。

新增接口或兼容的可选字段通常保留当前版本。删除字段、修改类型、改变核心语义，以及收紧必填条件、修改默认排序或错误语义，都须核对调用方并制定兼容或迁移方案。新增枚举值、事件类型不自动视为兼容，要核对客户端是否接受未知值。

内部契约也要考虑滚动发布期间的新旧组件共存。第三方回调协议、MCP 协议和工具契约独立管理，不把业务 API 主版本当作这些协议的版本。权限策略变化须评估调用影响，但不因保留旧版本而保留安全绕过路径。

### HTTP 入参与返回

| 项目 | 可直接采用的默认约定 |
| --- | --- |
| 路径与命名 | 遵循[路径与操作命名](#路径与操作命名)，组件设计维护具体入口和资源层级。 |
| 输入校验 | 声明类型、必填、可空、默认值、枚举和长度或大小上限。普通写入对象拒绝未知字段，重复的标量查询参数返回 `400`。PATCH 省略字段表示保留原值，显式 `null` 仅在允许清空时使用。 |
| 成功响应 | 单项直接返回资源对象，分页集合返回含 `items` 的对象，空集合返回 `items: []` 并保留分页字段。实际新建资源用 `201`，资源创建后还有后台工作不改变创建已成功的事实；首次仅被异步受理、尚未完成时用 `202` 并说明如何查询结果，无响应体用 `204`。已有资源能表达受理及执行状态时直接复用，不为异步动作默认新增控制标识或回执资源。重复调用的状态码由端点声明，业务是否执行完成看资源状态，复用已有资源不能冒充新建成功。 |
| 错误响应 | 统一错误结构，例如 `{"error":{"code":"invalid_filter","message":"筛选值无效","request_id":"…"}}`。调用方按 HTTP 状态和稳定的 `code` 分支，`message` 供人阅读，可选 `details` 指出具体字段。 |
| 请求与响应模型 | 分别声明可写字段和可读字段，特别是凭据、只读标识和服务端计算值。时间戳统一采用带时区的 RFC 3339，响应使用 UTC。文件下载、流等按实际媒体类型声明。 |

缺少有效认证返回 `401`，身份有效但操作未获准返回 `403`；需隐藏资源存在性时，在契约中统一约定 `404` 策略。状态冲突、幂等键冲突等用明确的 HTTP 状态与稳定错误码表达，不将失败统一包装为 `200`。

### 流式接口

平台资源的流式响应按所属资源组织，不能因为传输方式不同而另建业务权限边界。事件流契约声明事件类型，区分临时增量与持久化事实；支持可靠续读时，声明事件标识、续读位置、重复事件处理及位置过期后的恢复方式。文件等字节流声明媒体类型、传输中断和重新读取方式，不套用事件字典或事件续读规则。

订阅和重连均核验当前权限；长连接期间的撤权生效方式由组件设计明确。断开连接是否影响后台工作须显式约定。流开始前按普通 HTTP 错误处理，开始后不能再依赖修改 HTTP 状态报告错误，须定义流内错误或关闭及恢复行为。

### 接口验收

契约与路由核对方法、路径、操作标识、认证要求、请求和响应。覆盖匿名例外、未认证、越权、资源归属不匹配及相应错误；同一路径的不同方法分别验证。内部接口同时检查部署访问范围与服务身份，不能仅按路径前缀判断可信。

已发布接口变更核对调用方和版本兼容。异步、幂等、分页及流式操作分别覆盖回执查询、响应丢失后重试、稳定续读和撤权后的行为。与前端同域时，未知 API 不能被页面回退逻辑转换为 HTML。

## 资源标识与命名

资源 `id` 由系统生成，用作稳定引用。展示名 `name` 按业务需要允许修改。需要可读的技术标识时再引入 `key`，契约声明其唯一范围、大小写、是否可修改，以及删除后能否复用。对外使用哪种标识由端点声明。验收时改一次展示名，确认已有链接和外部引用仍指向同一资源。

## 写操作的幂等与并发

不统一要求所有写接口携带幂等 key，也不默认建设通用响应回放机制。普通 CRUD 优先用业务唯一条件、目标状态和版本检查定义重试行为；仅在重复受理会产生业务不允许的额外执行、费用或作用范围变化等关键操作中，按需要增加请求去重。创建操作不天然可安全重试，同名或同内容不等于同一次创建；接口须明确重试可能产生的新资源或冲突。

| 设计问题 | 契约与验证 |
| --- | --- |
| 操作已成功但调用方没收到响应，再提交一次会怎样？ | 逐操作声明重试条件。采用 key 时定义唯一范围、有效期、同键同内容的返回结果及不同内容的冲突；必要的去重引用与业务写入原子保存。优先返回原资源的当前状态，确需回放原响应时由契约单独说明。验证响应丢失和同键并发时只受理一次；普通 CRUD 验证其约定的状态、版本或唯一条件，不强求回放旧成功响应。 |
| 两个调用方从同一旧版本提交不同修改会怎样？ | 声明采用字段合并、后写覆盖还是版本条件更新。需要保护旧读结果时，可使用 `If-Match` 或版本号并原子检查。契约写清缺少前提和版本过期时的返回行为。版本冲突后重新读取判断，不自动换成最新版本覆盖；用不同请求竞争同一版本验证。 |
| 控制动作、受理与执行开始同时发生会怎样？ | 明确业务裁决点、作用范围及每种先后顺序的结果，以原子条件转换和数据库约束落实。重试是沿用原作用范围还是按当前状态重新执行，由端点契约声明；无状态变化时不重复产生同一状态事件。请求去重不能替代不同请求之间的并发控制。 |

授权应覆盖每次提交及去重命中后的资源返回。调用外部系统后若结果未知，应先通过原操作标识查询结果，再按该端点的重试约定决定下一步；数据库去重不能保证外部调用只执行一次。

平台自行定义的资源型 HTTP 操作采用幂等键时，统一使用 `Idempotency-Key` 请求头；第三方回调和工具协议使用可跨重试保持稳定的事件或调用身份，并由适配器映射内部去重范围。协议未提供这种身份时，在适配契约中补充，不能直接把连接内请求编号当作幂等键。幂等键关联同一次逻辑操作的重试，与用于链路追踪的 `X-Request-ID` 分开管理，不能用链路标识代替业务去重身份。

## 排序、筛选与分页

| 项目 | 可直接采用的默认约定 |
| --- | --- |
| 排序 | `sort_by` 和 `sort_order=asc\|desc`。每个列表声明可排序字段、默认顺序及空值位置。服务端把白名单映射到查询列。同值时追加唯一键，例如 `created_at DESC, id DESC`，保证翻页顺序确定。 |
| 筛选 | 精确匹配用字段名。不同字段按 AND，同一多值字段按 OR，仅数组参数允许重复。时间范围用 `<field>_gte` 和 `<field>_lt`，左闭右开。提供 `q` 时声明可搜索字段和匹配方式。 |
| 页码分页 | 适合需要跳页或精确总数的列表。用 `page`、`page_size`。若返回 `total`，它统计授权和筛选后的全集。 |
| 游标分页 | 适合连续遍历或深分页。用 `cursor`、`limit`，返回 `items` 和 `next_cursor`，末页返回 `null`。游标包含完整排序边界，绑定访问作用域、筛选和排序，并校验完整性。 |

每个端点固定分页模式并声明默认页大小和上限。服务端依次应用授权范围、筛选、稳定排序和分页。用一组主排序值相同的记录验证跨页无漏项，同时检查有无重复记录，再覆盖空页、末页、非法排序或筛选及更换筛选后复用旧游标。

## 身份与业务写入

业务 HTTP 接口默认要求认证，匿名访问按操作显式声明，并核对路由与契约一致；不能因所属分组含有登录或回调接口而整组免认证。内部接口同样要求服务身份与能力授权，不把用户登录态、API Key 和内部服务凭据无差别互认。

写清调用身份、允许的动作、可访问的数据范围。可信入口解析并校验工作区、主体、渠道和会话身份；客户端传入的范围和标识只能作为待核验目标，不能直接成为可信授权上下文。代表用户执行的服务调用保留原始主体，服务身份不能扩大其权限。详情、列表、计数、导出、下载、事件订阅和幂等回执重放使用同一套访问规则。验证父子资源的实际归属，以及缓存是否会跨用户或工作区命中。

每个操作声明接受的凭据类型与传递方式，多种凭据同时出现时不得静默切换主体，身份冲突的组合应拒绝。采用 Cookie 认证的写操作须提供 CSRF 防护。具体登录态、服务身份和运行时授权方案由组件设计维护。

明确配置和授权的生效时点，不能把历史授权当作永久有效；具体快照和重验时机由组件设计维护。用跨工作区引用、撤权后继续、授权范围不同的缓存读写验证边界。会话配置与逐轮授权方案见 [backend 职责与边界](../../backend/README.md#职责与边界)。

## SDK 和服务客户端

区分连接失败、超时、调用方取消和服务端返回的错误。自动重试限于可安全重复的操作，并设上限。分页迭代保留查询条件，遇到重复游标给出协议错误，避免无限请求。

客户端保存服务端请求标识供排查，重试同时遵守端点声明的幂等条件。不要在公共客户端中为所有写请求自动附加 key 或自动重放；仅在端点需要时生成去重键，同一次逻辑操作重试沿用原键和内容。版本冲突交由调用方重新读取判断，不自动替换预期版本；超时或断线不能当作服务端未受理。

## 后台任务与事件

为每类消息写清何时算已接收、何时算处理完成，以及如何处理重复和乱序。允许重放的消费者在处理成功后保存进度。验收覆盖“业务写入成功、确认响应丢失”后再次收到同一消息的结果。

区分输入已受理、已派发、执行已完成和结果已送达。持久化派发意图后再进行外部调用。接管时核对所有者和执行代次；消费者按事件身份去重，处理成功后推进进度。外部请求取消或响应丢失时，依据原调用回执判定结果。无法证明是否产生副作用时记录未知。

验证“提交成功但确认丢失”、重复或乱序消息和旧执行者迟到写入。结果通知发送失败时，保留已完成的业务任务。

## 日志与追踪

**请求标识**

HTTP 入口在第一条请求日志之前确定 `trace_id`。有效且受信的上游链路可以续接，缺失或无效时生成新值。每个 HTTP 响应在 `X-Request-ID` 返回它，错误体的 `request_id` 和 SDK 暴露的请求标识也使用这个值。请求上下文自动为每条日志附上 `trace_id`，包括校验、鉴权、业务处理和依赖调用产生的日志。调用方拿到 `request_id` 就能按 `trace_id` 原值检索。

服务间调用传播链路上下文。请求派生的异步任务将关联信息随任务保存，工作进程取出后恢复，重试时保留原值并记录尝试次数。独立定时任务在每次运行开始时建立自己的链路。进程启动、退出等没有请求上下文的日志用服务和实例标识定位。

**关键操作与错误**

在默认 INFO 日志级别下，应能查到关键操作的执行结果和所有失败记录。

| 场景 | 记录时机与内容 |
| --- | --- |
| HTTP 请求 | 请求结束时记一条摘要，包含方法、路由模板、实际状态码和耗时。若失败，附稳定的错误码。 |
| 关键业务操作 | 创建、删除、权限或配置变更等动作记录操作者标识、对象标识、动作和结果。涉及状态转换时记录变更前后状态，成功日志在事务提交或外部结果确认后输出。 |
| 异步或长任务 | 在受理、开始、完成、取消和最终失败时记录任务标识及阶段。出现重试时记录原因和尝试次数，使请求返回后仍能查到实际结果。 |
| 错误 | 每个请求或任务的失败都必须有可检索的日志。预期的输入错误、权限拒绝可在请求摘要中以 INFO 记录。需要关注的可恢复异常记 WARN。服务端 5xx、后台任务异常终止、重试耗尽和未捕获异常记 ERROR。 |

下层向上返回错误时补充失败步骤和依赖名称，由决定最终结果的请求或任务处理层记录一次错误详情。错误已在当前层处理时，由当前层记录其原因及采取的动作。错误记录要能回答“哪个操作、哪一步、为什么失败”，包括 `error_code`、安全的原因摘要和相关对象标识。未捕获异常附脱敏调用栈。

服务日志每条输出一行 JSON。公共字段为 UTC 时间 `time`、`level`、`service`、`event` 和简短的 `msg`。事件名保持稳定，标识、耗时、结果等变化值使用独立字段，便于过滤和统计。字段按用途选取，所有级别都排除密钥、密码、Token、Cookie、签名 URL 和请求或响应正文。下面是一条异步导出重试耗尽后的日志。

```json
{"time":"2026-01-15T10:32:14Z","level":"ERROR","service":"agent-engine","event":"export.failed","msg":"导出文件写入超时，已用尽重试次数","trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","job_id":"job-42","step":"write_file","dependency":"object_store","error_code":"storage_timeout","attempt":3,"duration_ms":3015}
```

验收时让一次已受理的任务在下游失败。从客户端收到的 `X-Request-ID` 出发，按同值检索到入口摘要、任务受理及最终错误，能定位失败服务、步骤和原因。另用一次入口校验失败核对错误体 `request_id`、响应头和日志 `trace_id` 三者相等。
