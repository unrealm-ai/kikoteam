# 数据库开发

适用于数据归属、持久化查询、结构迁移与数据清理。数据库选型、迁移执行归属及存储布局由组件与架构文档维护。

**章节导航**　[建模与查询](#建模与查询) · [迁移与回填](#迁移与回填) · [生命周期与清理](#生命周期与清理)。追加阅读条件见[规则索引](../../AI_RULES.md#按任务查阅)；写入权、跨组件提交点和资源引用关系见[数据归属](../architecture/data-ownership.md)。

## 建模与查询

Backend 自有业务表按权威数据所有者命名：Platform 使用 `platform_` 前缀，Manager 使用 `manager_` 前缀。前缀表达所有权，不代表独立 schema、独立数据库或独立迁移集；跨模块共享读取不改变所有者。Engine、Event Hub 等其他组件拥有的表不得机械归入 `manager_`。已发布表名和迁移不因本规则追溯改写，确需更名须新增迁移并协调调用方。评审与测试应核对新表前缀、写入归属及跨模块引用一致。

- 建表先明确记录代表什么、状态的权威写入方、主键是什么、哪些字段组合唯一、引用谁，以及删除时如何处理引用。字段定义说明类型、可空性和默认值，尤其注意“未提供”“未知”和“零值”的不同语义。跨工作区引用应能验证父子资源实际归属。
- 把并发下也必须成立的条件落到数据库，例如唯一约束、外键、稳定的数值约束、版本条件或事务内检查。业务层统一校验权限、格式和状态转换。创建前预查可以改善报错，并发创建仍由唯一约束裁决。
- 按真实查询设计索引，同时考虑授权条件、过滤条件、排序和翻页方向。关键查询用代表性数据查看执行计划，确认索引覆盖的是实际访问路径。用相同排序值的样本验证稳定分页。
- 需要共同成功的写入放进一个事务。业务状态变更与实际需要的去重记录、可靠事件或待派发记录按原子性要求提交；不为普通 CRUD 默认增加幂等表或完整响应缓存。去重优先保存必要的请求指纹和稳定资源引用，业务权限仍须在返回时核验。外部 I/O 放在事务之外。
- 并发写入按业务边界采用短事务、条件更新及唯一约束，组件设计明确锁顺序、裁决点和超时行为；取得锁后核验当前状态，不使用锁外旧读结果更新。执行代次只能隔离持久化写入，运行中旧进程及外部调用的隔离另由运行时落实。
- 仅对已确认回滚且可安全重做的数据库事务作有限重试，保留原请求身份和预期版本。连接断开或提交结果未知时，按端点的去重、状态或版本约定核对；数据库重试不包含外部模型、命令或工具调用。

## 迁移与回填

迁移脚本、执行器、迁移历史和结构快照应有明确的维护归属，业务查询与运行时写入权仍随数据所有者维护。同一迁移集内编号唯一、递增；已发布脚本保留原文，修正使用新编号。结构快照从临时空库全量重放迁移后生成，排除迁移工具内部状态；生成查询访问代码时使用同一结构来源，输出归消费模块维护。

**执行与恢复**

1. 执行评审过且与发布版本对应的迁移集。迁移入口、打包方式、工具选择和启动依赖记录在所属组件文档中。
2. 并发部署时确保同一迁移集不会被多个执行者同时推进。协调机制应支持空库启动，并明确执行权失效时如何停止后续操作；具体机制由组件设计确定。
3. 每次执行前重新读取已应用版本，按序执行待应用脚本并跳过已完成版本。恢复以已提交历史和实际结果为准，不能仅凭取消、超时或断线推定回滚。
4. 默认将单条迁移 SQL 与成功版本记录放在同一事务内提交。失败时停止后续升级，记录迁移编号和脱敏原因，向调用方返回失败，下次从已确认状态继续。必须在事务外执行的 SQL 应明确中断后如何识别和处理部分完成的结果，再决定是否重试。
5. 明确迁移期间各消费者的错误处理与恢复方式，区分后续访问恢复和已失败操作的重试。避免临时依赖错误造成不可恢复的初始化状态。

涉及数据回填、应用回退或破坏性结构变更时，说明已有数据的影响和恢复步骤。项目迁移归属、目录和启动方案见 [event-hub 组件设计](../../event-hub/README.md#启动与数据库迁移)。

**生成与验收**

同一变更提交新增迁移、重新生成的结构快照、受影响的查询与生成代码。CI 在隔离的临时库重放全部迁移并重新生成，发现版本号冲突、已发布脚本被改写或生成物差异就报告失败。另用带数据的旧版库验证升级和回填结果。重复运行应没有待执行项；并发运行时每个版本只成功应用一次；执行权失效或中途失败后应能从已确认状态恢复，事务外 SQL 另按恢复说明核验。

带旧数据升级时尤其核对新增默认值和历史引用的结果。验证空库初始化、迁移失败、并发执行和消费者恢复行为符合组件设计。测试应检查可观察的业务结果，区分待执行的验收要求与实际通过的验证记录。

## 生命周期与清理

每个资源说明支持哪些操作，例如停用、归档、删除和恢复。每个操作都要说明普通列表和详情是否可见，已有引用是否还能读取，能否建立新引用，以及原业务键在什么条件下可以复用。验收时分别以新调用方和持有旧引用的调用方验证结果。

按数据保留需求选择软删除、物理删除或到期清理。数据库记录、关联文件和历史记录分别说明保留期限及清理条件。清理前核对仍有效的引用、在途操作和幂等回执。释放资源后仍需要查询的结果应有明确的读取入口。

对象上传采用候选登记、上传校验、提交引用的顺序。清理前核对有效引用、在途操作、写回租约和仍需去重的回执。测试沙箱回收后历史及已发布产物仍可按权限读取，并区分未发布临时文件与已提交数据。
