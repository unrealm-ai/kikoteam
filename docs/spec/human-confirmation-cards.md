# 人工确认卡片与答复

范围：执行任务等待指定人员确认、确认人在 Web 或渠道内答复、原卡完成态和拒绝通知。不改变任务发起人、确认人选取或交接权限。

## 题型与提交

- 同意／拒绝使用独立的 `decision`（`approve` 或 `reject`），可不设题目。可附选填说明 `text`。飞书和可答复的 Web 收件箱提供说明框；钉钉、企微的原生审批卡不显示说明框，仍优先发卡。确认人要带说明可直接用文字回复。
- 提交型支持单选（选项 ID 作为 `value`）、多选（`optionIds`）、文字和数字。允许单题或混合；每题独立设置是否必答。旧式纯文字题与逐项文字提交继续有效。待确认工具返回有权限的题目、选项 ID 及显示文案；文字回复有歧义时先澄清，不依赖渠道历史能否读取卡片。
- 卡片操作和文字答复使用同一业务确认事务。验证确认人、确认单和版本；卡片还核验原投递、绑定身份以及回调来源。只有首个有效答复改变状态。批准或信息提交冻结答案并恢复原任务；拒绝停止，不启动新一轮执行。拒绝说明存入确认结果；存在原发起人的可验证私聊时发一条主动通知，不向原群聊公开。

## 渠道与原卡

| 渠道 | 表单投递 | 原卡更新 |
| --- | --- | --- |
| 飞书 | 原生卡；扫码创建配置包含卡片回调事件。已绑定应用仍需要在开放平台实际开通并发布回调 | 点卡可随回调更新；也可按原消息主动刷新完成态 |
| 钉钉 | 使用内置示例审批和表单模板，不要求用户自配模板。模板不适用才走文字 | 点卡或通过原卡实例更新。模板无法表达的完成态不宣称更新成功 |
| 企业微信 | 原生审批与可表达的纯选择题优先用卡；有文字或数字填空时整单发送文字 | 点击后可用对应回调更新。先用文字答时，后端先结单，旧卡再次点击只按服务端已保存的结果更新。例如先用文字同意，再点旧卡「拒绝」，仍显示「已经同意，无需再次提交」，不会停止任务或再次续跑 |
| Web | 沿用待确认收件箱及同一提交契约 | 使用服务端保存的确认状态 |

投递失败和结果未知分开处理，不能因未获得回执而无条件重发。原卡更新不补发卡片、不改变业务答复结果、不启动执行轮次。飞书确认通知成功回执和 Web 收件箱发布会向存在的确认人私聊写一次不触发模型的系统输入。发起人私聊中的拒绝结果通知不属于该回写。

## 回归证据

- [测试分支的真渠道演练](../proposal/human-confirmation-cards.md#测试分支验证与渠道限制)覆盖飞书原卡主动刷新与回读、钉钉审批和表单的主动更新接口。企微原卡替换只在按钮回调中验证。正式分支手机端完整业务流程、飞书扫码新建真实应用和钉钉跨组织模板使用未作为已通过项。
- 隔离 PostgreSQL 回归覆盖事件写入的会话范围、投递后只回写一次、不产生轮次、拒绝重放、群聊抑制、发送前权限撤回及终态卡片的版本／配置约束。Web 组件覆盖结构化作答、选填说明、已答生命周期与权限撤回。
