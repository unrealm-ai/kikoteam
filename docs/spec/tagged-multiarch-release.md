# Git 标签与双架构镜像发布

## 行为基线

- **R1 触发与版本。** 正式版本来自 Git 标签 `vX.Y.Z`（三段非负整数，不接受前导零、预发布或后缀，最长 128 个字符）。推送该标签才执行发布镜像流程，且标签指向的提交必须已进入 `main` 历史并包含此工作流。不匹配标签过滤器的标签不启动发布；匹配过滤器但未过严格校验的标签在构建前停止。普通 PR 和 `main` 推送继续执行相应的 CI 检查，不再触发镜像发布。
- **R2 构建与验收。** Backend、Event Hub、Agent Engine 分别在原生 Linux AMD64 与 ARM64 runner 构建；为同一提交生成三个双架构 OCI 索引。验收按固定候选摘要和平台运行，不读浮动标签。验证 Backend/Web、Event Hub 迁移和就绪，以及打包 Engine/Pi/Runner/内置 MCP 的端到端用例。独立的手动验收可指定已发布的完整 SHA（要求三个引用确属同一双架构版本），留空读取部署指针的完整批次，不执行发布。
- **R3 晋级与重跑。** 两种架构都通过才发布版本标签。已接受的版本固定到其提交及镜像索引摘要，不因重跑改变内容。补发较旧版本不覆盖 `latest` 或部署指针。注册表不能将多个标签原子地更新；晋级中断时可能出现部分标签已更新，重跑同版本恢复已验收的摘要。需要一致版本时固定版本标签或使用部署指针。
- **R4 托管部署。** 在三个 `latest` 都已更新并验证后，才更新 `backend:verified-deploy`。指针保留单调部署序号、完整源码 SHA 和三个索引摘要，并记录产品版本。部署器仍可读取已有仅 AMD64 的旧指针，但新双架构验收会拒绝该指针。不同的已验收摘要即使来自同一 SHA，也不复用当前部署的本地标签，以保护回退版本；托管机需更新部署器后才能处理这类发布。推进指针是供托管部署器消费，不表示新版本已经在运行。
- **R5 安装范围。** 本地 `./start.sh` 仍从源码构建；包名和访问权限保持不变。Linux ARM64 通过 CI 不等于 Apple Silicon Docker Desktop 实机验收。

## 实现与验证

[构建与晋级](../../.github/workflows/images.yml) · [镜像验收](../../.github/workflows/image-acceptance.yml) · [部署器](../../deploy/auto/deploy.py)

| 需求 | 验收方法与预期 |
| --- | --- |
| R1 | 检查普通分支推送与标签过滤；合法标签继续，错误标签和非主分支历史退出，未写入发布引用。 |
| R2 | 两种原生 runner 各验证索引选中的实际镜像及源码版本，验证空库迁移、HTTP 及 Engine 工具运行。任一失败阻止晋级。 |
| R3 | 对较旧版本、同版本重跑、同版本改提交分别验证：不回退、沿用原摘要、拒绝覆盖；模拟部分晋级中断后恢复。 |
| R4 | 指针对照已验收的三份索引摘要；[部署器用例](../../deploy/auto/test_deploy.py) 验证旧指针兼容、恢复拒绝错误标签或混用镜像、部署序号前进，以及相同 SHA 不同摘要时使用不同本地标签完成切换并保留旧版回退。 |
| R5 | 单独用 M 系列 Mac 在 Docker Desktop 启动隔离环境，检查容器平台、服务与任务。 |

验证记录：工作流静态检查、标签校验、模拟注册表的晋级与中断恢复、部署器回归，以及基于缓存 AMD64 镜像的隔离三服务冒烟已通过；未推送发布标签，未运行真实双架构发布和 M 系列 Mac 实机验收。

### 从旧发布工作流切换

首次打正式标签前，确认旧的 main 镜像发布和部署指针工作流均已结束；切换后不要重跑旧发布记录。GitHub 重跑会使用原提交的工作流，旧逻辑可能覆盖新标签的 `latest` 或部署指针。首发后核对三个 `latest` 索引及 `verified-deploy` 的提交和摘要是否与已验收版本一致。
