# 主分支与版本标签的 AMD64 镜像发布

## 行为基线

- **R1 触发与版本。** 每次推送到 `main` 都构建并发布三个服务的提交镜像，以完整 SHA 和 7 位短 SHA 标记。正式产品版本来自指向 `main` 历史的 Git 标签 `vX.Y.Z`（三段非负整数，无前导零，最长 128 个字符），单独发布对应版本标签。PR 与其他分支运行各自的 CI。
- **R2 构建与验收。** Backend、Event Hub、Agent Engine 各在原生 AMD64 runner 上构建一次。每个服务的 OCI 索引只包含一个可运行的 `linux/amd64` 镜像，并携带构建证明和 SBOM。验收按三个候选摘要启动服务，验证 Backend/Web、Event Hub 迁移和就绪，以及打包的 Engine/Pi/Runner/内置 MCP。手动复验可指定已发布的完整 SHA，留空读取部署指针。
- **R3 晋级与重跑。** AMD64 验收通过后才发布提交标签或版本标签。晋级串行执行，重跑使用该次发布首次记录的三份索引摘要。写入 `latest` 前读取远端 `main` 顶端，已被后续提交取代的构建只发布自己的 SHA 标签。补发产品版本只写该版本的引用。部分服务的别名更新中断时，可重跑恢复同一批次。
- **R4 开发环境自动部署。** 三个 `latest` 都更新并验证后，`main` 流程才写入 `backend:verified-deploy`。指针记录单调部署序号、完整源码 SHA 和三个索引摘要。开发机发现更高序号就拉取镜像、进入维护并停止应用，进行中的对话、任务或上传可能中断。部署器校验数据库和共享目录备份，启动新版本，并在服务及公网入口验证通过后记录新序号。相同或更低序号直接跳过。
- **R5 安装范围。** GHCR 为 Linux AMD64 部署提供预构建镜像。Mac 本地开发通过 `./start.sh` 从源码构建。

## 实现与验证

[构建与晋级](../../.github/workflows/images.yml) · [镜像验收](../../.github/workflows/image-acceptance.yml) · [部署器](../../deploy/auto/deploy.py)

| 需求 | 验收方法与预期 |
| --- | --- |
| R1 | 检查 `main` 推送与正式标签均进入构建，普通 PR、其他分支及删除引用不发布，标签须通过格式与主分支历史校验。 |
| R2 | 核对三个发布索引的可运行平台均为 `linux/amd64`，在原生 runner 验证实际镜像及源码版本、空库迁移、HTTP 和 Engine 工具运行。 |
| R3 | 验证旧提交晚完成、正式标签补发、同一提交重跑和别名冲突。只有当前主分支顶端可更新部署指针，重跑沿用首次验收摘要。 |
| R4 | [部署器用例](../../deploy/auto/test_deploy.py)覆盖相同或更低序号跳过、更高序号触发停服备份和重启、相同 SHA 改变摘要时保留回退镜像，以及迁移或入口验证失败时保留原部署序号。 |
| R5 | 本地源码启动走仓库的 Compose 测试，发布镜像走 AMD64 验收。 |

### 从旧发布工作流切换

GitHub 重跑会使用原提交的工作流。切换期间应等旧发布作业结束，后续从新工作流重试发布。可用首次 `main` 发布的完整 SHA 核对三个 `latest` 索引，以及 `verified-deploy` 的提交和摘要。
