## 职责与边界

- **数据库迁移**　统一维护全项目 PostgreSQL 迁移 SQL、执行器、迁移历史和结构快照。当选实例在启动业务工作前自动执行迁移；具体流程见[启动与数据库迁移](#启动与数据库迁移)，通用要求见[迁移与回填](../docs/rules/database.md#迁移与回填)。业务查询和各类记录的写入权仍归所属组件。
- **连接与入站**　按配置建立飞书 WebSocket、钉钉 Stream 和企微智能机器人长连接，处理启停、重连、换绑与状态上报。保留可信的租户、机器人、发送人、群、话题和消息标识，将输入送至 backend 去重受理。
- **业务定时与后台作业**　推进到期业务计划、通讯录同步等渠道工作，向 backend 提交带身份的触发。定时事件绑定规则版本、计划时刻和业务身份，重启后按计划约定处理漏触发。Engine 失联检查、Session 分配及环境执行维护归 backend / Engine。
- **执行边界**　渠道及计划产生的工作统一交 backend 受理。Engine 注册、心跳、容量和 Session 分配由 [backend](../backend/docs/engine-dispatch.md)负责，event-hub 不写执行归属或代次。

Conversation、Task、执行 Session 和共享环境均由 Backend 统一创建/登记，Hub 不自行创建 Sandbox 或决定回收。父会话归档后，后续渠道/定时事件由 Backend 准入与路由规则裁决，不得绕过归档重新开放原执行。生命周期见[专项设计](../docs/architecture/conversation-lifecycle.md)。
- **发送与回执**　消费 backend 登记的 Delivery，向指定目标发送答复、人工确认或事项通知。需要沿原连接回复时使用对应机器人连接。记录提供方可证实的发送结果；结果未知时按原操作标识核对。 企微联系人验证码的固定答复是例外：仅收到 Backend 已提交的类型回执后，沿原认证回调的 Socket 与请求标识回复一次，不写普通发件队列。丢失 ACK 或收到重复事件都不重发，也不回显验证码。

**交接边界**　失锁或无法确认主身份时，取消正在执行的迁移，停止后续 SQL、新业务触发及发送并关闭旧连接，然后退出。正常停机先停止新工作并收尾，最后释放锁。接管者重新读取已提交的迁移历史，并核对在途操作；渠道能力决定哪些结果可以查证。任务完成由 backend 根据执行事实判定。

**验收场景**　滚动重启期间同一期计划只触发一次。企微回复已发出但回执丢失时，保留原投递身份和未知结果，避免盲目重发。

## 代码与运行入口

GitHub Actions 随每次 `main` 更新发布 `ghcr.io/unrealm-ai/kikoteam/event-hub`，迁移 SQL 嵌入同版本的 Go 可执行文件。支持的平台和镜像标签见[镜像说明](../README.md#容器镜像)。

根目录可用 `make lint COMPONENT=event-hub`。检查器按 `tools/versions.mk` 固定版本自动安装到根 `.tools/`（首次需要网络）；业务函数圈复杂度上限 35，测试不限制复杂度，完整规则见[静态检查](../docs/rules/static-checks.md)。Python 辅助脚本不新增 lint。

Go module 位于本目录，最低 Go 1.26；CI 使用 Go 1.27.2、PostgreSQL 16。`cmd/event-hub` 装配信号、配置和日志，`internal/election` 管理持锁会话，`internal/app` 管理探针和单次主身份的生命周期，`database/postgres` 打包并执行迁移。`app.Work` 是以后接入在途恢复及业务工作的位置；未配置渠道 Backend 时入口仍传入 nil，迁移完成后维持主身份并等待退出；配置后接入飞书 Supervisor，不伪造其他渠道或业务定时能力。

在本目录执行：

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt  # OpenAPI 3.1 校验器，开发与 CI 使用
make build                         # 输出 bin/event-hub；发布时传 VERSION=<提交或版本>
make fmt                           # 格式化自有 Go 源码
make lint                          # 只检查：格式、golangci-lint、补丁、OpenAPI；不需要 PG
make vet
make test                          # race 测试；未提供测试 DSN 时明确跳过 PG 集成测试
export EVENT_HUB_TEST_DSN='postgres://postgres@127.0.0.1:5432/postgres?sslmode=disable'
make check                         # 必须有真实 PG：lint、race 测试、快照比较
make check-history BASE_REF=<基线提交>
make schema                        # 新增迁移后生成快照；不能手改 schema.sql
```

测试和快照工具需要专用测试 PG 的 `CREATEDB` 权限，分别新建 `event_hub_test_*`、`event_hub_schema_*` 数据库并清理；示例 DSN 应替换为本机测试实例。快照工具要求 PG 服务端和 `pg_dump` 都是 16.x，且客户端补丁版本不能低于测试服务端；CI 固定服务端和客户端为 16.16。旧客户端导出新服务端时可能带入非确定性的内部列版本（例如 16.15 客户端导出 16.16 的 `pg_attver`）；应升级客户端，不过滤业务结构 SQL。另需 Python 3、Git 执行源码及迁移历史检查。生产 Event Hub 不需要建库权限或 `pg_dump`。CI 入口为 [event-hub.yml](../.github/workflows/event-hub.yml)，对 PR 基线或 push 前提交检查历史不可变性，并运行上述检查与构建；新增正式业务迁移后应同时评审生成的快照。测试无法获得 PG 时，CI 会失败，不静默跳过。

运行时由部署环境注入 `EVENT_HUB_DATABASE_URL`，再运行 `./bin/event-hub`。不要将凭据提交到仓库或写入日志。配置如下，所有时间值使用正数 Go duration（例如 `2s`、`10m`）：

| 环境变量 | 默认值 | 作用 |
| --- | --- | --- |
| `EVENT_HUB_DATABASE_URL` | 必填 | 所有候选访问同一 PG 写入口与业务数据库 |
| `EVENT_HUB_CONNECT_TIMEOUT` | `5s` | 单次连接及竞选查询超时 |
| `EVENT_HUB_RETRY_INTERVAL` | `2s` | 备用竞选间隔，附加 0～20% 抖动；连接失败指数退避，基准上限 30 秒 |
| `EVENT_HUB_HEARTBEAT_INTERVAL` | `3s` | 空闲时核对持锁状态的间隔 |
| `EVENT_HUB_HEARTBEAT_TIMEOUT` | `2s` | 获得连接执行权后单次心跳超时 |
| `EVENT_HUB_MIGRATION_TIMEOUT` | `10m` | 本次启动全部待应用迁移的总操作预算，不是每条各 10 分钟 |
| `EVENT_HUB_SHUTDOWN_TIMEOUT` | `15s` | 工作停止、解锁及 HTTP 退出共用的总预算 |
| `EVENT_HUB_HEALTH_ADDR` | `127.0.0.1:8081` | 内部探针监听地址 |

## 内部模块与 Go 工程组织

Event Hub 先保持一个服务 Go module、一个常驻服务入口，内部按职责拆 package，而不是为每个系统模块新建 `go.mod`。当前已实现的是启动、选举、迁移和退出基础设施；`channel` 已有首批飞书适配和可选入口，`scheduler` 仍仅包骨架。

```text
event-hub/
├── go.mod / go.sum           # Event Hub 服务的依赖与 module 路径
├── cmd/
│   ├── event-hub/main.go     # 常驻服务入口：装配依赖、信号及退出
│   └── schema/main.go        # 开发期结构快照工具，不是第二个常驻服务
├── internal/
│   ├── app/                 # 已有：配置、日志、探针和主身份生命周期
│   ├── election/            # 已有：选主及持锁连接
│   ├── channel/             # 飞书长连接、配置同步及协议收发
│   └── scheduler/           # 包骨架：定时触发
├── database/postgres/       # 已有：全局迁移执行、嵌入 SQL 与结构快照
└── third_party/goose/       # 已有：受控第三方依赖适配，不是服务子模块
```

`lifecycle` 是生命周期职责的称呼，不要求新增同名目录。当前 `internal/app` 已经协调选主、迁移、恢复、运行和退出，调用 `internal/election` 与 `database/postgres` 完成专门工作。先保留这些边界，不把整个 Event Hub 移进 `lifecycle`，也不移动 `go.mod`、命令入口、迁移文件或第三方依赖。以后确有必要拆出 `internal/lifecycle` 时，只提取相应协调逻辑，避免连配置、日志和 SQL 都塞入一个包。

| 部分 | 负责 | 不负责 |
| --- | --- | --- |
| `app` / 生命周期协调 | 装配运行依赖，组织选主后的迁移、恢复与启动，管理健康状态、取消和退出收尾 | 不实现渠道协议或 AI 员工业务状态机 |
| `election` | 获取和核验主身份，管理持锁连接及失锁取消 | 不判断用户权限或执行任务 |
| `database/postgres` | 统一迁移文件、版本执行与结构快照 | 不因持有迁移职责而接管所有模块业务表写入 |
| `channel` | 建连、重连、渠道格式转换、协议回执、连接状态、沿连接发送及提供方结果回报 | 不决定使用范围、确认人、任务交接；普通 HTTP Webhook 仍由 backend 接收 |
| `scheduler`（包骨架） | 发现到期计划并产生带稳定触发身份的事件，按约定处理恢复和漏触发 | 不运行 Agent Loop，不承载完整业务任务状态机 |

长连接事件与定时事件交给 backend 的 `service` 处理业务。`channel` 的协议发送与 `service` 的投递状态、业务重试分开；计划管理与实际到点触发分开。具体传输方式、持久化受理与 ACK、计划获取和漏触发政策尚待设计，不因拆包默认采用某个协议。现有 `app.Work` 提供 `Recover`、`Run` 接入点；接入时需要组合各模块，使恢复先于运行，取消后关闭连接并等待 goroutine 退出，不能绕过主身份生命周期。

### Module、package 与进程的区别

- **Go module**：由 `go.mod` 定义依赖及导入路径边界，不等于一个操作系统进程。`third_party/goose` 自带 module 是依赖管理需要，不代表独立服务。
- **Package**：源码职责和可见性边界，通常一个目录一个包。`channel`、`scheduler` 可以共享 Event Hub 的 `go.mod`，通过进程内接口协作。
- **命令与进程**：`cmd/<名称>` 下的 `package main` 编译成可执行程序；运行一次产生一个进程。同一 module 可以提供多个命令。同一二进制也可以启动多个实例。
- **Goroutine**：同一进程内的并发执行，不提供独立进程的部署和故障隔离。

目前各模块共用同一 Hub 主身份，仍是多副本部署、全局单活；包的数量不会增加活跃实例数。如果以后拆成渠道进程和调度进程，可以先在同一 module 增加独立 `cmd` 入口，不必立即拆出多个 `go.mod`。独立依赖、版本或发布需求出现后，再评估 module 边界。

拆进程不是仅增加入口：若两个角色继续争抢当前同一把排他锁，它们不能同时活跃。届时必须重新评审角色归属、锁范围、唯一迁移执行者、跨进程通信、接管和旧实例失效机制，不能擅自修改现有锁键或让每个进程各执行一套迁移。Engine 注册、心跳、容量及 Session 分配已由 [API 设计](../backend/docs/engine-dispatch.md)承接，本节不改变该职责划分。

## 选举锁与连接

每个实例建立一条由选举模块独占管理的 PostgreSQL 物理连接，在同一个业务数据库上尝试取得会话级排他锁：

```sql
SELECT pg_try_advisory_lock($1::integer, $2::integer);
```

两个参数固定为项目命名空间 `0x4b494b4f`（KIKO）和 event-hub 选举编号 `1`，定义在 `internal/election/session.go`。同一套部署的所有实例、所有版本使用相同键，不能带实例 ID、版本号或随机值；同一数据库内的其他 advisory lock 使用不同键。该函数立即返回：`true` 表示当选，`false` 表示保持备用并按间隔重试；当选前查询失败时保持非主状态，重建连接后再竞选。已取得锁后，即使读取会话 PID 失败，也清理并结束本次启动，不在同一进程重选。备用实例不执行迁移、不建立机器人连接、不扫描业务定时任务、不发送消息。

会话级锁持续到主动释放或数据库会话结束，不随事务提交或回滚释放；不使用事务级锁或长期打开的事务维持主身份，也不创建选举业务表，因此空库即可竞选。取得锁后不能用重复加锁充当心跳，因为会话级锁可重入，重复获取会累计释放次数。语义见 [PostgreSQL advisory lock](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS) 和[锁函数](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS)。

持锁连接贯穿迁移和业务运行，不归还普通连接池，也不允许透明重连后沿用原主身份。迁移 SQL、迁移成功记录，以及 event-hub 所属业务触发和投递的关键主实例写入，都在这条连接上串行执行；各自仍按业务要求使用事务，外部网络调用在事务之外。普通查询可以使用连接池。所有待执行的主实例工作受同一生命周期控制，失锁后取消排队中的工作，不能将失败的关键写入转交其他连接继续执行。

这使数据库结束持锁会话时，旧主不能在另一条连接上继续迁移或提交新的主实例业务写入；旧会话尚未结束时，其他实例也拿不到同一把锁。迁移使用 Goose 的本地外部连接适配，传入该连接且不增加迁移锁，见[Goose 适配说明](third_party/goose/README.md)。

`Session.Do` 串行执行持锁操作，开始前在同一连接查询 `pg_locks` 核对持锁状态；操作超时从取得串行执行权之后计算，并保留调用方更早的截止时间。回调必须使用传入的 context，结束自身事务，不能保留原始连接或改变选举锁。当前基础实现对任何已开始的持锁 SQL 操作错误都结束本次主身份，包含业务 SQL 错误；业务层若要处理可预期冲突，应在回调内明确处理并保持事务完整。正常停机通过 `Session.Drain` 先关闭新操作和排队操作的入口，再取消业务 context，让已经开始的持锁操作在原截止时间及进程退出预算内完成。故障路径通过 `Session.Stop` 强制取消运行中及排队中的操作；`Stop` 不主动解锁，但驱动取消或连接故障可能结束数据库会话。`Session.Close` 等当前操作退出后才主动解锁和关闭连接。专用池不缓存空闲连接，持锁连接也不会被替换。

部署依赖 PostgreSQL 保持单一可写主库，所有竞选连接访问同一写入口；数据库主备切换负责隔离旧主库。选举连接采用直连或 session pooling，不能经过 transaction pooling；[PgBouncer 支持说明](https://www.pgbouncer.org/features.html)明确列出会话级 advisory lock 的限制。

## 启动与数据库迁移

第一阶段即部署 event-hub，即使机器人渠道和业务定时触发尚未接入，也由它完成数据库自动迁移。评审过的迁移 SQL 与执行器随对应版本的 event-hub 工件交付。启动顺序为：建立 PostgreSQL 专用连接 → 获取选举锁 → 读取迁移历史并执行待应用 SQL → 迁移成功 → 核对在途业务触发和投递记录 → 启动当前阶段已接入的连接、业务定时器和投递工作。

选举锁覆盖迁移和业务运行全过程，不另设迁移锁。按[选举锁与连接](#选举锁与连接)在空库上先当选，再初始化迁移历史。每次取得选举锁后重新读取迁移历史，空库从第一条开始，已有库按序执行待应用脚本，跳过已完成的版本；默认让单条迁移 SQL 和成功版本记录在持锁连接的同一事务内提交。

迁移失败时停止后续 SQL 和本次启动，不进入业务运行，记录迁移编号和脱敏原因，清理连接并退出，由部署系统重启。取消或断线不能证明当前迁移一定回滚；下次当选者从已提交的迁移历史核对状态，事务外 SQL 另按部分完成恢复说明处理。backend 和 Engine 独立运行，不以 event-hub 的迁移状态作为启动或整体接流量的前置条件。数据库事务、失败恢复及验收要求见[数据库规则](../docs/rules/database.md#迁移与回填)。

backend 和 Engine 不执行迁移，不检查数据库结构版本或完整性，启动及就绪检查也不等待 event-hub 迁移。缺表或缺字段按当前请求或任务的正常错误语义处理，不导致进程退出或永久失效的初始化状态；结构补齐后，后续访问无需重启即可恢复。已经失败的请求或任务仍按原回执和重试约定处理，具体行为分别见 [backend](../backend/README.md) 和 [Engine](../agent-engine/README.md)。

### 迁移文件与生成

全项目使用一套全局递增的迁移编号，由 event-hub 维护迁移 SQL、执行器、历史和结构快照。业务查询和运行时写入权随数据所有者维护，例如会话分配由 backend 写，Turn 和运行事实由 Engine 写。迁移与快照已采用下表路径，消费组件的查询目录仍为示例。

| 位置 | 谁维护、用来做什么 |
| --- | --- |
| `event-hub/database/postgres/migrations/` | 手写结构变更和必要的数据迁移，例如 `000012_add_display_name.sql`。同一迁移集内编号唯一、递增。已发布脚本保留原文，修正用新编号。 |
| `event-hub/database/postgres/schema.sql` | 在临时空库全量重放迁移，再用 `pg_dump --schema-only` 自动导出结构快照，排除迁移工具自己的版本表。供代码生成和差异检查使用。 |
| `<消费组件>/database/postgres/queries/<模块>/` | 模块所有者维护业务查询。使用 sqlc 时，将查询与共享的 `event-hub/database/postgres/schema.sql` 一起输入生成器，访问代码输出到消费模块自己的仓储包。 |

迁移采用 Goose v3.30.1，驱动采用 pgx/v5 v5.13.0。上游 Provider 接收 `*sql.DB`，本地受控适配新增 `NewProviderWithConn`，借用选举连接，版本表初始化、历史查询、SQL 和成功记录均不切换连接；Provider 的清理与 Close 不释放外部连接。适配禁止 Go 迁移及工具额外锁，保留上游 SQL 解析和事务语义；来源、补丁及升级校验见[适配说明](third_party/goose/README.md)。

迁移通过 `go:embed` 随二进制交付，生产入口只执行 Up，历史表为 `public.goose_db_version`。文件名为至少六位正整数编号加小写下划线名称，例如 `000001_create_sessions.sql`；拒绝重复数值编号、嵌套目录和非 SQL 迁移。启动检查已记录历史是否缺失文件，默认拒绝补插低版本迁移，CI 比对基线禁止修改、删除历史脚本。Goose 本身不记录脚本内容校验和，文件不可变性由代码评审及 CI 保证。

当前尚无已评审的业务建表 SQL，迁移目录仅有说明。空迁移集在空库不创建历史表；已有历史时仍检查工件是否丢失旧文件，不能把空工件当作成功升级。测试表只存在于测试夹具，结构快照目前只包含 PG 空库结构。

单条迁移默认事务执行。确需 `-- +goose NO TRANSACTION` 的 SQL（例如并发索引）必须在该脚本注释中说明部分完成的检测、恢复和重试步骤；失败不能假设没有副作用，也不能靠 `IF NOT EXISTS` 忽略无效索引。复杂函数使用 `StatementBegin/StatementEnd`。自动启动不执行 Down，恢复使用核实后的修复步骤或后续迁移；数据库角色需要目标 schema 的 DDL 和版本表读写权限。

`make schema` 使用专门的测试 DSN 新建临时空库，取得同一选举锁并全量迁移，使用 PG 16 的 `pg_dump --schema-only --no-owner --no-privileges` 导出并排除版本表，规范化版本标头和随机限制标记后写入快照，最后删除临时库。`make check-schema` 只比较，不修改快照。这个开发工具不接受生产迁移目标，部署入口仍只有 Event Hub 启动流程。sqlc 尚未接入；它仍是消费组件查询生成的示例。新增迁移、快照、受影响查询及生成代码的提交要求见[数据库规则](../docs/rules/database.md#迁移与回填)。

## 健康检查与失锁

锁本身没有应用层 TTL，不需要定期续租。持锁连接空闲时执行简单查询检查连通性；正在执行迁移或调度 SQL 时，不在同一连接上并发插入心跳，由当前操作的执行超时和连接故障检测处理异常。迁移超时按迁移需要设置，不套用短心跳超时；排队等待连接也不能误判为心跳失败。

选举与健康检查的默认行为如下；环境变量入口见[代码与运行入口](#代码与运行入口)：

| 参数 | 初始值或处理方式 |
| --- | --- |
| 备用实例竞选间隔 | 2 秒，附加随机抖动；连接失败后保持非主状态，按退避重连 |
| 持锁连接空闲时健康检查间隔 | 3 秒；不重复获取锁作为心跳 |
| 单次健康检查超时 | 2 秒；失败即停止主实例工作并退出 |
| 迁移或调度 SQL 正在执行 | 不并发使用该连接做心跳；按当前操作的超时和连接故障检测处理，迁移不套用 2 秒心跳超时 |

结合客户端操作超时、TCP keepalive 和部署环境支持的 TCP 超时设置，使两端能发现失联。具体值随网络及运行环境确定，并通过断网演练测量实际接管时间，不能仅凭上述参数承诺固定秒数恢复。

当前客户端与服务端 TCP keepalive 设为闲置 10 秒、间隔 3 秒、最多 3 次探测；服务端使用 `tcp_keepalives_*` 会话参数，客户端使用 Go `net.Dialer`。平台对部分 socket 参数的支持可能不同，这些参数不是租约期限，也不能保证代理后的服务器及时识别断线。

进程健康、备用状态、迁移中和业务运行状态分别报告；健康备用不因尚未当选而被存活探针反复重启，迁移中也不能报告为业务已运行。

内部探针为匿名、只读的 `GET /livez`、`GET /readyz`、`GET /status`，契约见 [OpenAPI](contracts/openapi.yaml)。默认只监听 loopback；容器中如设为 `:8081`，应只允许集群运维探针访问，不发布到 backend 公网入口。`livez` 在竞选、备用、迁移、正常运行和收尾期间存活；`readyz` 只在 `standby` 或 `running` 返回 200，迁移、恢复和收尾返回 503。健康备用就绪不等于已经当选，也不等于目标版本迁移已完成。`status` 返回具体 `phase`、当选后的 PG `session_pid`、`workers_configured`；未配置渠道时为 `false`，配置渠道 Work 时为 `true`；不表示所有渠道已在线。响应带 `X-Request-ID`，错误体 `request_id` 与日志 `trace_id` 一致。未知路径返回 404，不支持的方法返回 405。

持锁连接故障、健康检查超时或无法确认主身份时，立即停止产生新工作，取消当前迁移、调度与发送，关闭机器人连接及持锁连接，然后退出。不得在原业务循环仍运行时重连并恢复主身份；重启后从竞选流程开始。

客户端健康检查失败并不代表 PostgreSQL 已释放锁。新实例必须实际取得锁才可接管，接管耗时包含服务端识别旧连接失效并结束会话的时间，不能按心跳参数承诺固定秒数。数据库锁只能仲裁持锁会话，无法撤回已发出的外部请求或瞬间终止故障实例；触发去重、执行代次和投递回执继续生效，未知结果按原操作身份核对。

## 退出与接管

正常发布或停机按以下顺序处理：

1. 停止新业务触发、新发送及渠道重连，关闭主实例工作入口。
2. 在退出时间预算内取消或收尾当前 SQL 和业务操作，关闭机器人连接；尚未确认的结果保留原操作身份供接管者核对。
3. 收尾完成后，最后在原连接释放选举锁并关闭连接。超出退出预算时终止进程，不能提前解锁后让旧工作继续运行。

故障或失锁按[健康检查与失锁](#健康检查与失锁)立即停止并退出，不等待正常业务收尾。进程崩溃后的锁由 PostgreSQL 在结束会话时清理；客户端发出关闭或取消并不等于服务端已经完成清理。

实现中正常退出先进入 Drain，再取消主工作 context；不能直接取消正在使用持锁连接的 pgx 查询，以免驱动提前断开连接，让备用在渠道收尾之前当选。已开始的 `Session.Do`（包括本轮迁移）保留原操作截止时间，并受总退出预算约束；正常退出期间不再进入恢复或业务运行阶段。真正失锁、操作超时或工作异常仍走强制停止，不受 Drain 保护。故障退出只清理，不继续推进业务或重试未知结果。

`SIGINT`/`SIGTERM` 触发正常退出；当选后连接失效、迁移失败、工作异常或收尾失败使进程以非零状态退出，不能因同时收到退出信号而吞掉故障。`app.Work.Recover` 必须在 `Run` 之前完成；`Work.Run` 必须在取消后关闭外部渠道并等待自身 goroutine 结束，不能留下仍在发送的后台任务。总退出预算超时返回 `ErrShutdownTimeout`，程序入口随即终止整个进程；绝不能捕获该错误后继续运行旧工作。部署系统的终止宽限期应大于配置的总退出预算，留出进程退出和数据库清理时间。

新实例取得锁后，先完成[启动与数据库迁移](#启动与数据库迁移)，再沿持久记录恢复工作。event-hub 换主不触发 Session 重分配；执行归属、代次和失联接管始终由 backend 与 Engine 按各自职责处理。发送成功但回执丢失的操作保留未知状态，按渠道能力查证，不能换新操作 ID 盲目重发。业务时序见[触发、分配与接管](../docs/flows/triggers-and-dispatch.md)。

新版本作为备用启动不会抢占旧主。发布流程必须让旧主退出，并让旧版本候选退出竞选，确保目标版本接任，才会执行该版本新增迁移；不能等待新副本成为主实例或迁移完成后才允许旧主退出。接任后验证目标版本的迁移和业务运行状态，只创建新副本不代表新增 SQL 已应用。通用发布原则见[发布与退出](../docs/rules/operations.md#发布与退出)。

## 诊断与恢复

选举诊断记录实例标识、运行版本、竞选与主备状态变化、持锁会话身份、健康检查失败及退出原因；必要时结合 PostgreSQL 的 `pg_locks` 和会话信息核对实际持锁者。区分客户端已停止、数据库会话已结束和新主已开始业务三个时刻。

数据库迁移问题从选举状态、迁移编号及执行结果定位。迁移失败时先核对已提交的版本和事务外操作的实际状态，再恢复启动；迁移期间其他组件的缺表或缺字段错误，按对应请求或任务记录排查。恢复后核对 backend 和 Engine 无需重启即可继续访问。恢复演练覆盖双实例竞争、迁移中断、仅持锁连接断开、网络静默中断及滚动交接，具体场景见[验收要求](#验收要求)。

## 验收要求

自动化测试使用真实 PostgreSQL，每个测试创建隔离数据库并清理，不依赖 SQL mock。已覆盖：

- Goose 借入连接的 Ping、Status、Up、HasPending、GetDBVersion、Close；迁移在原 backend 执行，迁移中只有调用方的 advisory lock，完成后连接和锁仍归调用方。
- 迁移重复执行跳过、DDL 失败回滚、成功版本写入失败时 DDL 同步回滚、历史文件缺失拒绝启动、事务外并发索引和复杂 SQL 解析。
- 两个实例从空库竞争，只有一个进入工作、迁移只应用一次；备用在原主退出后重新读取历史接任。
- 迁移中终止 PG backend，已提交版本保留、当前事务回滚，原 Provider 不重连，新持锁会话继续未完成版本。
- 仅终止持锁会话，普通数据库池仍可用，旧主取消工作；退出拒绝排队操作，正在执行的回调结束前不解锁，业务忽略取消导致退出超时也不提前解锁；长 SQL 不被排队心跳的短超时误杀。正常停机遇到正在执行的 SQL 时，保留会话直至 SQL 与渠道收尾完成；收尾错误不再被正常取消掩盖。
- TCP 代理静默丢弃流量，旧主检测超时停止，而服务端会话仍持锁；备用必须等服务端连接结束才接任。真实子进程的 SIGTERM 和 SIGKILL 后备用接任。
- 状态探针、配置校验、错误脱敏；请求标识和生命周期行为。非空迁移快照全量重放、排除 Goose 表及关联序列、可重复生成与差异检出。

以下业务与完整部署场景仍需在对应能力接入后验收，不能把基础测试视为已经覆盖：

- 两个实例同时连接空库，只有一个当选并迁移，备用实例没有渠道、业务定时触发或发送行为；同一迁移版本只成功应用一次。
- 迁移失败时 event-hub 不进入业务运行；backend 和 Engine 在缺表或缺字段时保持进程运行，受影响操作报错，结构补齐后无需重启即可恢复后续访问，已失败操作仍按原回执和重试约定处理。
- 迁移中终止持锁会话或进程，新主从已提交历史继续；旧主不能换连接继续 SQL。事务外迁移按恢复说明核对部分结果。
- 仅断开持锁连接、保留普通连接池和渠道网络可用，旧主仍停止工作并退出，排队中的主实例业务写入不能继续执行。
- 模拟网络静默中断，旧主在故障检测后停止；备用实例在 PG 实际释放锁之前不能接管，不将本地心跳超时当作锁已释放。
- 正常滚动交接先收尾后解锁；新版本启动为备用，旧主退出且目标版本接任后才执行新增迁移，不因发布就绪条件相互等待。
- 外部发送成功但回执丢失、提交成功但确认丢失时，接管保留原操作身份并核对结果；同一期计划去重，正常 Engine 不因 event-hub 换主被无条件重分配。

## 飞书连接首批实现（2026-11-17）

配置 `EVENT_HUB_BACKEND_URL` 和独立 `KIKO_HUB_TOKEN` 后，入口启用 `internal/channel.Supervisor`；未配置时仍只运行选举和迁移。凭据及规则全部经 Backend 内部 API 获取，不读取 Platform 配置表。`EVENT_HUB_CONTROL_ADDR` 默认 `127.0.0.1:8082`，仅用于受认证的配置刷新通知，禁止公开暴露；容器部署应设置内部监听地址。`EVENT_HUB_CONFIG_INTERVAL` 默认 `30s`，最小 `1s`。

主实例在 Recover 全量拉取一致配置后才进入连接运行。Platform 通知 `POST /api/internal/v1/channel-bindings/refresh` 只触发重新拉取，202 不代表已应用。首次拉取失败不建连；周期拉取失败保留最后有效快照，Manager 仍按当前权限和绑定代次准入。删除、停用和变更先取消并等待旧连接退出，再启动新配置；失锁取消所有连接和发送工作，保持原有收尾后解锁规则。首版规则更新也重建该绑定连接，其他绑定不受影响。

官方飞书 Go SDK 固定 v3.13.0。建连前查询 bot info 核验机器人身份并回报；仅结构化 mention 的 open_id 等于当前机器人时视为 @。私聊不进行关键词预筛，飞书群按 @、关键词或 Go 正则 OR 匹配；正文中的昵称/@ 文本不建立身份。正则预编译，规则数量、表达式和消息长度有上限。钉钉、企微适配尚未实现，不沿用飞书群关键词规则。

匹配事件交 Manager 持久 inbox，受理失败或超时从 SDK handler 返回错误，不返回成功协议回执。应用、租户不匹配亦不受理；配置已验证的不匹配群事件直接忽略，不会因后来增加关键词自动补跑。非文本私聊交 Manager 决定支持范围。SDK原始日志关闭，避免凭据、协议内容泄漏；配置保存、已应用、已连接是不同状态。真实飞书账号连通及平台重投行为仍需持有测试应用的验收，单元测试不代表已验证线上收发。

按需历史由 Manager 授权后创建持久 job，Hub 的独立 worker 领取并使用 `internal/channelhistory.Reader` 读取，不能从原始监听流自行补读。每页及发布快照前重新向 Manager 核验同一 job/lease/绑定代次、租户和目标；整个 job 限时 15 秒。用户确认策略为 `since_last_trigger`：上次有效触发之后至本次触发之前，最多 100 条；首次取最近历史。有效触发锚点由 Manager 持久维护，不按 Hub 最后收到或最后发出消息猜测；不跨话题扩读。失败提交 unavailable，由 Manager 降级为当前输入；有界截断提交 partial。快照只作为不可信历史上下文，不授予历史作者当前操作权限。完整授权 Job 比较同时包含上次与本次触发锚点。Hub 不推进边界；Manager 在当前 Input 成功持久受理时原子推进，历史不可用但当前输入成功仍推进，输入失败或拒绝则不推进。历史和当前触发按用户决定合成一条 user 输入，批量/静默追加暂缓。

### 飞书群生命周期（2026-11-18）

Hub 注册机器人/成员加入、删除、撤回及群解散事件，校验 provider 身份后提交 Manager 持久受理；SDK ACK 以有效持久回执为准。elected worker 执行 Manager 租约授权的 `is_in_chat` 只读核验，错误保持未知，由 Manager 持久退避重试。群状态、成员水位、终止墓碑和出站隔离均归 Manager，不驻留 Hub 内存作为权威。详见 [群生命周期](../backend/docs/channel-group-lifecycle.md)。

### 飞书富文本正文

入站 `post`、群/话题历史以及按需共享历史复用同一有界解析器：保留标题、段落、文本样式、Markdown、HTTP(S)普通链接、代码、表情和分隔线；优先 `content_v2`，不与旧版内容重复拼接。语言包装优先中文、英文，其余语言按键稳定选择。图片仅标记“图片附件未读取”，不下载、不读取资源键、不新增附件能力。未知节点保留类型占位，结构非法返回错误，不假装完整正文。

富文本 at 只有展示含义，触发仍只依赖提供方事件 mentions。群正文按真实 mention ID 映射到既有 key，由 Manager 完成显示名解析、前导标签及身份去重；私聊和共享历史直接展示名称，无匹配保留节点名称/ID，不把占位当可信身份。post 沿用原权限、话题隔离、历史锚点和失败路径；仍不受理机器人来源的实时消息。单条 post 限 1 MiB / 10,000 节点。本轮不包含结构化附件、媒体读取和资产 ID，且语言兜底采用确定性排序。
